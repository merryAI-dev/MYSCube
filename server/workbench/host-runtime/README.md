# Dedicated Workbench host installation contract

These are reviewable installation templates, not a provisioned host or an activated service. A Cloud Run candidate does not provide this Docker host. Install only after the independent project, cost, identity and read permissions have been approved. Do not run these units on the business-service host.

## Host and release inputs

- A dedicated Linux host with systemd, Node 24 at `/usr/bin/node`, a local Docker daemon/CLI, and a reviewed `axr-runtime` account. Docker-group access grants host-level authority; non-root and `NoNewPrivileges` do not remove that authority. The generated renderer receives neither the Docker socket nor host credentials. See [Docker's privilege explanation](https://docs.docker.com/engine/install/linux-postinstall/).
- One broker process on the host. The restart guard is not a multi-host lock. Renderers have independent Docker resource limits and run outside the broker service's cgroup. Size the host for the broker, the four renderer limits and the OS; the unit's `CPUQuota` and `MemoryMax` do not limit the Docker daemon's children.
- A reviewed release at `/opt/myscube-workbench`, owned by an installation account and read-only to `axr-runtime`. Install root and `server/workbench` lockfile dependencies, build `dist-workbench` with approved public Firebase auth configuration, and build the fixed renderer image from the **same release and lockfile**. The release must include the runtime imports described by the Workbench Dockerfile. Never transfer local `.env`, cloud CLI credentials, production keys or a developer's `node_modules`.
- A root-owned mode-0600 `/etc/myscube-workbench/runtime.env`, based on `../operations.env.example`, with all actual project/identity values supplied. Set `WORKBENCH_REMOTE_RUNTIME_ENABLED=true` and `WORKBENCH_REMOTE_RUNTIME_DRIVER=docker-host` only after the renderer image and external reaper pass acceptance. Keep AI disabled until its dedicated credential and quota are approved. The runtime account must not be able to edit the environment file or installed code.
- Runtime IAM for the independent Workbench database only. The separately scheduled source-copy identity gets approved source reads; do not put its source credentials in the API/broker process. Use a dedicated attached workload identity or explicitly approved credential delivery, not a developer's home-directory ADC file. `ProtectHome=true` intentionally prevents that fallback.

## Installation and verification

The operator installs `systemd/myscube-axr-workbench.service` and the two units from `../remote-runtime/systemd/` in `/etc/systemd/system`. Review the absolute Node/release paths, account, Docker socket access and resource limits for the approved host before enabling them. The environment file is required; missing configuration must fail startup.

Run `systemd-analyze verify` on all three units, then reload the unit files and enable the reaper timer before starting the Workbench service. These operations must run only on the approved dedicated host. Unit verification checks the definitions; it does not prove identity, cloud access, TLS, actual cgroup enforcement or application health. Service restart and execution settings follow the upstream [service](https://github.com/systemd/systemd/blob/main/man/systemd.service.xml) and [execution](https://github.com/systemd/systemd/blob/main/man/systemd.exec.xml) references.

The service binds `127.0.0.1:8791`. Keep that value out of `runtime.env` so the unit is the reviewed source for binding. A separately configured TLS proxy must forward to this loopback endpoint. Validate the intended origin/host, Firebase authorized domains, body size (application maximum 1 MB), request timeout (up to 125 seconds for generation), security headers and unauthenticated API rejection through the real external endpoint before exposing traffic. No permissive cross-origin proxy or public plaintext listener is supplied by this template.

`PrivateTmp=true` gives Node and its compile/query workers private temporary storage. The Docker CLI uses its Unix socket; renderer temporary files use the Docker-created `/tmp` and `/dev/shm` tmpfs and do not mount the broker's private temporary directory. There is no writable release-directory exception. Logs go to the system journal; configure bounded journal retention on the dedicated host, without printing request bodies or credentials.

On SIGTERM the app stops accepting traffic and initiating renderer sessions. It waits for HTTP drain, confirmed renderer deletion and database termination under one ten-second deadline; only all three finishing produces exit code zero. The unit allows 15 seconds. `KillMode=mixed` sends the initial termination signal to the main process so it can use Docker cleanup, and kills remaining service processes at the deadline. Timeout exits unsuccessfully; containers left after a timeout or broker crash are removed by the independent reaper timer. Until managed containers are gone, the startup guard rejects new broker allocation; the 60-second retry allows recovery after expiry. Verify this with actual process termination on the approved host. It is not zero-downtime recovery.

Acceptance requires: `/health` and static assets through TLS; unauthenticated API 401; current authorized and revoked accounts; real model and source-copy freshness; React click/API interaction; failed candidate preserving the good frame; container resource/network checks; broker crash/reaper cleanup/restart; and host/session latency under concurrent work. Keep traffic closed if any of these checks is incomplete. Record the release SHA and renderer image ID together.

## Rollback

Stop the Workbench service, let its renderer cleanup finish, and inspect only containers with the managed renderer label. Do not delete arbitrary Docker resources. Keep the independent reaper timer active. Switch the read-only release and fixed renderer image together to a previously tested pair, verify the startup guard, then restart and repeat the acceptance smoke checks. Do not roll back or rewrite saved pages, versions, receipts or business data. A schema-incompatible release is not an eligible rollback target.
