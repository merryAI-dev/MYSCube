# SPEC-06 — 목표 아키텍처 (도메인 / 애플리케이션 서비스 / API)

**작성:** 2026-08-07 · **위상:** SPEC-01을 대체하는 **최종 목표 정의**. SPEC-05(트랜잭션 경계)가 이 문서의 상한이다.
**목표:** 안정성을 계층 분리로 높이되, **사용자가 체감하는 개선**을 실제로 만든다.

---

## 0. 두 목표는 충돌하지 않는다

이 프로젝트가 지금까지 실패한 방식은 둘이다.

| 실패 유형 | 사례 |
|---|---|
| 구조만 바꾸고 체감 개선 없음 | `7247ce2` — HTTP 홉 제거, 지배적 비용이 아니어서 무효 |
| 체감 개선만 노리고 구조를 방치 | 14일 61커밋 중 46% fix, 서브시스템 3개 생성 후 삭제 |

**계층 분리는 체감 개선의 수단이다.** 규칙이 한 곳에 있어야 고칠 수 있고, 고칠 수 있어야 느린 경로를 좁힐 수 있다. 반대로 체감 개선이 없는 계층 분리는 이 저장소에서 이미 실패한 접근이다.

**모든 계층 작업은 체감 지표를 하나 이상 개선하거나, 개선의 선행 조건임을 근거로 증명해야 한다.**

## 2. 원칙 1 — 영향 분리와 작업 중단 0

> **요청받지 않은 관심사 때문에 작업이 중단되어서는 안 된다.**

### 2-1. 현재 위반 지점

| 중단 지점 | 위치 | 무엇이 무엇을 막는가 |
|---|---|---|
| 시트 반영 락 → 월 결산 **조회** 차단 | `jvm-weekly-api.mjs` `assertCashflowSheetPublicationReady` | 쓰기 상태가 **읽기**를 막는다 |
| 동일 (JVM) | `…Persistence.java:3596` | 동일 |
| fingerprint 불일치 → 전체 재실행 후 409 | 월 결산 조회 루프 | 낙관적 검사가 응답을 없앤다 |
| JVM 응답 필드 검증 실패 → 502 | 6개 코드 | 일부 결손이 **전체 대시보드**를 없앤다 |

2026-08-06 사고의 본질이다. SPEC-11(PR #470)이 시간으로 끊었으나 **결합 자체는 남아 있다.** SPEC-01 워커가 지금 이 작업을 진행 중이다.

### 2-2. 규칙

1. **읽기는 쓰기 상태로 중단되지 않는다.** 진행 중인 반영은 데이터로 실어 보낸다 (`pendingApply { startedAt, expiresAt }`). 응답을 없애지 않는다
2. **부분 실패는 부분으로 남는다.** 한 섹션 결손 시 그 섹션만 비우고 사유를 표시한다. 전체를 502로 만들지 않는다
3. **도메인 판정 실패는 오류가 아니다.** "이 상태에서는 결산할 수 없다"는 **정상 응답**(결과 객체)이다. 인프라 실패만 오류다
4. **낙관적 검사는 재시도를 유발하되 응답을 없애지 않는다**

### 2-3. 체감 지표

| 축 | 현재 | 목표 |
|---|---|---|
| 반영 진행 중 대시보드 조회 성공률 | **0%** | **100%** (부분 표시) |
| 읽기가 쓰기 상태로 중단되는 지점 | 2 | **0** |
| 부분 결손 → 전체 실패 지점 | 6 | **0** |

## 3. 원칙 2 — 설명 가능한 가이드

> 사용자가 보는 것은 **다음에 무엇을 하면 되는가**여야 한다.

### 3-1. 3층 구조 (SPEC-14로 구현됨, PR #472 머지)

| 층 | 내용 | 대상 |
|---|---|---|
| 1. 가이드 | 무엇이 일어났고 다음에 무엇을 하면 되는지 | 사용자 |
| 2. 상태 | `retry` / `wait` / `contact` | 사용자 |
| 3. 식별자 | `code` + `requestId` (보조) | 지원·개발 |

### 3-2. 계층 배치 — 도메인이 사유를, 서비스가 문구를

- **도메인**: "지금 수행 불가. 사유 X, 해소 조건 Y, 예상 해소 시각 Z" — **구조화된 결과 객체**. 문자열이 아니다
- **애플리케이션 서비스**: 그 구조를 사용자 언어로 번역

도메인이 한국어 문구를 들면 규칙과 표현이 붙어 재사용이 막힌다. 서비스가 사유를 추론하면 규칙이 두 곳에 생긴다.

### 3-3. 알려진 한계

`resolution: 'contact'` 7건 중 3건(`approver_required`, `mirror_revision_conflict`, `request_conflict`)이 실제로는 **사용자 본인 행동**이라 상태명과 안내가 어긋난다. 4번째 상태 추가는 후속 얼라인에서 다룬다.

## 4. 원칙 3 — 단방향 의존과 공통 인터페이스

### 4-1. 의존 방향 (하드 규칙)

```
API → 애플리케이션 서비스 → 도메인      허용
도메인 → 상위 계층                      금지
도메인 → 도메인                         허용
도메인 → 프레임워크 / I/O / 설정        금지
API → 영속화 (계층 건너뜀)              금지
```

**"애플리케이션 서비스에 의존해서 작업 전체가 중단되면 안 된다"** — 도메인이 서비스에 의존하면 서비스의 외부 I/O 실패가 도메인 판정까지 끌고 내려간다. 도메인 판정은 입력만 있으면 항상 가능해야 한다.

구체적 금지:
- 도메인 함수가 DB 핸들·HTTP 클라이언트·`process.env`·Spring 컨텍스트를 받지 않는다
- 도메인 함수는 `async`일 이유가 없다 (I/O가 없으므로)
- 설정값은 **호출자가 계산해 인자로 넘긴다** (`cashflowApplyLeaseMs(env)` → `readCashflowApplyLeaseState(doc, {leaseMs})` 패턴)

### 4-2. 현재 상태 (측정)

| 항목 | 현재 | 목표 |
|---|---|---|
| `domain` → 상위 import | **0** ✅ | 0 유지 |
| `service` → `storage` import | 1 | 허용 (조정 계층의 정당한 의존) |
| **`api` → `storage` import** | **1** ❌ | **0** |
| BFF 계층 구조 | **없음** | 도메인 모듈 분리 |

**`WeeklyExpenseController.java:26`이 `WeeklyExpensePersistence`를 직접 import하고 `persistence.` 을 3회 호출한다.** API가 영속화를 건너뛰어 호출하는 위반이다. 서비스 계층을 거쳐야 한다.

대조: `WeeklyExpenseCommandService`는 `persistence.`를 96회 호출한다 — 이것이 정상 위치다.

**중요:** 이 3회 중 하나가 `readCashflowSource`(`:304`)이고 SPEC-19가 조사 중인 대시보드 읽기 경로다. **계층 위반과 성능 문제가 같은 지점**이다.

### 4-3. 공통 인터페이스

> 외부는 서비스 계층이 유지하는 **공통 인터페이스**로 연결되고, **식별 가능한 동작의 API가 서로 일치**해야 한다.

현재 위반 — 같은 동작이 계층마다 다른 이름:

| 동작 | 프론트 | BFF | JVM |
|---|---|---|---|
| 반영 진행 상태 조회 | `apply-status` | `readCashflowSheetApplyStatus` | `sheet-lab/operations` |
| 결산 기한 | (표시만) | `cashflowMonthCloseDeadline` | `closeDeadline` |
| 주차 라벨 | `getYearFinanceWeeks` | 동일 모듈 | `financeWeekDeadline` (별도 구현) |

요구사항:
1. **하나의 동작에는 하나의 이름.** 계층을 넘어도 동일 용어
2. 같은 동작의 **입력·출력 필드명·오류 표현이 일치**한다
3. 외부는 **서비스 계층 인터페이스만** 본다. 도메인 타입이 외부로 새지 않는다
4. 인터페이스 정의는 **한 곳**에서 하고 나머지가 따른다

## 5. 상한 — SPEC-05가 우선한다

계층 분리는 **트랜잭션 경계를 넘지 않는다.**

- `WeeklyExpensePersistence`를 여러 Port로 쪼개지 마라
- 감사·멱등 기록을 본 트랜잭션 밖으로 빼지 마라
- 쓰기 경로를 여러 repository로 분산하지 마라
- **나누지 말고 뽑아내라** — 판정 로직을 도메인 순수 함수로 추출하면 원자성은 유지되고 계층 분리의 실질을 얻는다

분할 제안 시 SPEC-05 §3의 5단계 판단 절차를 먼저 답한다.

## 7. 진행 순서

```
[완료] SPEC-11 락 임대 · SPEC-14 오류 가이드
[진행] SPEC-01 작업중단 0 · SPEC-13-A/B 정책 SSOT · SPEC-17 승인 게이트 · SPEC-18-B 승인 마감
[조사] SPEC-19 대시보드 읽기 범위 · SPEC-16 revision 계약
[대기] API→storage 위반 제거 (SPEC-19 결과와 함께)
[보류] SPEC-15 소유권 이관 (SPEC-05 제약 반영 필요)
```

**API→storage 위반 제거를 단독으로 하지 않는다.** SPEC-19가 그 지점의 읽기 범위를 조사 중이므로, 계층 정리와 성능 개선을 **한 번에** 한다. 같은 파일을 두 번 건드리지 않기 위해서다.
