## 1. 문제

### 1-1. 한 라이프사이클을 두 언어가 반씩 소유한다

| 단계 | 소유자 |
|---|---|
| 결산 요청 생성 / 샤드 저장 | **BFF** (`jvm-weekly-api.mjs:3293, 3295`) |
| 조직장 지정 | **BFF** (`:3392` 라우트, `:3834, 3872` 트랜잭션) |
| 승인 / 거절 / UNCERTAIN 전이 | **BFF** (`:4015, 4066, 4133, 4188, 4220, 4249, 4325`) |
| 근거 해시 대조 | **JVM** (`…Persistence.java:2869, 3108`) |
| `monthly_closes` 최종 기록 | **JVM** (`:2800`) |

BFF가 Firestore에 직접 쓴 문서를 JVM이 다시 읽어 해시로 검증한다. 두 계층이 서로를 신뢰하지 않아 생긴 방어 코드가 그대로 지연시간과 오류 표면이다.

### 1-2. 상호 차단 고리

```
BFF 소유 락(cashflow_sheet_publications) ──검증──► JVM이 결산 거부
JVM 소유 결산(monthly_closes)            ──검증──► BFF가 반영 거부
```

2026-08-06 사고가 이 고리였다. SPEC-11(머지됨, PR #470)이 시간으로 끊었지만 **구조는 남아 있다.**

### 1-3. 왜 JVM으로 모으는가

`docs/architecture/2026-07-27-jvm-bff-channel-audit.md`의 결론을 따른다:

> 재무 불변식을 실제로 검증하는 코드가 JVM에 있다. 실제 Firestore 트랜잭션과 MockMvc 기반 테스트 약 40개가 원자성, 스냅샷 불변성, 멱등성, 결산 기한, 카운터 오버플로를 검증한다. 반면 프론트엔드 `CashflowProjectSheet.shell.test.ts`는 288개 단언이 **전부 소스 코드 문자열 검사**(`expect(source).toContain(...)`)다. `@testing-library`를 쓰는 파일은 저장소에 0개다.

즉 보증이 가장 잘 지켜지는 쪽으로 모은다. 반대 방향(BFF로 모으기)은 그 40개 보증을 잃는다.

## 2. 정량 목표

| 축 | 현재 | 목표 | 회귀 예산 |
|---|---|---|---|
| `cashflow_*` 컬렉션에 쓰는 계층 수 | 2 (BFF+JVM) | **1 (JVM)** | 1 |
| 월 결산 상태 전이 구현 위치 | 2 | **1** | 1 |
| BFF의 월결산 Firestore 트랜잭션 수 | 11 | **0** | 0 |
| `jvm-weekly-api.mjs` 줄 수 | 4,255 | **≤ 2,500** | ≤ 3,000 |
| **응답시간** p95 (월결산 조회) | SPEC-12 이후 기준선 | **회귀 없음** | +10% 이내 |
| **참조 횟수** | SPEC-12 이후 기준선 | **감소 또는 동일** | 증가 금지 |
| 409 오류 코드 종류 (`cashflow_month_close_*`) | 30+ | **≤ 15** | ≤ 20 |

마지막 항목이 중요하다. 30여 종의 409는 계층 분할을 봉합하는 비용이었다. 소유권이 하나면 상당수가 불필요해진다. **다만 사용자에게 필요한 구분까지 줄이면 안 된다** — 5-4 참조.

## 3. 단계 (contractVersion 게이트로 점진 전환)

JVM에 `CASHFLOW_MONTH_CLOSE_CONTRACT_VERSION`이 이미 있다. 이를 전환 게이트로 쓴다.

### PR-A: JVM에 쓰기 엔드포인트 신설 (동작 변경 없음)
- 요청 생성 / 조직장 지정 / 승인 / 거절을 JVM 엔드포인트로 추가
- **BFF는 아직 호출하지 않는다.** JVM 테스트로만 검증
- 기존 BFF 경로는 그대로 동작

### PR-B: BFF를 프록시로 전환 (게이트 on/off)
- env 플래그로 신·구 경로 선택
- 플래그 off = 기존 동작 (즉시 롤백 가능)
- 두 경로가 **같은 결과**를 내는지 대조 테스트

### PR-C: 구 경로 삭제
- 플래그 제거, BFF Firestore 트랜잭션 11개 삭제
- `jvm-weekly-api.mjs`를 도메인별로 분해 (SPEC-00 D절 5: 400줄 규칙)

**PR-C 없이 끝내지 않는다.** 병행 유지는 SPEC-00 H절 위반이며, 감사 문서가 기록한 실패 패턴(되돌리기가 히스토리에 안 남음)의 원인이다.

## 4. 요구사항

- 전환 후 **BFF는 `cashflow_*` 컬렉션에 쓰지 않는다.** 읽기도 최소화하고, 판정은 하지 않는다
- BFF에 남는 책임: 인증·테넌트 검증·RBAC·JVM 오류코드 → 한국어 문구 매핑(SPEC-14 산출물 재사용)·응답 셰이핑
- JVM 엔드포인트는 **멱등**해야 한다 (같은 요청 키 2회 = 1회 효과)
- 상태 전이는 단일 Firestore 트랜잭션 안에서 끝난다 (BFF·JVM 걸침 금지)

## 5. 성공 조건

### 5-1. 소유권 (핵심)

1. **소스 스캔**: `server/bff/**`에 `cashflow_month_close_requests` / `monthly_closes` / `cashflow_cumulative_close_heads` 쓰기(`.set(`/`.update(`)가 **0건**
2. `server/bff/routes/jvm-weekly-api.mjs` ≤ 2,500줄
3. BFF에 월 결산 상태 전이 로직 부재 (승인/거절/UNCERTAIN 판정이 JVM 응답 전달로만 이뤄짐)

### 5-2. 동등성 (PR-B에서 반드시)

4. 게이트 on/off 두 경로가 **동일 입력에 동일 Firestore 최종 상태**를 만든다 — 요청 생성·승인·거절 각각
5. 동일 오류 상황에서 동일 `code`를 반환 (사용자 경험 회귀 방지)
6. 기존 저장 문서(구 경로가 만든 것)를 신 경로가 **읽고 이어서 처리**할 수 있다 (마이그레이션 없이)

### 5-3. 멱등·동시성 (SPEC-00 G절 7·8)

7. 같은 요청 키로 요청 생성 2회 → 문서 1개, 두 응답 동일
8. 같은 요청에 승인 2회 → 1회 효과, 두 번째는 replay 응답
9. **동시 승인**: 서로 다른 두 승인자가 같은 요청을 동시에 승인 → 하나만 성공, 다른 하나는 명확한 충돌 오류
10. **동시 승인+거절** → 하나만 반영, 최종 상태가 모순 없음
11. 요청 생성 중 조직장이 변경됨 → `cashflow_month_close_approver_stale` 유지 (기존 보호 동작)
12. 승인 트랜잭션 중 JVM 재시작 시뮬레이션 → 부분 상태가 남지 않음 (원자성)

### 5-4. 오류 코드 정리 — 줄이되 잃지 않는다 (회귀 방지 쌍)

13. **유지 존재 확인**: 아래 구분은 반드시 살아 있다 (사용자 행동이 달라지므로)
    - 조직장 미지정 / 본인 승인 불가 / 이미 요청 존재 / 근거 변조 / 기한 초과
14. **제거 부재 확인**: 계층 분할 때문에만 존재하던 코드가 사라졌다 (예: BFF↔JVM 근거 해시 대조 실패 계열). 제거 목록을 PR 본문에 열거하고 그 목록을 테스트로 고정
15. 최종 `cashflow_month_close_*` 코드 종류 ≤ 15

### 5-5. 최악 조건 (SPEC-00 E절)

16. 9년 108개월 누적 결산 요청 → 응답시간이 SPEC-12 기준선 +10% 이내
17. 108개월 근거 샤드 무결성 검증이 단일 요청에서 완료 (타임아웃 없음)
18. 동시 사용자 10명이 같은 프로젝트 결산 상태 조회 → 오류 0, 상태 일관

### 5-6. 오염·경계 (SPEC-00 G절 2~5)

19. `yearMonth`가 `null`/`''`/`"2026-13"`/10만 자 → 명확한 400, 상태 변경 없음
20. `requestId`가 `__proto__`/`constructor` → 조회 폴백, 오염 없음
21. 승인 사유가 10만 자 → 저장 상한 적용 또는 거부, 문서 크기 한계(1MiB) 초과 없음
22. 존재하지 않는 `requestId` 승인 → 404, 다른 문서 변경 없음
