## A. 왜 이 규격이 있는가

`docs/architecture/2026-07-27-jvm-bff-channel-audit.md`가 기록한 것: 14일간 캐시플로 영역에 61커밋, 그중 46%가 `fix`. 만들었다가 몇 시간 만에 삭제된 서브시스템이 셋. **되돌리기를 한 번도 `git revert`로 하지 않아, 실패한 접근이 히스토리에 남지 않았다.**

원인은 실력이 아니라 구조다. 한 파일이 너무 많은 것을 들고 있어서, 한 곳을 고치면 다른 곳이 조용히 깨진다. 이 규격은 그 재발을 막는다.

## C. SSOT — 사실 하나당 주인 하나

전 스펙 공통 원칙. 어떤 사실(fact)이든 **정의하는 곳 1곳, 판정하는 곳 1곳**이어야 한다. 나머지는 읽기만 한다.

| 사실 | SSOT 위치 (목표) | 나머지 계층 |
|---|---|---|
| 캐시플로 라인 16종·별칭 | `policies/cashflow-policy.json` | 읽기만 |
| 재무주차 달력 (`26-8-1`) | 공유 모듈 1곳 | 읽기만 |
| 160셀 / 주차 5 상수 | policy JSON | 파생만 |
| 월 결산 기한 (익월 10일) | JVM | 응답 필드를 표시만 |
| 시트 반영 락 상태 | `cashflow-apply-lease.mjs` 판정 | 호출만 |
| 오류 → 사용자 문구 | `api-error-messages.ts` | 호출만 |

**금지:** 같은 규칙을 두 언어로 각각 구현하는 것. 불가피하면(런타임이 달라서) **한쪽을 생성물로 만든다**(codegen). 손으로 두 번 쓰지 않는다.

## D. 최소 권한 — 모듈이 들고 갈 수 있는 것

새로 만들거나 손대는 모듈은 다음을 지킨다.

1. **주입받은 것만 쓴다.** 모듈 내부에서 `process.env`를 직접 읽지 않는다. 설정은 인자로 받는다 (기존 `cashflow-apply-lease.mjs`의 `cashflowApplyLeaseMs(env)` 패턴을 따른다)
2. **I/O와 판정을 섞지 않는다.** 순수 판정 함수는 별도 파일로 분리하고 단위 테스트를 붙인다. DB 핸들을 받는 함수는 판정 로직을 갖지 않는다
3. **필요한 필드만 읽는다.** 문서 전체를 로드해 2개 필드만 쓰는 코드는 금지 (SPEC-12 참조)
4. **쓰기 권한은 소유자만.** 다른 계층이 소유한 컬렉션에 쓰지 않는다
5. **한 파일 400줄을 넘기면 분리한다.** 기존 파일을 전부 쪼개라는 뜻이 아니라, **이번 변경으로 추가되는 코드**는 새 파일로 간다

## E. 정량 목표 규격 — 모든 스펙이 아래 4개를 명시한다

각 스펙은 다음을 **숫자로** 제시하고, 검증 방법을 함께 적는다.

| 축 | 의미 |
|---|---|
| **응답시간** | p50 / p95, 콜드·웜 구분 |
| **참조 횟수 (최악)** | 요청 1건이 읽는 문서 수 — **최악 조건(계약기간 최대·다년도·이력 누적)에서** |
| **트래픽** | 응답 바이트, 계층 간 왕복 횟수 |
| **회귀 예산** | 이 값을 넘으면 실패로 간주하는 상한 |

**최악 조건 정의 (공통):**
- 계약기간 9년 (2024–2032) — 실제 `cashflow_sheet_year_totals`에 존재하는 범위
- `cashflow_weeks` = 9년 × 12월 × 5주 = **540 문서/프로젝트**
- `monthly_closes` = 9년 × 12월 = **108 문서/프로젝트**
- 동시 사용자 10명이 같은 프로젝트 대시보드를 조회

## F. 측정 방법 (공통)

계측은 이미 들어가 있다. **새로 만들지 말고 이것을 쓴다.**

- `server/bff/cashflow-performance.mjs` — `createCashflowPerformanceTrace`
- 프로덕션에서 이미 동작 중이다: `defaultLogger`는 `NODE_ENV==='test'`일 때만 skip하고, 그 외에는 stdout에 JSON을 낸다
- 필터: `message="cashflow.performance"`, 필드 `operation` / `phase` / `durationMs` / `totalMs` / `attempt`

**문서 읽기 횟수**는 테스트에서 세는 것을 원칙으로 한다. 테스트 하네스의 fake db가 이미 쿼리를 기록한다 (`createDb`의 `queries` 배열, `__getDocumentsByPrefix`). 실측 로그가 아니라 **테스트로 상한을 고정**해야 회귀를 막을 수 있다.

## G. 테스트 강도 규격 (전 스펙 공통 최소선)

행복 경로만 검증하는 테스트는 반려한다. 각 스펙은 아래를 **전부** 포함한다.

1. **경계값** — 0, 1, 최대, 최대+1
2. **빈/누락 입력** — `null` / `undefined` / `''` / `{}` / `[]`
3. **타입 오염** — 문자열 자리에 숫자·객체·배열
4. **프로토타입 오염** — 키가 `__proto__` / `constructor` / `toString`
5. **초장문 입력** — 10만 자 문자열
6. **최악 규모** — E절의 최악 조건 데이터셋으로 1회 이상
7. **동시성** — 같은 자원에 동시 요청 2건 이상 (해당되는 경우)
8. **멱등성** — 같은 요청 2회가 같은 결과 (변경 API인 경우)
9. **회귀 방지 쌍** — 제거 대상의 **부재**와 유지 대상의 **존재**를 같은 스위트에서 검증
10. **성능 상한** — 참조 횟수·왕복 횟수를 숫자로 단언

> 9번은 과거 실패에서 나온 규칙이다. 업로드 UI 제거 요청이 인접한 수기 편집 기능 삭제로 번진 적이 있다. **무엇을 지워야 하는지만 적지 말고, 무엇이 남아야 하는지도 단언한다.**

## H. 커밋·PR 규격

- 브랜치 prefix: `feat/` `fix/` `docs/` `chore/` `refactor/` `test/` 중 하나
- Conventional Commits
- **접근을 바꿨으면 이전 코드를 같은 PR에서 지운다.** 병행 유지 금지 (게이트로 감싸는 경우는 예외이며, 제거 시점을 PR 본문에 적는다)
- PR 본문에 반드시 포함: 정량 목표 대비 실측치, 회귀 예산 초과 여부, **하지 않은 것**
- 실패한 접근은 PR 본문에 남긴다 (히스토리에 신호를 남기기 위해)

## I. 공통 금지 사항

- `npm test`를 파이프(`| tail`)로 실행해 exit code를 가리는 것
- `npm run build` 통과를 타입 안전으로 간주하는 것 (`vite build`는 타입 검사를 하지 않는다. `npx tsc --noEmit`은 기존 오류가 많으므로 **변경 파일 기준 diff**로 확인한다)
- 테스트를 기대값에 맞춰 고치기 전에 **구현이 맞는지 먼저 확인**하지 않는 것
- 이 스펙에 없는 파일 수정
