## 0. 왜 조사부터인가

재무주차 달력이 두 벌이고 **타임존이 다르다**:

| 구현 | 위치 | 기준 |
|---|---|---|
| FE/BFF 공유 | `src/app/platform/cashflow-week-core.mjs` | **UTC** (`Date.UTC`, `getUTCDay`) |
| JVM | `…Persistence.java` `financeWeekDeadline` / `weeklyComplianceStatus` | **Asia/Seoul** |

KST = UTC+9. **월 경계·주 경계에서 두 계층이 다른 주차 판정을 낼 수 있는 구조**다.

이것이 7개 이중 계약 중 유일하게 **저장된 데이터가 틀어질 수 있는** 항목이다:
- 주차 라벨(`26-8-1`)이 `cashflow_weeks` 문서 ID·필드에 저장됨
- `ON_TIME`/`COMPLETED_LATE` 준수 판정이 저장됨
- 미준수 누적이 이 판정으로 계산됨

**통일을 잘못하면 과거 준수 이력이 소급 변경된다** (SPEC-04 위반). 그래서 구현 전에 영향 범위를 숫자로 확정한다.

## 1. 조사 질문 (전부 코드/데이터 근거로)

### Q1. 두 구현이 실제로 다른 답을 내는 입력의 전수
`cashflow-week-core.mjs`의 주차 계산과 JVM의 주차 계산을 **동일 입력으로 대조**하라.

- 월 시작 요일 7가지 × 월 경계 케이스를 표로: 각 케이스에서 라벨·마감이 갈리는가
- **핵심 가설 검증:** UTC 기준 목요일 자정과 KST 기준 목요일 자정은 9시간 차이다. 이 창(목 15:00 UTC ~ 금 00:00 KST)에 완료된 정산의 `ON_TIME` 판정이 두 구현에서 갈리는가
- 라벨 자체(`26-8-1`)가 갈리는 날짜가 존재하는가, 아니면 마감 시각만 갈리는가 — **이 구분이 위험도를 결정한다**

### Q2. 각 구현이 실제로 쓰이는 지점 전수
| 구현 | 소비처를 전부 나열 (파일:줄) |
|---|---|
| `cashflow-week-core.mjs` | FE 표시? BFF 검증? 저장 라벨 생성? |
| JVM 주차 계산 | 마감 판정? 준수 기록? 저장 라벨 생성? |

**"어느 쪽이 저장 라벨을 만드는가"가 핵심이다.** 라벨 생성자가 한쪽뿐이면 라벨 불일치는 이론적 위험이고, 양쪽 다면 실재 위험이다.

### Q3. 저장된 데이터의 실태
- `cashflow_weeks` 문서 ID 형식과 라벨 필드 — 어느 계층이 썼는가 (코드 경로로 추적)
- `cashflow_weekly_update_completions`의 준수 판정 — JVM만 쓰는가
- 판정이 갈릴 수 있는 창(Q1)에 실제로 저장된 완료 기록이 존재할 가능성 — 완료 시각 필드로 판단 가능한가

### Q4. 업무 기준은 무엇인가
확정된 업무 규칙(SPEC-04 §1-B): 주간 마감 = 목요일 자정 = **금요일 0시 KST**. 즉 **업무 정의는 KST다.**

- UTC 구현(`cashflow-week-core.mjs`)이 업무 정의와 어긋나는 입력 구간을 명시하라
- FE가 UTC 주차로 표시 중이라면, 사용자가 보는 주차와 JVM이 판정하는 주차가 **이미 어긋나는 화면**이 존재하는가

### Q5. 통일 방향별 영향
| 방향 | 조사할 것 |
|---|---|
| (a) 전부 KST로 | UTC로 저장된 라벨·판정 중 바뀌는 것의 범위. FE 표시 변화 |
| (b) 전부 UTC로 | 업무 정의(KST)와의 괴리. JVM 판정 변경 범위 — **과거 준수 이력 소급 위험** |
| (c) 현상 유지 + 문서화 | 갈림 창의 실제 발생 빈도. 허용 가능한가 |

각 방향에 대해 SPEC-04 T-4(월 경계 케이스 차이 열거)를 수행하라.

## 2. 산출물 요구사항

1. Q1~Q5의 답. 모든 항목 `파일:줄` 근거, 미확인은 명시
2. **갈림 창의 정확한 정의** — 어떤 시각 범위의 어떤 이벤트가 다른 판정을 받는가
3. 방향별 정량 영향: 판정이 바뀌는 저장 레코드의 추정 범위 (0건이면 0건이라고)
4. **권장안과 근거.** 소급 변경이 0건인 경로가 존재하는가
5. Freeze Unit 분해 (구현 시)
6. 되돌릴 수 없는 변경 후보
