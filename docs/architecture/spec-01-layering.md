# SPEC-01 — 계층 아키텍처 (설계 축 상향)

**작성:** 2026-08-07 · **대상:** codex 독립 세션 · **위상:** SPEC-00과 함께 **모든 스펙의 상위 규범**
**이 문서가 SPEC-12/13/14/15의 "무엇을 어디에 둘 것인가"를 결정한다.**

---

## 0. 왜 축을 올리는가

지금까지의 논의는 **JVM이냐 BFF냐**로 진행됐다. 그것은 배포 단위이지 설계 축이 아니다. "월 결산을 JVM으로 모은다"는 결정은 **어느 프로세스에 코드가 사는가**를 정할 뿐, **비즈니스 규칙과 조정 로직이 섞이는 문제**를 풀지 못한다.

축을 바꾼다.

```
[잘못된 축]  BFF(Node) ←──→ JVM(Java)          ← 배포 단위. 인프라 관심사
[올바른 축]  애플리케이션 서비스 ──→ 도메인      ← 책임. 설계 관심사
```

배포 단위는 도메인의 **구현 세부사항**이다. 같은 도메인 규칙이 Node에 있든 Java에 있든, 그것이 도메인 규칙이라는 사실은 변하지 않는다.

## 1. 현재 상태 (측정)

### 1-1. 좋은 소식 — JVM의 의존 방향은 이미 단방향이다

```
domain 패키지 → api/service/storage/repository 로의 import: 0건
```

도메인 클래스가 상위 계층을 참조하지 않는다. **이 불변식은 이미 지켜지고 있으므로 깨뜨리지 않는다.**

### 1-2. 나쁜 소식 — 규칙이 도메인 밖에 산다

| 계층 | 줄 수 | 상태 |
|---|---|---|
| `domain` | 2,769 | **빈혈(anemic)** — 규칙이 여기 없다 |
| `storage` | **6,891** | 영속화 + **비즈니스 규칙** 혼재 |
| `service` | 4,621 | 조정 + 규칙 혼재 |
| `api` | 4,821 | DTO + 컨트롤러 |
| `repository` | 185 | — |

`storage/FirestoreInheritedWeeklyExpensePersistence.java`가 들고 있는 **도메인 규칙**:

| 규칙 | 위치 | 본래 소속 |
|---|---|---|
| 월 결산 기한 = 익월 10일 | `:580`, `:1111` (`atDay(10)`) | 도메인 |
| 재무주차 달력·마감 | `financeWeekDeadline` | 도메인 |
| 주간 준수 판정 | `weeklyComplianceStatus` | 도메인 |
| 결산 상태 정규화 | `canonicalMonthStatus` | 도메인 |
| `yearMonth` 형식 규칙 | `requireYearMonth` (7곳+) | 도메인 |

**영속화 클래스가 비즈니스를 판정한다.** 그래서 규칙을 바꾸려면 Firestore 코드를 열어야 하고, 규칙만 테스트할 수 없다.

### 1-3. 더 나쁜 소식 — BFF에는 계층이 아예 없다

`server/bff/routes/*.mjs`가 인증·조정·도메인 판정·영속화를 한 파일에 담는다. `jvm-weekly-api.mjs` 4,255줄, `cashflow-sheet-lab.mjs` 4,170줄에 계층 경계가 없다.

예외: `server/bff/cashflow-apply-lease.mjs`(53줄). 순수 판정만 담고 I/O를 갖지 않는다. **이것이 목표 형태다.**

**언어와 배포 단위는 이 그림에 나타나지 않는다.** Node의 `cashflow-apply-lease.mjs`와 Java의 `CashflowFormulaValidator`는 **같은 계층**이다.

## 3. 원칙 1 — 영향 분리와 **작업 중단 로직 0**

### 3-1. 규칙

> **요청받지 않은 관심사 때문에 작업이 중단되어서는 안 된다.**

지금 이 규칙을 어기는 지점들:

| 중단 지점 | 위치 | 무엇이 무엇을 막는가 |
|---|---|---|
| 시트 반영 락 → 월 결산 **조회** 차단 | `jvm-weekly-api.mjs` `assertCashflowSheetPublicationReady` | 쓰기 관심사가 **읽기**를 막는다 |
| 락 → 월 결산 차단 (JVM) | `…Persistence.java:3596` | 동일 |
| fingerprint 전후 불일치 → 전체 재실행 후 409 | `jvm-weekly-api.mjs` 월결산 조회 루프 | 낙관적 검사가 응답 자체를 없앤다 |
| JVM 응답 필드 검증 실패 → 502 | 같은 라우트 6개 코드 | 일부 필드 문제가 **전체 대시보드**를 없앤다 |

2026-08-06 사고의 본질이 이것이다. **시트 반영이라는 쓰기 작업의 상태가 월 결산 조회라는 읽기 작업을 막았다.** SPEC-11(PR #470)이 시간으로 끊었지만 결합 자체는 남아 있다.

### 3-2. 요구사항

1. **읽기 경로는 쓰기 상태 때문에 중단되지 않는다.** 진행 중인 반영이 있으면 그 사실을 **데이터로 실어 보낸다**(예: `pendingApply: {startedAt, expiresAt}`). 응답을 없애지 않는다
2. **부분 실패는 부분으로 남는다.** 대시보드의 한 섹션 데이터가 없으면 그 섹션만 비우고 사유를 표시한다. 전체를 502로 만들지 않는다
3. **도메인 판정 실패와 인프라 실패를 구분한다.** 도메인이 "이 상태에서는 결산할 수 없다"고 말하는 것은 정상 응답이다(422/409가 아니라 **결과 객체**). 인프라가 죽은 것만 오류다
4. **낙관적 검사는 재시도를 유발하되 응답을 없애지 않는다.** fingerprint 불일치는 "이 값은 방금 바뀌었을 수 있다"는 메타데이터로 전달한다

### 3-3. 측정

| 축 | 현재 | 목표 |
|---|---|---|
| 읽기 경로가 쓰기 상태로 중단되는 지점 | 2 (BFF, JVM) | **0** |
| 부분 데이터 결손이 전체 실패로 번지는 지점 | 6 (502 코드) | **0** |
| 대시보드 조회 성공률 (반영 진행 중) | 0% | **100%** (부분 표시) |

## 4. 원칙 2 — 사용자에게는 **설명 가능한 가이드**

### 4-1. 규칙

> 사용자가 보는 것은 **다음에 무엇을 하면 되는가**여야 한다. 기술 식별자가 아니다.

현재는 두 극단을 오간다:
- `Internal server error` — 정보 0
- `cashflow_month_close_request_evidence_tampered` — 사용자가 해석 불가

### 4-2. 요구사항

오류 표현은 **3층**으로 나눈다.

| 층 | 내용 | 대상 |
|---|---|---|
| **1. 가이드** (항상 표시) | 무엇이 일어났고 **무엇을 하면 되는지**. 운영 언어 | 사용자 |
| **2. 상태** (항상 표시) | 재시도로 풀리는가 / 기다려야 하는가 / 담당자가 필요한가 | 사용자 |
| **3. 식별자** (보조 표시) | `code`, `requestId` | 지원·개발 |

**1층에 기술 용어·내부 필드명·오류 코드 문자열을 넣지 않는다.**

예시 (`cashflow_sheet_apply_in_progress`):
- ❌ "cashflow_sheet_apply_in_progress"
- ❌ "시트 반영 중입니다" (무엇을 하라는 건지 없음)
- ✅ "시트 값을 반영하는 중이에요. 약 3분 뒤 자동으로 풀립니다. 그때 다시 눌러 주세요." + 상태: 기다림 + 코드: `cashflow_sheet_apply_in_progress`

### 4-3. 가이드는 도메인이 만들고, 문구는 서비스가 만든다

**중요한 분리다.**

- **도메인**: "이 요청은 지금 수행할 수 없다. 사유는 X이고, 해소 조건은 Y이며, 예상 해소 시각은 Z다" — **구조화된 결과 객체**를 돌려준다. 문자열이 아니다
- **애플리케이션 서비스**: 그 구조를 사용자 언어로 번역한다

도메인이 한국어 문구를 들고 있으면 규칙과 표현이 붙어 재사용이 막힌다. 반대로 서비스가 사유를 추론하면 규칙이 두 곳에 생긴다.

### 4-4. 측정

| 축 | 현재 | 목표 |
|---|---|---|
| 사용자가 다음 행동을 알 수 있는 오류 | 0% | **100%** |
| 1층 문구에 기술 식별자 포함 | — | **0건** (테스트로 강제) |
| 도메인이 표현 문자열을 보유 | 다수 | **0** |

## 5. 원칙 3 — 단방향 의존과 공통 인터페이스

### 5-1. 의존 방향 (하드 규칙)

```
애플리케이션 서비스 ──→ 도메인          허용
도메인 ──→ 애플리케이션 서비스           금지
도메인 ──→ 도메인                       허용
도메인 ──→ 프레임워크/IO/설정            금지
```

**"애플리케이션 서비스 클래스에 의존해서 작업 전체가 중단되면 안 된다"** — 도메인이 서비스에 의존하면, 서비스의 외부 I/O 실패가 도메인 판정까지 끌고 내려간다. 도메인 판정은 입력만 있으면 항상 가능해야 한다.

구체적 금지:
- 도메인 함수가 DB 핸들·HTTP 클라이언트·`process.env`·Spring 컨텍스트를 받지 않는다
- 도메인 함수는 `async`일 이유가 없다 (I/O가 없으므로)
- 설정값은 **호출자가 계산해서 인자로 넘긴다** (`cashflowApplyLeaseMs(env)` → `readCashflowApplyLeaseState(doc, {leaseMs})` 패턴)

### 5-2. 공통 인터페이스

> 외부 애플리케이션은 서비스 계층이 유지하는 **공통 인터페이스**를 통해 연결되고, **식별 가능한 동작의 API가 서로 일치**해야 한다.

현재 위반: 같은 동작이 계층마다 다른 이름·형태를 갖는다.

| 동작 | 프론트 | BFF | JVM |
|---|---|---|---|
| 반영 진행 상태 조회 | `apply-status` | `readCashflowSheetApplyStatus` | `sheet-lab/operations` |
| 결산 기한 | 자체 계산 없음(표시) | `cashflowMonthCloseDeadline` | `closeDeadline` |
| 주차 라벨 | `getYearFinanceWeeks` | 동일 모듈 | `financeWeekDeadline` (별도 구현) |

요구사항:
1. **하나의 동작에는 하나의 이름.** 계층을 넘어도 동일 용어를 쓴다
2. **같은 동작의 API 형태가 일치한다.** 입력 필드명·출력 필드명·오류 표현이 계층마다 달라지지 않는다
3. 외부(브라우저·배치)는 **서비스 계층 인터페이스만** 본다. 도메인 타입이 외부로 새지 않는다
4. 인터페이스 변경은 **한 곳**에서 정의하고 나머지가 따른다 (SPEC-13의 SSOT 원칙과 같은 메커니즘)

### 5-3. 측정

| 축 | 현재 | 목표 | 검증 |
|---|---|---|---|
| 도메인 → 상위 계층 import | 0 (JVM) / 해당없음 (BFF에 계층 없음) | **0 유지** | 소스 스캔 테스트 |
| 도메인 모듈의 I/O 의존 | 다수 (storage에 규칙 존재) | **0** | 도메인 파일에 DB/HTTP import 부재 |
| 동작 이름 불일치 | 3+ | **0** | 용어집 대조 테스트 |
| 도메인 타입의 외부 노출 | 미측정 | **0** | API 응답 스키마 검사 |

## 6. 각 스펙에 미치는 영향 (필독)

| 스펙 | 계층 관점 재해석 |
|---|---|
| **SPEC-12** (읽기 증폭) | 범위 계산은 **도메인**(`CashflowQueryScope`), 질의 실행은 **서비스**. 이미 그렇게 지시되어 있다. 추가: `requireYearMonth` 등 형식 규칙을 storage에서 도메인으로 **이동** |
| **SPEC-13** (정책 SSOT) | policy JSON은 **도메인 정의**다. 계층 이동(`src/app` → 공유 위치)은 이 계층화의 일부다. 추가: 기한·주차 계산을 storage에서 도메인으로 이동 |
| **SPEC-14** (오류 노출) | §4의 3층 구조로 **재작성**. 단순 code 노출이 아니라 **가이드 우선**. 도메인은 구조화된 사유를, 서비스가 문구를 |
| **SPEC-15** (소유권) | "JVM으로 모은다"를 **"도메인 규칙은 도메인 계층으로, 조정은 서비스 계층으로"**로 재해석. 배포 단위는 결과이지 목표가 아니다 |

## 7. 공통 성공 조건 (모든 스펙에 추가)

각 스펙의 성공 조건에 아래를 **추가**한다.

1. **의존 방향 테스트**: 새로 만든/이동한 도메인 모듈이 I/O·프레임워크·설정을 import하지 않는다 (소스 스캔)
2. **도메인 순수성 테스트**: 도메인 함수가 인자만으로 결정적 결과를 낸다 (같은 입력 → 같은 출력, 1,000회)
3. **중단 0 테스트**: 인접 관심사가 실패해도 요청받은 작업이 부분 결과를 돌려준다 (해당되는 경우)
4. **가이드 테스트**: 사용자 노출 문구에 기술 식별자(`/[a-z]+_[a-z_]{5,}/`)가 없다
5. **용어 일치 테스트**: 계층을 넘는 동작 이름이 용어집과 일치한다

## 8. 하지 말 것

- 계층화를 이유로 이번 스펙 범위 밖 파일을 재배치
- 도메인에 프레임워크 애노테이션 추가 (Spring `@Component` 등)
- 도메인 계층에 한국어 사용자 문구 배치
- 배포 단위(JVM/BFF)를 계층 이름으로 사용
- **한 번에 전부 옮기기** — 각 스펙 범위 내에서 해당 규칙만 이동한다
