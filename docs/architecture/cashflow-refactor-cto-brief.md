## 1-B. 조사로 교정된 사항 (2026-08-07 갱신)

초기 진단 중 **2건이 조사에서 뒤집혔다.** 코드를 읽고 추론한 것과 실행으로 확인한 것의 차이다.

| 항목 | 초기 진단 | 조사 결과 | 근거 |
|---|---|---|---|
| **#3 재무주차 타임존** | "UTC vs KST — 월 경계에서 판정이 갈릴 수 있는 구조" (높음) | **이중 계약 아님** | Node 실구현과 JVM 등가식을 **36,525일(2000~2099) 실행 대조 → 차이 0건**. `Date.UTC`는 타임존 선택이 아니라 런타임 로컬 타임존과 무관한 **날짜 산술 결정성 장치**이며 입력·출력 모두 `YYYY-MM-DD` 문자열이다. FE/BFF 코어에는 마감·준수 판정이 **없고**(`deadline`/`ON_TIME` 문자열 0건) 판정자는 JVM 한 곳뿐이다 |
| **#7 수식 검증** | "BFF 3모듈 vs JVM validator 중복" (중) | **범위 과장 + 실제 결함 1건** | 3모듈 중 `annual-total`은 읽기 모델 요약, `comparison`은 화면용 비교(JVM에 대응 없음), `sheet-template`은 외부 형식 어댑터다. **이월잔액은 중복이 아니라 JVM 단독 규칙.** 대신 금액 계약이 실제로 갈린다 |

### #7에서 발견된 실제 결함

`server/bff/cashflow-annual-total.mjs:4-7`
```js
return Number.isSafeInteger(amount) ? amount : 0;   // ← 조용히 0
```

| 입력 | BFF | JVM |
|---|---|---|
| `0.1` | **0** (무음 누락) | `must be a whole-won value` 오류 |
| `9007199254740992` | **0** (무음 누락) | 정상 계산 |

반올림 오차가 아니라 **실패 의미의 불일치**다. JVM은 `BigDecimal.longValueExact()`로 Java `long` 범위를 쓰는데 JS `Number.isSafeInteger`는 2⁵³-1에서 끊긴다. 최종 저장은 JVM 재검증이 막지만 **화면과 mirror에는 0이 노출**된다.

### 교훈

**"코드를 읽고 추론한 것"과 "실행으로 확인한 것"을 구분해야 한다.** #3은 실행 대조로 기각됐고, #7은 실행 대조로 다른 결함이 드러났다. 이후 모든 조사에 실행 증명을 의무화했다.

### 2-1. 선행지표

14일간(2026-07-13 ~ 07-27) 이 영역에 **61 커밋, 그중 46%가 `fix`**. 만들었다가 몇 시간 만에 삭제된 서브시스템이 셋(정산주차 쓰기잠금 2시간 38분, 연간합계 컬럼 19분, edit-lease 펜싱 13일에 걸쳐 해체).

## 3. 실제 발생한 손실

### 3-1. 2026-08-06 장애 — 프로젝트 전면 잠금

시트 반영 중 BFF 함수가 중단되자 락이 영구히 남아, 해당 프로젝트의 **월 결산 조회와 재반영이 모두 409로 차단**됐다. 코드에도 화면에도 해제 경로가 없어 **Firestore를 직접 수정해야만** 복구 가능한 상태였다.

주목할 점: 같은 날 21:56에 인접 수정(PR #469)이 머지됐고 **13분 뒤 사고가 났다.** 개별 수정으로는 이 문제 계열이 닫히지 않는다는 증거다.

**대응 완료** — PR #470 머지 대기 중. 고착이 무기한 → **최대 10분 자동 해제**. 관리자 강제 해제 경로 추가.

### 3-2. 진단 불가

모든 5xx가 화면에 `Internal server error` 하나로 표시된다. 결과:

| 실제 원인 | 성질 | 사용자가 보는 것 |
|---|---|---|
| 환경변수 미설정 | **영구** | Internal server error |
| 토큰 발급 실패 | 영구/일시 | Internal server error |
| 네트워크 타임아웃 | **일시** | Internal server error |

**영구 장애와 일시 장애를 구분할 수 없다.** 사용자는 풀리지 않을 오류에 새로고침을 반복하고, 지원 담당자는 서버 로그를 뒤져야 한다. 감사 문서가 이 항목을 "레버리지가 가장 크다"고 지목했다.

### 3-3. 이전 성능 개선의 실패

커밋 `7247ce2` "stabilize cashflow dashboard loading"은 BFF→JVM **HTTP 홉 하나를 제거**했으나 효과가 없었다. **지배적 비용은 홉이 아니라 Firestore 읽기 증폭**이었기 때문이다. 같은 커밋이 응답에 배열을 추가해 크기는 오히려 늘었다.

→ 이번 스펙에서 **홉 감소 접근을 명시적으로 금지**했다.

### SPEC-12 — 읽기 증폭 제거 (효과 최대)

Firestore를 SQL처럼 쓰는 코드가 원인. `whereEqualTo("projectId")`만 걸고 `yearMonth` 필터도 `limit`도 없다. **`.limit(`은 4,700줄에서 2회만 사용.**

복합 인덱스는 `firestore.indexes.json`에 **이미 선언되어 있으나 쿼리가 `yearMonth`를 쓰지 않아 사용되지 않는다.** 인덱스 배포 불필요.

## 5. 설계 방침 — 축을 올린다

지금까지 논의는 **"JVM이냐 BFF냐"**로 진행됐다. 그것은 배포 단위이지 설계 축이 아니다.

```
[기존 축]  BFF(Node) ←→ JVM(Java)        ← 인프라 관심사
[신규 축]  애플리케이션 서비스 → 도메인     ← 책임 분리
```

- **도메인**: 비즈니스 규칙. 도메인끼리만 의존. I/O·프레임워크·설정 접근 금지
- **애플리케이션 서비스**: 조정. 외부 I/O, 트랜잭션 경계, 인증, 도메인 결과 → 사용자 가이드 번역
- **외부 애플리케이션**: 서비스 계층의 공통 인터페이스로만 연결. 동일 동작은 계층을 넘어 동일한 이름·형태

**JVM 유지 결정은 그대로 둔다.** 근거는 감사 문서에 있다 — 재무 불변식(원자성·스냅샷 불변성·멱등성·기한·오버플로)을 실제로 검증하는 Firestore 트랜잭션/MockMvc 테스트 약 40개가 JVM에 있는 반면, 프론트 테스트 288개 단언은 **전부 소스 문자열 검사**이고 `@testing-library` 사용 파일은 0개다. 보증이 가장 잘 지켜지는 쪽을 지킨다.
