# SPEC-02 — 반우회 헌장 (Anti-Gaming Charter)

**작성:** 2026-08-07 · **위상:** SPEC-00/01과 함께 **모든 스펙의 상위 규범**
**적용:** 구현자(codex)의 의무이자, 검수자(MERRY)의 체크리스트다.

---

## 0. 전제

> **테스트 통과는 목적이 아니라 증거다.**

테스트가 목적이 되는 순간 가장 흔한 실패가 시작된다. 통과했지만 문제는 그대로 남고, 다음 사람은 "테스트가 있으니 검증됐다"고 믿는다. 이 문서는 그 경로를 막는다.

이 프로젝트에는 이미 그 흔적이 있다. 프론트엔드 `CashflowProjectSheet.shell.test.ts`의 **288개 단언이 전부 소스 문자열 검사**(`expect(source).toContain(...)`)이고, `@testing-library`를 쓰는 파일은 저장소에 **0개**다. 테스트 수는 많지만 동작을 검증하지 않는다.

---

## 1. 금지된 우회 패턴

아래에 해당하면 **구현을 되돌리고 다시 한다.** "통과했으니 됐다"는 근거가 아니다.

### G-1. 단언을 구현에 맞추기
구현이 실패하자 **기대값을 바꿔** 통과시키는 것.
- 판별: 테스트 diff에서 기대값이 구현 결과 쪽으로 이동했는가
- 의무: 기대값을 바꾸기 전에 **구현이 틀렸을 가능성을 먼저 조사**하고, 조사 결과를 보고에 남긴다
- 예외: 스펙 자체가 틀렸다고 판단되면 구현하지 말고 근거와 함께 보고 (SPEC-02 §3)

### G-2. 소스 문자열 검사로 동작 검증 대체
`expect(source).toContain('...')`로 "구현했다"고 주장하는 것.
- 허용: 특정 문자열의 **부재**를 강제하는 회귀 방지(금지어·제거 확인)
- 금지: 그것만으로 **동작을 검증했다고 주장**하는 것
- 의무: 동작은 실제 호출·실제 응답으로 검증한다

### G-3. 좁은 픽스처로 최악 조건 회피
`limit`이나 필터를 넣고 **3개짜리 픽스처**로 통과시키는 것. 540문서에서의 동작은 검증되지 않았다.
- 의무: SPEC-00 E절의 최악 조건(계약 9년, 540/108문서) 데이터셋으로 **최소 1회** 검증
- 의무: 참조 횟수는 **숫자로 단언**한다. "빨라졌다"가 아니라 "≤10건"

### G-4. 예외를 삼켜 통과시키기
`try/catch`로 감싸 오류를 없애고 정상 응답을 반환하는 것.
- 판별: 새로 추가된 `catch` 블록이 로그만 남기고 흘려보내는가
- 의무: 삼킨 예외는 **반드시** 호출자가 알 수 있는 형태로 남긴다 (결과 객체의 사유 필드 등)
- 주의: SPEC-01의 "작업 중단 0"은 **예외를 숨기라는 뜻이 아니다.** 부분 결과 + 사유 전달이지, 조용한 성공이 아니다

### G-5. 조용한 폴백
검증 실패 시 **기존 동작으로 되돌아가** 테스트를 통과시키는 것.
- 대표 위험: SPEC-12에서 `yearMonth`가 잘못됐을 때 무필터 전체 스캔으로 폴백 → 테스트는 통과, 성능 회귀는 조용히 부활
- 의무: 폴백은 **명시적 실패**로 대체하거나, 폴백했다는 사실을 관측 가능하게 남긴다

### G-6. 테스트 비활성화·완화
`skip` / `todo` / `only` 추가, 타임아웃 연장, 단언 삭제, 조건 완화.
- 의무: 기존 테스트를 끄거나 약화시키는 diff는 **개별 사유를 보고에 적는다**
- 판별: `it.skip` / `describe.skip` / `@Disabled` / `assumeTrue` 신규 등장

### G-7. 범위 밖 파일로 문제 밀어내기
스펙 대상 파일을 "깨끗하게" 만들려고 인접 파일에 로직을 옮기는 것.
- 의무: 스펙에 명시되지 않은 파일 수정은 금지. 필요하면 보고 후 승인

### G-8. 병행 유지로 되돌리기 회피
새 경로를 만들고 옛 경로를 남겨 두는 것. 두 경로가 갈라지면 이중 계약이 하나 더 생긴다.
- 의무: 접근을 바꿨으면 **같은 PR에서** 옛 코드를 지운다. 게이트로 감싸는 경우 **제거 시점을 PR 본문에 명시**

### G-9. 측정 없는 성능 주장
"빨라졌을 것"으로 완료 처리하는 것.
- 의무: 개선치는 **테스트가 강제하는 숫자**이거나 **실측**이어야 한다
- 전례: 커밋 `7247ce2`는 HTTP 홉을 제거했으나 효과가 없었다. 지배적 비용이 아니었기 때문이다

## 2. 근거 의무 (Evidence Requirement)

> 설계 판단에는 **출처가 있는 근거**를 붙인다. 의견은 근거가 아니다.

### 2-1. 언제 근거가 필요한가

아래 판단을 할 때는 근거를 **보고에 명시**한다:

1. 스펙이 지시하지 않은 **추상화를 새로 도입**할 때 → **YAGNI** 관점에서 정당화하라. 지금 필요한가, 아니면 나중에 필요할 것 같은가. 후자면 만들지 마라
2. 스펙이 지시하지 않은 **일반화·설정화**를 할 때 → 사용처가 **2곳 이상 실재**함을 코드로 제시하라 (Rule of Three)
3. **라이브러리·API 동작에 의존**할 때 → 공식 문서 또는 소스의 **정확한 위치**를 인용하라
   - 예: Firestore `whereIn` 상한 30 → Google Cloud Firestore 공식 문서의 해당 제한 항목
   - 예: `select()` 사용 시 누락 필드가 `null`이 되는 동작 → 문서 근거
4. **기존 코드를 지울 때** → 호출부가 없음을 **전수 검색 결과**로 제시하라
5. **성능 관련 결정** → 측정치 또는 데이터 모델 기반 산출을 제시하라

### 2-2. 근거의 형식

```
[근거] <주장>
  출처: <URL 또는 파일:줄>
  확인: <실제로 확인한 내용 한 줄>
  적용: <이 근거가 이 결정에 어떻게 연결되는가>
```

**금지:** 기억에 의존한 인용. 확인하지 않은 URL. "일반적으로 알려진" 같은 표현.

### 2-3. YAGNI 적용 기준

이 리팩토링은 **코드를 줄이는 작업**이다. 늘리는 방향의 판단에는 특히 엄격하다.

| 상황 | 판단 |
|---|---|
| 스펙이 요구한 인터페이스 | 만든다 |
| "나중에 다른 구현체가 올 수도" | **만들지 않는다** |
| 사용처 1곳뿐인 추상 계층 | **만들지 않는다** |
| 설정 가능하게 해두면 유연할 것 같음 | **만들지 않는다** (스펙이 요구한 env 게이트는 예외) |
| 사용처 2곳 이상 실재 + 규칙이 동일 | 만든다 (SSOT) |

**판단 근거를 보고에 남긴다.** "만들지 않았다"도 판단이므로 기록한다.

## 3. 스펙이 틀렸다고 판단될 때

구현하다 보면 스펙이 틀렸음을 발견할 수 있다. **실제로 이번 작업의 선행 단계에서 그런 일이 있었다** — SPEC-11(락 임대) 구현 중, 원래 설계였던 "JVM 기록으로 화해"가 오류 유발적임이 드러나 "락만 놓고 판정하지 않는" 방식으로 바뀌었다.

### 의무
1. **구현을 강행하지 마라.** 스펙에 맞추려고 우회 코드를 쓰지 마라
2. **테스트를 스펙에 맞춰 조작하지 마라**
3. 즉시 보고한다:
```
[스펙 이의] SPEC-NN §X
  스펙 주장: <무엇을 하라고 되어 있는가>
  실제 관찰: <코드/실행에서 확인한 사실 + 파일:줄>
  왜 불가능/위험한가: <구체적 실패 시나리오>
  대안: <있다면>
```

**스펙이 틀렸다는 보고는 감점이 아니다.** 틀린 스펙을 그대로 구현한 것이 감점이다.

## 4. 완료 보고에 반드시 포함할 것

```
1. 구현 요약 (무엇을 바꿨는가)
2. 게이트 결과 — 명령어와 exit code, 테스트 수/통과 수 (파이프로 가리지 말 것)
3. 정량 개선치 — 스펙의 목표 대비 실제 측정값
4. 근거 목록 (§2-2 형식) — 특히 YAGNI 판단
5. 스펙 이탈 여부 — 있으면 §3 형식으로
6. 우회 자가 점검 — G-1~G-9 각각에 대해 "해당 없음" 또는 해당 내용
7. 하지 않은 것 — 범위 밖으로 남긴 것과 그 이유
8. 실패한 접근 — 시도했다가 되돌린 것 (히스토리에 신호를 남기기 위해)
```

**8번이 비어 있는 보고는 의심 대상이다.** 한 번에 맞았다면 그것도 사실이지만, 대개는 기록하지 않은 것이다.

## 5. 검수자(MERRY) 체크리스트

구현 보고를 받으면 아래를 **코드로 직접 확인**한다. 보고를 믿지 않는다.

- [ ] 테스트 diff에서 기대값이 구현 쪽으로 이동했는가 (G-1)
- [ ] 새 테스트가 실제 동작을 검증하는가, 소스 문자열만 보는가 (G-2)
- [ ] 최악 조건 픽스처가 실재하는가, 참조 횟수가 숫자로 단언됐는가 (G-3)
- [ ] 새 `catch`가 예외를 삼키는가 (G-4)
- [ ] 검증 실패 시 조용한 폴백이 있는가 (G-5)
- [ ] `skip`/`only`/타임아웃 연장/단언 삭제가 있는가 (G-6)
- [ ] 스펙 밖 파일이 diff에 있는가 (G-7)
- [ ] 옛 경로가 남아 있는가 (G-8)
- [ ] 성능 주장에 측정 근거가 있는가 (G-9)
- [ ] 새 추상화에 YAGNI 정당화가 있는가 (§2-3)
- [ ] 인용된 출처를 **실제로 열어** 확인했는가
- [ ] 보고의 "실패한 접근"이 비어 있다면, 커밋 히스토리로 교차 확인
- [ ] **테스트를 일부러 깨뜨려 보고** 실제로 실패하는지 확인 (통과만 보고 믿지 않는다)
