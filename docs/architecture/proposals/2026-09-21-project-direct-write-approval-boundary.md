# 프로젝트 직접 쓰기와 승인 경계 후속 제안

이번 변경에는 적용하지 않는다. 주정산·월결산 파이프라인과 기존 운영 저장 동작을 유지하기 위해 `/api/v1/projects` 직접 쓰기 경로는 변경하지 않았다. 새로운 필수 완성도 검사는 등록·수정 초안의 최종 제출 경로에서 적용한다.

## 실제 호출 경로와 위험

- `ProjectWizard.tsx` 관리자 수정은 직접 `updateProject`를 호출한다.
- `portal-store.tsx` 상태/체크아웃 저장은 기존 프로젝트 전체 객체에 상태/체크아웃만 바꿔 전송한다.
- `CashflowWeeklyPage.tsx`의 조직장·책임자 연결은 같은 API로 `executiveApproverId/Name/Email`, `managerId/Name`을 변경한다.
- `store.tsx`는 전체 객체의 수익 별칭을 정규화하고 전송한다. 저장본에 `totalRevenueAmount`가 없어도 `profitAmount`/`profitRate`에서 파생한 값이 들어올 수 있다.
- `DataMigrationTab.tsx`도 기존 프로젝트 전체 객체를 직접 저장한다.

따라서 제출 소유 필드가 포함됐다는 이유로 직접 쓰기를 차단하면 체크아웃과 주정산/월결산 화면의 담당자 연결이 차단된다. 원시값 비교만으로도 기존 수익 별칭 정규화가 실제 계약 변경으로 오인될 수 있다.

## 후속 설계

1. 관리자의 등록정보 수정도 임시저장·최종 제출 경로로 연결한다.
2. 상태/체크아웃/정산 운영/담당자 연결을 명시적 업무 명령으로 분리한다. 기존 권한과 데이터 경로를 각각 검증한다.
3. 계약 변경은 불변 제출본을 거쳐 승인하도록 통일하고, 직접 쓰기에는 해당 명령이 소유한 필드만 허용한다.
4. 전환 완료 후 트랜잭션 안에서 최신 저장본 대비 실제 계약 필드 변경을 거부한다. 기존 운영 데이터의 공란을 임의로 0으로 간주하지 않는다.
5. 최종 gate는 운영 화면별 실제 사용자 흐름과 임시저장 왕복, 동시성, 전체 객체 no-op 저장을 검증한 뒤 도입한다.

이는 다음 작업 제안이다. 이번 변경에서 직접 쓰기 API에 차단 코드를 남기지 않았다.
