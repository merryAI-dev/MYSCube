## 개선 1 — `api → storage` 계층 건너뜀 제거 (−15)

### 현상

```java
// WeeklyExpenseController.java:26
import dev.merryai.innerplatform.weekly.storage.WeeklyExpensePersistence;
```
`persistence.` 직접 호출 **3회**. 대조로 `WeeklyExpenseCommandService`는 96회 — **그쪽이 정상 위치**다.

### 왜 아직 안 했나

3회 중 하나가 `readCashflowSource`(`:304`)이고, 이는 **SPEC-19가 조사 중인 대시보드 읽기 경로**다. 계층 위반과 성능 문제가 같은 지점이라 **같은 파일을 두 번 건드리지 않기 위해** 의도적으로 보류했다.

### 계획

| 단계 | 내용 | 선행 |
|---|---|---|
| 7-1-A | SPEC-19 결과로 대시보드 읽기 범위 확정 | **SPEC-19** |
| 7-1-B | 3개 호출을 서비스 계층 메서드로 이관. `readCashflowSource`는 확정된 범위 계약으로 | 7-1-A |
| 7-1-C | Controller에서 `storage` import 제거 + **소스 스캔 테스트로 0건 고정** | 7-1-B |

**주의(SPEC-05):** 서비스 메서드로 옮길 때 `WeeklyExpenseCommandService`의 public 메서드가 되면 **자동으로 트랜잭션에 들어간다**(Aspect가 모든 public 메서드를 감쌈). 읽기 전용 호출이 불필요하게 트랜잭션을 여는지 확인하고, 필요하면 별도 read 서비스에 배치한다. **이 판단을 건너뛰지 마라.**

### 성공 조건
1. `api` 패키지의 `storage` import **0건** (소스 스캔 단언)
2. `WeeklyExpenseController`의 `persistence.` 호출 **0건**
3. 기존 응답 스키마 **변화 0** (계약 테스트)
4. 읽기 경로가 불필요한 트랜잭션을 열지 않음 (근거 제시)

## 개선 2 — 공통 인터페이스 이름 정합 (−6)

### 현상 — 같은 동작이 계층마다 다른 이름

| 동작 | 프론트 | BFF | JVM |
|---|---|---|---|
| 반영 진행 상태 조회 | `apply-status` | `readCashflowSheetApplyStatus` | `sheet-lab/operations` |
| 결산 기한 | (표시만) | ~~`cashflowMonthCloseDeadline`~~ | `closeDeadline` |
| 주차 라벨 | `getYearFinanceWeeks` | 동일 모듈 | `financeWeekDeadline` |

남은 역참조 `server/bff → src/app` **5건**(8→5, 13-A 효과).

### 계획

| 단계 | 내용 | 선행 |
|---|---|---|
| 7-2-A | **용어집 작성** — 동작별 정식 이름 1개씩 확정. `docs/architecture/cashflow-glossary.md` | 없음 |
| 7-2-B | 13-D: `server/bff → src/app` 역참조 5→0. 공유 모듈을 최상위로 | SPEC-01 머지 ✅ |
| 7-2-C | 13-F: BFF `cashflowMonthCloseDeadline` 삭제, JVM 응답 필드 사용 | 7-2-A |
| 7-2-D | 이름 불일치 3건 정렬 + **용어집 대조 테스트** | 7-2-A |

**13-G(타임존 통일)는 폐기한다.** SPEC-21 조사에서 이중 계약이 아님이 실행 대조로 확인됐다. 대신 **날짜 전용 코어를 "KST 업무 달력"으로 명명·문서화**만 한다(소급 변경 0건 경로).

### 성공 조건
1. `server/bff → src/app` import **0건**
2. 용어집의 각 동작이 3계층에서 **동일 이름**
3. BFF에 기한 계산 구현 부재 (소스 스캔)
4. 기존 API 응답 필드명 **변화 0** (외부 계약 보존)

## 개선 3 — 규칙의 도메인 이주 (−15)

### 현상

| 계층 | 줄 수 | 상태 |
|---|---:|---|
| `domain` | 2,769 → **2,900+** | 빈혈 (개선 중) |
| `storage` | **6,891** | 영속화 + 비즈니스 규칙 혼재 |

`storage`가 들고 있는 도메인 규칙: 결산 기한(`atDay(10)` 2곳), 재무주차 달력, 주간 준수 판정, 결산 상태 정규화, `yearMonth` 형식 규칙(7곳+).

### 방법 — 나누지 말고 뽑아내라 (SPEC-05)

**인터페이스 분할 금지.** `WeeklyExpensePersistence`를 Port로 쪼개면 thread-local 7종으로 공유되는 트랜잭션 원자성이 깨진다. 월 확정 하나가 8개 컬렉션을 한 트랜잭션에서 쓴다.

**추출(extract)은 트랜잭션 경계를 건드리지 않는다.** persistence는 하나로 남고 원자성은 그대로이면서 규칙만 순수 함수가 된다. 이미 검증된 패턴이다:
- `CashflowQueryScope` (SPEC-12) ✅
- `CashflowApplyLease` (SPEC-20) ✅
- `CashflowMonthReopenApprovalPolicy` (SPEC-17) ✅
- `ApproverDeadlineCalculator` (SPEC-18-B) ✅

### 추출 대상과 순서

| 단계 | 추출 대상 | 현재 위치 | 크기 | 위험 |
|---|---|---|---|---|
| 7-3-A | `yearMonth` 형식 규칙 (`requireYearMonth`) | storage 7곳+ | 소 | 낮음 |
| 7-3-B | 결산 기한 (`atDay(10)` 2곳 → 1곳) | `:580`, `:3789` | 소 | 낮음 — **13-F와 함께** |
| 7-3-C | 재무주차 달력 (`financeWeekDeadline`) | `:1745` | 중 | 중 — SPEC-21 명명 정리와 함께 |
| 7-3-D | 주간 준수 판정 (`weeklyComplianceStatus`) | `:1761` | 중 | **중 — 저장 판정값. SPEC-04 준수 필수** |
| 7-3-E | 결산 상태 정규화 (`canonicalMonthStatus`) | 다수 | 대 | 높음 — SPEC-15와 함께 |

**7-3-D 주의:** 준수 판정은 **저장되는 값**이다. 추출 후 결과가 1비트라도 달라지면 과거 이력이 소급 변경된다. 추출 전후 **동일 입력 → 동일 출력**을 실행 대조로 증명해야 한다(SPEC-21이 쓴 방법론).

### 성공 조건
1. 각 추출이 **단독 커밋**, 호출부 0이어도 존재 가능 (F-1)
2. 추출된 함수가 DB·HTTP·설정·`async` **없음**
3. persistence는 **호출 한 줄만** 남음
4. **추출 전후 동일 입력 → 동일 출력** 실행 대조 (특히 7-3-D)
5. `storage` 줄 수 감소를 숫자로 보고
6. 트랜잭션 원자성 회귀 0 (기존 Firestore 트랜잭션 테스트)
