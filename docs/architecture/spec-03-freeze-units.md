# SPEC-03 — 동결 가능한 최소 기능 단위 (Freeze Units)

**작성:** 2026-08-07 · **위상:** SPEC-00/01/02와 함께 **모든 스펙의 상위 규범**
**배경:** 동작하는 부분을 live에서 순차적으로 **freeze**할 예정이다. 이 문서는 그 전제를 만족하도록 작업 단위를 규정한다.

---

## 0. 전제 — 리팩토링은 "전체 교체"가 아니다

이 프로젝트의 목표는 캐시플로 영역을 한 번에 새로 짜는 것이 **아니다.** 동작이 확인된 부분부터 **순차적으로 동결**하고, 동결된 부분은 이후 변경에 흔들리지 않아야 한다.

따라서 모든 작업은 다음 조건을 만족해야 한다.

> **각 변경은 그 자체로 동작하고, 독립적으로 동결 가능하며, 동결 이후 다른 작업의 영향을 받지 않는다.**

이 조건을 만족하지 못하는 변경은 아무리 옳아도 **지금 하지 않는다.**

---

## 1. 최소 기능 단위(Freeze Unit)의 정의

하나의 Freeze Unit은 아래를 **전부** 만족한다.

| # | 조건 | 검증 |
|---|---|---|
| F-1 | **단독으로 배포 가능** — 다른 미완성 작업에 의존하지 않는다 | 이 커밋만으로 게이트 통과 |
| F-2 | **단독으로 되돌리기 가능** — 되돌려도 다른 기능이 깨지지 않는다 | revert 후 게이트 통과 |
| F-3 | **계약이 명시적** — 이 단위가 외부에 약속하는 입출력이 문서·타입·테스트로 고정됨 | 계약 테스트 존재 |
| F-4 | **동결 후 불변** — 이후 작업이 이 단위의 내부를 고치지 않고도 진행 가능 | 의존 방향이 단방향 |
| F-5 | **하나의 관심사** — 두 가지를 동시에 바꾸지 않는다 | PR 제목이 "A와 B"가 아님 |

**F-2가 핵심이다.** 되돌릴 수 없는 변경은 동결의 대상이 아니라 위험이다.

---

## 2. 계층 간 계약을 "직접 주고받게" 만든다

SPEC-01의 계층 분리는 **동결을 가능하게 하는 수단**이다. 목적을 다시 적는다.

```
애플리케이션 서비스 ──[명시적 계약]──> 도메인
        │                              ↑
        │                              │ 이 경계가 고정되면
        │                              │ 도메인은 서비스 변경에 영향받지 않는다
        └── 외부 I/O, 프레임워크, 설정 ──┘  (동결 가능)
```

### 2-1. BFF↔JVM 관계를 참조 모델로 삼는다

BFF와 JVM은 이미 **명시적 계약**(HTTP 엔드포인트 + 요청/응답 스키마)으로 연결되어 있다. 한쪽을 바꿔도 계약이 유지되면 다른 쪽은 영향받지 않는다. 이것이 좋은 성질이다.

**도메인과 애플리케이션 서비스 사이도 같은 성질을 가져야 한다.**

| 항목 | BFF↔JVM (참조 모델) | 도메인↔서비스 (목표) |
|---|---|---|
| 계약의 형태 | HTTP 스키마 | **함수 시그니처 + 결과 타입** |
| 계약의 위치 | 코드 밖(문서·DTO) | **도메인 모듈의 공개 API** |
| 한쪽 변경의 파급 | 계약 유지 시 없음 | **계약 유지 시 없음** |
| 검증 | 계약 테스트 | **계약 테스트** |

### 2-2. 구체 규칙

1. **도메인 모듈의 공개 함수는 계약이다.** 시그니처와 결과 타입을 바꾸려면 별도 단위로 취급한다
2. **결과는 구조화된 객체로 돌려준다.** 예외를 제어 흐름으로 쓰지 않는다 — 예외는 서비스 계층에서 잡히면 도메인 계약이 깨진 것처럼 보인다
3. **도메인은 서비스의 실패에 영향받지 않는다.** 입력이 주어지면 항상 판정한다. I/O 실패는 서비스가 다룬다
4. **서비스는 도메인 내부를 알지 못한다.** 공개 API만 호출한다. 도메인 내부 타입을 외부로 노출하지 않는다
5. **계약 테스트를 단위마다 남긴다.** 이 테스트가 동결의 증거다

## 3. 각 스펙의 Freeze Unit 분해

기존 스펙을 아래 단위로 쪼개 진행한다. **한 PR = 한 Unit.**

### SPEC-14 (진행 중) — 이미 최소 단위에 가깝다
| Unit | 내용 | 동결 가능 |
|---|---|---|
| 14-A | 오류 → 가이드 매핑 모듈 (순수 함수 + 계약 테스트) | ✅ 단독 |
| 14-B | `PlatformApiError`가 code/serverMessage 보존 | ✅ 단독 |
| 14-C | 캐시플로 화면 표시 연결 | 14-A·B 이후 |

14-A는 **아무것도 호출하지 않아도 존재 가능**하다. 가장 먼저 동결한다.

### SPEC-12 (진행 중) — 쿼리 지점별로 쪼갠다
| Unit | 내용 | 동결 가능 |
|---|---|---|
| 12-A | 범위 계산 도메인 클래스 (순수, whereIn 청크 포함) + 단위 테스트 | ✅ 단독 (호출부 0) |
| 12-B | `monthly_closes` 필드 선택 | ✅ 단독 |
| 12-C | `cashflow_weeks` 필터 — **메서드 1개씩** | ✅ 각각 단독 |

**12-C를 한 번에 하지 마라.** 메서드마다 호출부 검증이 필요하고(SPEC-12 §4-2), 하나가 틀리면 전부 되돌려야 한다. 메서드 단위로 커밋하면 되돌리기 범위가 그 메서드로 한정된다.

### SPEC-13 (대기) — 이미 PR 3분할, 더 쪼갠다
| Unit | 내용 |
|---|---|
| 13-A | policy JSON을 공유 위치로 **이동만** (동작 변경 0) |
| 13-B | 프론트 하드코딩 배열 → JSON 파생 |
| 13-C | BFF 리터럴 `160` → 파생 상수 |
| 13-D | `server/bff → src/app` import 방향 정리 |
| 13-E | JVM 카탈로그를 JSON 소비로 |
| 13-F | 기한 판정 단일화 (BFF 계산 삭제) |
| 13-G | 주차 달력 통일 — **승인 후** |

13-A는 **동작을 전혀 바꾸지 않는 이동**이므로 가장 안전하고, 나머지의 전제가 된다.

### SPEC-15 (대기) — 착수 조건 유지 + 더 쪼갠다
기존 PR-A/B/C를 유지하되, PR-A(JVM 엔드포인트 신설)를 **엔드포인트 1개씩** 쪼갠다. 각 엔드포인트는 호출되지 않는 상태로도 존재 가능하므로 단독 동결 가능하다.

## 4. 하지 말아야 할 것 (동결을 깨뜨리는 패턴)

| 패턴 | 왜 안 되는가 |
|---|---|
| 여러 관심사를 한 PR에 | 하나가 틀리면 전부 되돌려야 한다 (F-2 위반) |
| "겸사겸사" 인접 코드 정리 | 동결 대상이 아닌 코드가 diff에 들어온다 |
| 미완성 코드를 미리 넣기 | 단독 배포 불가 (F-1 위반) |
| 계약 변경과 구현 변경 동시 | 되돌리기 단위가 커진다 (F-5 위반) |
| 동결된 단위의 내부 수정 | 동결의 의미가 사라진다 (F-4 위반) |
| 전체를 새로 짜고 스위치 | 되돌리기가 전부-아니면-전무가 된다 |

**마지막 항목이 가장 위험하다.** 큰 리팩토링은 "다 됐다"는 시점까지 검증되지 않는다. 이 프로젝트는 이미 그 방식으로 실패한 기록이 있다(14일 61커밋 중 46% fix, 서브시스템 3개 생성 후 삭제).

---

## 5. 성공 조건 추가 (모든 스펙에 적용)

각 스펙의 성공 조건에 아래를 추가한다.

1. **단위 독립성**: 각 커밋이 단독으로 게이트를 통과한다
2. **되돌리기 안전성**: 각 단위를 `git revert` 했을 때 게이트가 통과한다 (최소 1개 단위에 대해 실제로 검증)
3. **계약 테스트**: 도메인 모듈의 공개 API마다 계약 테스트가 있다 — 시그니처·결과 타입·경계 동작
4. **서비스 독립성**: 도메인 단위 테스트가 DB·HTTP·설정 없이 실행된다 (mock조차 필요 없어야 한다)
5. **동결 선언**: PR 본문에 "이 단위는 동결 가능하다" 근거를 F-1~F-5로 적는다
