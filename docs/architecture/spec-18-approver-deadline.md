## 0. 이 스펙만 신규 기능이다

다른 스펙(12·13·15·17)은 **기존 동작을 유지하는 리팩토링**이다. 이 스펙은 **없던 판정을 추가**한다. 따라서:

- 다른 스펙과 **같은 PR에 섞지 마라**
- SPEC-13(정책 단일화)이 policy 파일을 옮기는 중이므로 **파일 충돌을 피해 순서를 조율**한다. policy 정의 추가는 SPEC-13-A 완료 이후에만 가능하다(이미 완료: `policies/cashflow-policy.json`)

## 1. 업무 규칙 (확정)

| 대상 | 실무자 마감 | **조직장 최종 승인 마감** | 미준수 누적 기준 |
|---|---|---|---|
| 주간 정산 | 목요일 자정 (금 0시) | **익일 금요일 13:00** | 실무자 마감 |
| 월간 결산 | 익월 10일 자정 (11일 0시) | **3일 이내 자정 (14일 0시)** | 실무자 마감 |

### 핵심 불변식

> **미준수 누적(compliance)은 실무자 마감만 본다.** 조직장 승인이 늦어도 실무자의 미준수로 카운트하지 않는다.

이 불변식을 깨면 실무자가 남의 지연으로 불이익을 받는다. **승인 시각을 기존 compliance 판정에 끌어들이지 마라.**

## 2. 현재 구현 (조사 완료)

| 규칙 | 상태 | 위치 |
|---|---|---|
| 주간 실무자 마감 | ✅ 구현 | `financeWeekDeadline` — 주차 내 목요일 +1일, Asia/Seoul |
| 월간 실무자 마감 | ✅ 구현 | `atDay(10)` — `:580`, `:3789` |
| compliance = 실무자 마감 기준 | ✅ 구현 | `weeklyComplianceStatus(completedAt, deadline)` → `ON_TIME`/`COMPLETED_LATE` |
| **조직장 승인 마감** | ❌ **개념 자체가 없음** | `approverDeadline`/`approvalDeadline` 검색 0건 |

## 3. 범위

### 이번에 하는 것
1. policy JSON에 두 승인 마감 규칙을 **정의로 기록**
2. JVM 도메인에 **승인 마감 계산** 순수 함수 추가
3. 월 결산/주간 정산 조회 응답에 `approverDeadline` 필드 **노출**
4. 승인이 마감을 넘겼는지 여부(`approvalLate`) **계산 및 노출**

### 이번에 하지 않는 것 (명시)
- 승인 마감 초과 시 **차단**하지 않는다 (기한이 지나도 승인 가능)
- 알림·리마인더 발송
- 기존 compliance 카운터 변경
- 승인 마감을 실무자 compliance에 반영
- UI 표시 (백엔드 필드 노출까지. 화면은 후속)

**차단하지 않는 이유:** 현재 승인 마감 개념이 없으므로, 도입 즉시 차단하면 진행 중인 결산이 막힌다. 먼저 관측만 하고 정책 강제는 별도 판단으로 남긴다.

## 4. 요구사항

### 4-1. 계산 규칙 (정확히)

**주간:** 실무자 마감(주차 내 목요일 다음날 0시, KST) → 그 **금요일 13:00 KST**

주의: 실무자 마감이 이미 "목요일 +1일 = 금요일 0시"다. 승인 마감은 **같은 금요일 13:00**이다. 별도 요일 계산을 하지 말고 실무자 마감 날짜에 13시간을 더하는 방식이 맞는지 **코드로 확인하고 판단을 보고하라.**

**월간:** 실무자 마감(익월 10일 자정 = 11일 0시) → **14일 0시 KST**
= 익월 11일 0시 + 3일

### 4-2. 계층 (SPEC-01)

- 계산은 **도메인 순수 함수**. Firestore 핸들·Spring 컨텍스트를 받지 않는다
- `FirestoreInheritedWeeklyExpensePersistence.java`(6,891줄)에 넣지 마라. 신규 도메인 클래스로 분리
- policy JSON에서 값을 읽되, **요청 경로에서 반복 로드하지 마라** (기동 시 1회)

### 4-3. SPEC-04 준수

- **확정(CLOSED)된 월의 저장값을 바꾸지 마라.** `approverDeadline`은 **계산해서 응답에 실을** 뿐, 기존 문서에 소급 기록하지 않는다
- 이미 승인이 끝난 과거 건에 `approvalLate`를 소급 기록하지 마라 (계산 결과를 응답에 노출하는 것은 허용)
- 기존 `late`, `closeDeadline`, `snapshotHash`, `amendmentCount`는 **바이트 단위로 동일**해야 한다

## 6. 성공 조건

### 6-1. 계산 정확성
1. 주간: 마감이 해당 주 **금요일 13:00 KST**
2. 월간: 마감이 익월 **14일 0시 KST**
3. 월 경계: 12월 대상 → 다음 해 1월 14일 0시
4. 윤년 2월 대상 → 3월 14일 0시
5. 주차가 월을 걸치는 경우 판정이 흔들리지 않는다
6. **타임존**: 모든 계산이 Asia/Seoul. UTC로 계산해 하루가 밀리지 않는다

### 6-2. 불변식 보존 (핵심)
7. **기존 compliance 판정값이 변하지 않는다** — `ON_TIME`/`COMPLETED_LATE`가 승인 시각과 무관
8. 승인이 마감을 넘겨도 실무자 미준수 카운터가 증가하지 않는다
9. CLOSED 월의 저장 필드가 바이트 단위로 동일 (SPEC-04 T-1)

### 6-3. 경계·오염
10. 승인 시각 없음(미승인) → `approvalLate`가 예외 없이 판정 가능 (아직 늦지 않음/이미 늦음)
11. `yearMonth`가 `null`/`''`/`2026-13` → 명확한 오류, 무필터 폴백 없음
12. policy에 승인 마감 값이 없으면 → **기동 실패** (조용히 기본값 쓰지 마라)
13. 프로토타입 오염 키 → 폴백

### 6-4. 회귀 방지 쌍
14. **유지 존재**: 실무자 마감·compliance 판정·기존 응답 필드가 전부 그대로
15. **제거 부재**: 승인 시각이 compliance 계산에 흘러드는 경로가 없다
