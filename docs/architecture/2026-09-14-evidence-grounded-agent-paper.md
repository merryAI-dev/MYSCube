# 결정론적 업무 데이터 실행과 동적 에이전트 궤적의 분리

## MYSCube Slack 정산 에이전트의 실패 분석과 증거 기반 재설계

**문서 성격:** 기술 연구 초안·설계 제안·운영 사례 기록. 단일 사례 검증을 포함하며, 일반화 성능을 검증한 연구 논문이나 전체 운영 완료 보고서는 아니다.
**작성일:** 2026-09-14  
**현재 버전:** v0.4 — 실제 Slack 답변·서버 실행 trace 대조. 최신 결과는 §14, §3·§10의 초기 상태는 당시 기록이다.
**범위:** 사내 Slack의 읽기 전용 프로젝트·주정산·월결산 질의응답.  
**핵심 명제:** 고정해야 할 것은 권한과 데이터 의미 및 실행 계약이다. 질문 해석, 조회 경로, 답변 표현까지 고정하지 않는다.

## 초록

본 문서는 MYSCube Slack 정산 에이전트에서 관찰된 형식 불이행, 불필요한 다중 조회, 승인 시각 누락을 분석한다. 사용자는 조직별 요약, 전사 미완료 목록, 특정 승인 시각 등 다양한 질문을 하지만, 기존 시스템은 좁은 보고서 도구와 고정 렌더러를 사용했다. 코드 조사에서는 모델 최종 문장 폐기, CIC 및 시각 필드의 도구 응답 누락, 제한된 실행 단계가 확인됐다. 이 관찰은 해당 실패를 모델 능력 부족만으로 설명할 수 없음을 보여준다. 다만 모델 간 성능 차이나 각 원인의 기여율을 실험으로 규명한 것은 아니다.

우리는 JVM의 업무 의미와 권한 검증을 유지하면서, 모델이 데이터 계약을 탐색하고 조회를 조합하는 실행 구조를 제안한다. 질문의 데이터 요구와 표현 요구를 분리하고, 출처가 있는 관측 결과를 바탕으로 다음 행동을 선택한다. 자연어 피드백은 우선 관찰 자료로 저장하며, 향후 외부 궤적 선택 정책에 PLC-DPO의 clean/flip/tie 목적함수를 적용하는 실험을 정의한다. 후속 운영 QA 한 건에서 실제 Gemini가 두 읽기 도구의 결과를 사용해 요청된 주차의 제출·승인 시각만 답했고, 두 값 모두 기록된 서버 관측과 초 단위로 일치했다. 다만 실행 trace는 기존 `settlement-read-v2`였으므로 이를 Hermes 전환 효과로 귀속하지 않는다. 실제 사용량·단일 응답 지연은 §14에 기록하며 일반화 성능·비용 절감·학습 효과는 미측정이다.

## 1. 연구 질문과 배경

핵심 연구 질문은 다음과 같다.

1. 업무 데이터의 단일 진실 원천(SSOT)을 유지하면서 사전에 정의하지 않은 질의 조합에 대응할 수 있는가?
2. 형식 변경과 데이터 범위 변경을 분리하면 불필요한 조회와 후속 질문 실패를 줄일 수 있는가?
3. 도구 계약의 정보 손실과 모델의 추론 실패를 어떻게 구분할 것인가?
4. 사용자의 자연스러운 피드백을 사실 판정이나 권한과 혼동하지 않고 외부 정책 개선에 활용할 수 있는가?

이 문서의 ReAct는 React UI 철학이 아니라 관측과 행동을 반복하는 에이전트 접근을 의미한다. ReAct는 외부 환경에서 얻은 관측으로 행동 계획을 수정하는 구조를 제안한다.[1] Gemini function calling은 모델이 함수와 인자를 제안하고 호스트가 실행한 결과를 다시 모델에 전달할 수 있도록 지원한다.[2] 이 기능 자체가 올바른 업무 판단을 보장하지는 않는다.

### 3.2 합의한 방향

- 질문별 답변·도구 시나리오를 계속 추가하는 방식은 중단한다.
- JVM 상태·업무 판정 및 권한을 유지하고 조회 경로와 답변 구성은 모델에 맡긴다.
- 자연스러운 한국어, 오타, 생략, 여러 질문, 후속 정정을 지원한다.
- Slack에서는 간결한 문장·강조·emoji를 허용하되 완료·미확인을 혼동하지 않는다.
- 승인·금액·파일·Drive 삭제 등 업무 쓰기 권한은 이 연구 범위에 추가하지 않는다.
- 기존 cloud worker·queue·인증·감사 저장을 재사용한다. 프레임워크 교체는 선행조건이 아니다.
- 사용자가 실제 Slack QA를 수행하기로 했다. 무단 시험 공지나 사업 데이터 변경을 수행하지 않는다.
- 사용자 요청에 따라 이번 기록·설계 작업에는 스킬을 사용하지 않는다.

## 4. 문제의 정식화

시각 t의 업무 상태를 D_t, 인증 주체를 u, 버전이 명시된 데이터 계약을 S_v, 질문을 x, 대화 상태를 H라 하자. 실행 도구의 의미는 다음과 같다.

\[
o_i = T(a_i; D_t, u, S_v)
\]

T는 허용된 행동 a_i에 대해 권한 검사, 조회, 도메인 판정, 계산을 수행한다. 동일한 스냅샷·주체·정책·입력에 대한 결과 재현성을 목표로 한다. 살아 있는 DB를 서로 다른 시각에 조회해도 같은 값이 나온다는 뜻은 아니다.

모델은 외부 관측과 대화에 조건부로 다음 행동을 제안한다.

\[
a_i \sim \pi_\phi(\cdot\mid x,H,S_v,o_{1:i-1}),\qquad
y \sim \pi_\phi(\cdot\mid x,H,E)
\]

E는 출처와 조회 시각이 확인된 관측의 집합이며 y는 자연어 응답이다. 모델의 내부 파라미터 φ는 현재 실험에서 고정된 외부 API다. 도구 구현이 결정론적이라는 사실은 행동 선택이나 생성 문장의 결정론성을 뜻하지 않는다.

제안하는 실행 목적은 사용자 요청 충족 U를 높이고 불필요한 비용 C, 지연 L, 중복 조회 R을 줄이는 것이다.

\[
\max_\pi\;\mathbb{E}[U-\lambda_c C-\lambda_l L-\lambda_r R]
\]

단, 권한 밖 행동·업무 쓰기·미등록 실행은 **페널티가 아니라 불허 제약**이다. 보상이 높아도 이 경계를 넘을 수 없다. 자연어 주장의 근거 충족은 별도 평가 대상이며, 이 목적함수가 환각 부재를 증명하지 않는다. λ 값과 효과는 아직 선정·측정하지 않았다.

## 5. 제안 방법: 계약 탐색과 조합 가능한 조회

### 5.1 책임 경계

```text
Slack → 기존 인증·영속 큐 → Gemini 실행 루프
                              ↕ 탐색 / 조회 / 결과 참조
                         BFF 읽기 capability
                              ↕ 주체·계약·입력 검증
                         JVM 업무 조회·판정
                              ↕
                         실제 저장 데이터

조회 결과 → 출처·시각·완전성 기록 → Gemini 답변 생성 → Slack
```

JVM이 canonical settlement state와 승인 기록의 의미를 소유한다. 프로젝트·CIC·People 메타데이터는 현재 BFF의 기존 원장을 사용한다. 이를 모두 새 JVM DB로 이전한 것처럼 기술하지 않는다. BFF의 메타데이터 결합과 집계는 버전된 계약으로 재사용하고 JVM 상태를 재정의하지 않는다.

### 5.2 최소 capability 제안

다음 이름은 **설계안**이며 현재 존재하는 API라고 주장하지 않는다.

| capability | 입력·출력 계약 | 고정하지 않는 것 |
| --- | --- | --- |
| `describe_data` | 허용된 업무 view, 필드 타입·의미·nullable 여부, 관계, 연산자, 지원 기능 반환 | 질문 문구와 조회 순서 |
| `resolve_entities` | 사업·조직·사람의 검색 후보 및 안정된 ID, 일치 근거·모호함 반환 | 임의 top-1 확정 |
| `query_data` | view·선택 필드·필터·그룹·집계·정렬·페이지를 검증한 후 실행 | 월결산 미완료 같은 완성 보고서 종류 |
| `read_result` | 기존 결과 참조를 재인증하고 원래 snapshot 의미로 읽기 | 답변 형식 enum과 고정 문장 |

도구 수를 위 네 개로 영구 고정할 필요는 없다. 이미 있는 데이터 접근기를 재사용하고 실제 실행할 수 있는 capability만 등록한다. 전체 Firestore schema를 모델에 공개하거나 임의 SQL·shell·URL 실행을 허용하지 않는다. 지원하지 않는 관계나 필드는 근사값으로 채우지 않고 구조화된 오류로 돌려준다.

계약은 우선 다음 기존 근거에서 추출한다.

- 프로젝트: name, cic, executiveApproverId 및 현재 조회 범위 정책.
- 인물 연결: People uid, name, nickname; 중복·미연결은 명시적 불확실성.
- 월결산: settlementCycle.businessState, health, workflowRevision, 대상월·주기월.
- 주정산: period, status, submittedAt, approvedAt, deadlineAt, approverDeadlineAt, revision.
- 과거 승인 이벤트·월결산 상세 처리 시각: **추가 원장 및 API 유무 확인 필요**. 현재 상태에서 과거 이력을 복원하지 않는다.
- 정산 의무·체크아웃 제외: 현 agent report에 연결되지 않았다. 지원 전에는 `unsupported`로 설명하고 등록 사업 조회와 구분한다.

필터는 서버에서 타입·연산자·허용 필드·권한을 검사하는 제한된 AST로 받는다. 집계 전에 권한과 필터를 적용하고 페이지 일부를 전사 총계로 계산하지 않는다. 전체 계산이 불가능하면 partial 및 계산 범위를 반환한다. EMPTY, ZERO, null, 기록 없음, 조회 실패를 통합하지 않는다. 기존 시트 좌표 계약도 변경하지 않는다.

### 5.3 결과 봉투

결과에는 `resultId`, `contractVersion`, `query`, `queriedAt`, 사용 가능한 `sourceRevision`, `coverage`, `complete`, `nextCursor`, `rows` 또는 `aggregates`, `warnings`를 포함한다. 존재하지 않는 revision을 만들어내지 않는다. 여러 원장을 읽었다면 각각의 시각·revision을 기록하고 전역 원자적 스냅샷이라고 주장하지 않는다.

기존 공개 스레드 권한과 요청자 식별은 호스트에서 유지한다. 모델 인자로 tenant·role을 받지 않는다. 저장 결과 재사용 시 계정·프로젝트 접근을 재검사한다. 감사용 ID와 사용자에게 보여주는 사업명은 분리한다.

## 6. 동적 궤적과 다중 턴

대화 상태는 `dataIntent`, `presentationIntent`, `entityBindings`, `resultRefs`, `unresolved`로 구분하는 것을 제안한다. 이는 업무 질문 종류의 닫힌 enum이 아니라 모델이 현재 요청과 이전 대화를 정리하는 상태다. 실행 전에 query AST는 별도로 검증한다.

```text
인증하고 현재 대화 상태와 사용 가능한 계약을 읽는다.
시간·호출·토큰 예산이 남아 있는 동안:
  모델이 조회 / 계약 탐색 / 기존 결과 읽기 / 확인 질문 / 최종 답변을 선택한다.
  조회라면 인자·권한을 검증하고 실행해 관측과 출처를 저장한다.
  같은 snapshot에 대한 동일 조회가 반복되면 기존 결과를 참조하게 한다.
  오류라면 지원 필드·불확실성을 돌려주고 모델이 다음 행동을 선택한다.
  답변이라면 확보한 근거와 미확인 범위를 대조하고 전달한다.
예산이 끝나면 확인된 것과 아직 확인하지 못한 것을 구분해 종료한다.
```

항상 discovery부터 실행하는 고정 시나리오를 만들지 않는다. 계약이 이미 알려져 있으면 바로 조회할 수 있다. 독립 조회는 병렬 실행할 수 있지만 결과 ID·권한·기간을 서로 섞지 않는다. 의미 있는 모호함은 질문하고 단순 오타마다 사용자에게 형식 입력을 요구하지 않는다.

“CIC별로 다시”는 표현 변경이고 “월결산만”은 데이터 범위 축소일 수 있다. 모델이 이를 해석하되, 기존 leader-only 같은 필터는 명시적 변경이 없으면 보존한다. 확보한 결과로 새 요청을 충족할 수 있으면 재사용하고, 새로운 기간·필드·최신 상태가 필요하면 조회한다. 이전 assistant 문장을 DB 증거로 사용하지 않는다.

형식 재구성에도 집계가 필요하면 기존 결과를 서버 연산으로 계산한다. 모델에게 모든 숫자 계산을 금지하면서 계산 도구는 주지 않는 모순을 만들지 않는다. 간단한 인사·피드백 확인에는 DB 조회를 강제하지 않되 정산 사실을 섞어 답하면 근거가 필요하다.

## 7. 생성·검증·감사

Gemini가 최종 문장, 구조, 설명 정도, emoji를 선택한다. 고정 renderer는 모델 또는 연결 장애 시 확인된 근거를 보존하는 fallback이지 정상 응답 경로가 아니다. Slack 문법은 지원하되 도구 데이터나 생성문에서 자동 멘션·임의 링크 구문이 활성화되지 않도록 escape한다.

검증은 두 층으로 구분한다.

1. 코드 검증: 입력과 출력 계약, 권한, 출처 참조, 집계 결과, 페이지 완전성, 내부 ID 노출, 중복 실행, 발송 주체.
2. 의미 평가: 질문 충족, 주장과 근거의 연결, 오해를 부르는 표현, 불필요한 내용. LLM judge는 확률적 평가자이며 같은 모델의 공통 오류를 놓칠 수 있다.

숫자에 출처 참조가 있다고 해서 주변 문장까지 참이 되는 것은 아니다. 주장 근거 연결과 인간 검토를 함께 평가한다. “요청 전”을 “조직장이 승인을 지연했다”로 바꾸거나 현재 미승인을 과거 마감 당시 미승인으로 단정하지 않는다.

감사에는 질문, 선택한 행동·인자, 구조화된 짧은 행동 이유, 결과 참조, 실제 토큰·시간, 오류와 답변 버전을 저장한다. 모델의 비공개 사고 과정 원문은 요구하거나 저장하지 않는다. 기존 hash chain은 관리자에 의한 anchor 동시 재작성을 막지 못하며 WORM 보장으로 표시하지 않는다.

## 8. PLC-DPO와 외부 정책 학습의 관계

### 8.1 적용 대상

DPO는 선호 쌍에 대한 정책과 기준 정책의 확률비를 이용하는 학습 방법이다.[3] 사용자 제공 PLC-DPO 본문은 이를 clean/flip/tie routing으로 혼합한다.[4] 현재 API 호출만으로 Gemini 내부 φ를 업데이트하거나, 없는 sequence log-probability를 임의 점수로 대체해 “Gemini PLC-DPO 학습”이라고 부를 수는 없다.

대신 **우리 소유의 외부 후보 궤적 선택기** θ를 실험 대상으로 제안한다. 동일 요청에서 생성·검증된 후보 궤적 집합 A(x)에 대해 특징 f(x,τ)와 학습 가능한 weight θ를 둔다.

\[
p_\theta(\tau\mid x,A)=\frac{\exp(\theta^\top f(x,\tau))}{\sum_{\tau'\in A}\exp(\theta^\top f(x,\tau'))}
\]

이 확률은 Gemini 응답 확률이 아니라 외부 선택기의 후보 조건부 확률이다. 후보 집합과 특징 버전을 저장하고, 같은 후보 집합 위에서 고정 기준 θ₀와 비교한다. 후보가 하나면 선호 학습을 하지 않는다. 실제 결과 특징은 실행 후 평가에만 쓰며, 실행 전 선택기 입력에 미래 결과를 누출하지 않는다. 위반 권한의 후보는 점수와 무관하게 먼저 제거한다.

### 8.2 실험 목적함수

검토된 선호 쌍 (τ_w,τ_l)에 대해 다음 margin을 정의한다.

\[
m=\beta\left[\log\frac{p_\theta(\tau_w\mid x,A)}{p_{\theta_0}(\tau_w\mid x,A)}-
\log\frac{p_\theta(\tau_l\mid x,A)}{p_{\theta_0}(\tau_l\mid x,A)}\right]
\]

PLC-DPO 본문의 구조를 따라 detached margin의 batch mean·variance를 EMA로 갱신하고 z=(stopgrad(m)−μ)/max(√v,σ_min)로 정규화한다. routing은 아래와 같다.

\[
q=\operatorname{stopgrad}\,\operatorname{softmax}\left(
\log\pi_c^0+z/\tau_{dir},\;
\log\pi_f^0-z/\tau_{dir},\;
\log\pi_t^0-|z|/\tau_{tie}\right)
\]

\[
L_c=\operatorname{softplus}(-m),\quad L_f=\operatorname{softplus}(m),\quad
L_t=\operatorname{softplus}(|m|)
\]

\[
C(q)=\left(\frac{\max(q)-1/3}{2/3}\right)^\kappa,\qquad
L=(1-\gamma_s C)L_c+\gamma_s C(q_cL_c+q_fL_f+q_tL_t)
\]

warm-up 중 γ_s=0, 이후 제한된 schedule을 사용한다. 이 수식은 **PLC-DPO 목적함수를 외부 궤적 선택기에 이식하는 제안**이지 논문의 Gemini·업무 에이전트 성능 결과가 아니다. 추가 L2를 실험한다면 `λ‖θ−θ₀‖²/2`로 별도 표시하고 원 논문과 동일한 목적함수라고 주장하지 않는다. routing temperature는 API 생성 temperature와 다르다.

### 8.3 피드백 수집과 안전한 평가

버튼과 대화 정정은 모두 관측이다. “CIC별로 해달랬는데”는 형식 불일치 증거일 수 있지만 정산 수치 오답의 라벨은 아니다. 침묵·공손함·짜증을 정답/오답으로 변환하지 않는다. “좋아요”만 있고 비교 대상이 없다면 선호 쌍을 구성하지 않는다.

같은 근거 snapshot·같은 요청에서 두 답변 또는 궤적을 비교할 수 있고 선호 방향이 검토됐을 때만 학습 후보로 승격한다. 데이터 정정·표현 선호·서비스 장애를 분리한다. 모델의 높은 flip score로 사용자의 사실 정정을 자동으로 무효화하지 않는다. clean/flip/tie는 학습 신호 routing이지 사용자 신뢰도나 정답 인증이 아니다.

초기에는 shadow 평가만 수행하고 θ를 운영에 자동 반영하지 않는다. 변경 전후 정책과 독립 평가를 저장한다. SLA·권한·업무 판정은 학습 대상이 아니다. 학습기를 먼저 만드는 대신 아래 데이터 capability와 기준선 실험을 먼저 완성한다.

## 9. 평가 설계

### 9.1 비교 조건

- B0: 기존 좁은 보고서 도구 + 고정 렌더러.
- B1: 같은 도구 계열 + Gemini 최종 생성 + 근거 검토. 초기 PR #782/#783 후보이며, 후속 운영 관측은 §14에 기록한다.
- B2: 계약 탐색 + 조합 가능한 조회 + 관측 기반 재계획. 본 문서의 제안, 미구현.
- B3: B2 + 외부 궤적 선택 정책의 shadow 학습. 데이터 확보 후 연구 단계.

우선 동일한 Gemini 모델과 동일한 도구 근거 snapshot으로 B0/B1/B2를 비교한다. 모델 변경 효과는 이후 같은 B2 harness에서 별도 비교한다. 모델 ID, 계약·코드·프롬프트 버전, 원시 usage, 실패 응답과 재시도를 모두 기록한다.

### 9.2 데이터 분리

사용자가 이미 제공한 실패 질문은 개발 회귀 세트다. 이를 수정한 후 그 질문만 통과했다고 일반화 성능을 주장하지 않는다. 별도 평가자는 코드 작성에 사용하지 않은 표현·기간·관계·필터 조합을 구성한다. 같은 대화 스레드와 그 패러프레이즈는 같은 split에 둬 누출을 방지한다. 재무 정답은 같은 snapshot의 서버 결과로 만들고 문체 평가는 별도 라벨로 관리한다.

### 9.3 측정 항목

| 지표 | 정의 |
| --- | --- |
| 과업 완료율 | 요구한 데이터 범위와 표현을 모두 충족한 질문 / 평가 질문. 오류·미완료도 분모에 포함 |
| 사실 근거율 | 근거가 확인된 업무 주장 / 전체 업무 주장. 주장 없는 답변은 N/A로 별도 처리 |
| 필드·집계 정확도 | 서버 oracle과 일치한 평가 항목 / 평가 가능한 항목 |
| 후속 정정 성공률 | 기존 조건을 보존하며 정정을 충족한 턴 / 정정 턴 |
| 불필요한 조회 | 정답에 기여하지 않은 조회 및 동일 snapshot 중복 조회 수. 판정 기준 사전 명시 |
| 적절한 확인 질문 | 실제로 필요한 모호함과 불필요한 확인을 분리해 precision/recall 측정 |
| 효율 | 접수 안내와 최종 응답 지연을 분리한 p50/p95, DB 읽기, 입력·출력·thinking·cache 토큰 |
| 비용 | 실제 usage와 기록된 적용 단가로 계산한 비용. 청구서 금액·환율과 구분 |
| 안전 | 권한 밖 조회, 업무 쓰기, 데이터 누출, 기간 혼합, 부분 결과를 전체라고 표시한 건수 |

샘플 수·반복 수·pass 기준은 측정 전에 확정한다. 본 문서에 임의의 개선율이나 p-value를 넣지 않는다. 필수 안전 검증에서는 위반 0건을 gate로 두지만 유한 시험으로 전체 안전성을 증명했다고 쓰지 않는다.

### 9.4 제거 실험과 실패 분석

계약 설명 제거, 필드 투영 축소, 모델 최종 생성 제거, 결과 참조 기억 제거를 각각 비교해 병목을 분리한다. 고정 단계 상한과 예산 기반 종료도 같은 비용 범위에서 비교한다. 자연어 judge 사용 여부는 사실성과 지연·비용에 미치는 영향을 따로 측정한다. 제약을 모두 풀어 성능을 올린 결과와 권한을 유지한 개선을 섞지 않는다.

| 6 | 피드백 쌍 데이터와 외부 정책 shadow 실험 | 고정 기준선·데이터 분리·재현 가능한 margin 없이는 학습 효과 주장 금지 |

초기 1차 구현은 프로젝트/인물 연결 및 canonical 주·월 상태·시각에 한정했다. 후속 승인으로 Hermes 클라우드 런타임 구현과 실호출을 진행했으며 현재 증거는 §14에 기록한다. 과거 이력·미지원 의무 판정·범용 DB는 여전히 완료 범위가 아니다. 기존 읽기 구현을 대체하면 호출부에서 실제 연결하고 중복 경로를 정리한다. 선언만 한 도구나 실행되지 않는 새 모듈을 완료로 보고하지 않는다.

## 12. 한계와 운영 고려

사용자 월 비용 목표는 50,000원이다. 기존 구현의 시도당 500원·월 30,000원 예약은 실제 토큰 정산이 아니며 인프라 포함 50,000원의 강제 청구 상한도 아니다. 단계 수를 늘릴 때 단순히 예약 정책만 유지하고 비용이 보장된다고 주장하지 않는다. 생성·검토·재시도 비용을 합산하고 예산 부족 시 새 유료 호출 전에 중단한다.

권한 있는 데이터도 외부 모델로 전송될 수 있으므로 필요한 view와 필드만 제공한다. 보존 기간, 접근 기록, 결과 snapshot 접근 범위를 운영 정책으로 확정해야 한다. 논문 공개본에는 실제 사업명·임직원명·내부 ID·채널 ID 및 Slack 원문을 별도 승인 없이 포함하지 않는다. 이 문서는 내부 연구 기록이다.

Hermes/OpenClaw가 본 구조보다 우수하거나 비용이 낮다는 비교 실험은 없다. framework 채택 여부는 같은 계약·같은 평가 세트에서 판단한다. 더 많은 단계, 더 긴 문맥, 더 강한 모델을 쓴다고 정확성이 자동으로 높아지는 것도 아니다.

## 13. 추가 승인 범위: 연결 시트 읽기와 Hermes 독립 조사

사용자는 본 문서 작성 중 연결된 시트까지 조회 범위를 확장하고, 별도 워커가 GitHub의 “Hermes agent2”를 확인해 소스를 받아오도록 요청했다. 허용 범위는 **조회·읽기**다. 이 추가 요청은 시트 편집·공유 변경·업무 DB 쓰기 또는 범용 shell 권한의 승인이 아니다.

### 13.1 확인한 기존 연결 경로

- `projects.cashflowSheetLabSources`의 연도별 연결 및 기존 `cashflowSheetLab` 설정: `routes/cashflow-sheet-lab.mjs`의 `readCashflowSheetLabConfig(s)`가 해석한다.
- `projects.participationSheetLink`: `src/app/data/types.ts`에 등록된 참여율 시트 링크다.
- `google-sheets.mjs`는 `getSpreadsheetMeta`, `getSheetValues`, `getSpreadsheetFreshness`를 제공한다. 같은 객체에 `batchUpdateValues`도 있고 인증 scope도 현재 `spreadsheets`이므로 객체 전체를 외부 에이전트에 노출하면 안 된다.
- `getSheetValues`는 현재 표시 문자열을 반환한다. 이 값만으로 수식 유무, 원시 숫자 타입 또는 수식 계산 오류를 확정하지 않는다. 수식·effective value 검증이 필요하면 별도 읽기 계약을 먼저 구현한다.
- 기존 mirror refresh는 Firestore snapshot 저장 등 부작용을 갖는다. 이름이 조회처럼 보여도 읽기 전용 agent에서 동기화·refresh·apply 경로를 호출하지 않는다.

### 13.2 읽기 권한과 데이터 경계

모델은 프로젝트의 연결 source를 탐색하고 해당 source 참조로 탭·허용 범위의 내용을 요청한다. 호스트는 프로젝트 접근권한과 실제 저장된 연결을 확인한 후에만 Google 호출을 수행한다. 모델이 spreadsheet ID·임의 URL·토큰을 바꿔 조직 전체 Drive로 탐색 범위를 넓히게 하지 않는다. 시트 내부의 다른 링크도 자동으로 신뢰·추적하지 않는다.

Google 읽기 자격은 `spreadsheets.readonly`, 필요할 때 `drive.metadata.readonly`로 한정한다. OAuth scope와 파일 ACL은 서로 다른 경계다. 새 파일 접근이 필요하면 정확한 파일과 읽기 주체를 확인한 뒤 Viewer 권한을 요청한다. 기존 다른 업무에서 사용하는 editor 권한을 일괄 변경하지 않는다. 공개 링크, anyone/domain 공유, 조직 전체 위임, Drive 편집권을 기본 해법으로 사용하지 않는다.[5][6]

Sheets OAuth scope는 개별 탭 단위로 제한되지 않으므로 호스트가 연결 source·탭·필드·범위를 제한해야 한다.[5] 프로젝트/채널 권한이 있다는 이유만으로 연결 문서의 인건비·개인정보 전체가 공개 채널 수신자에게 허용된다고 가정하지 않는다. 문서별 데이터 분류와 공개 가능 범위를 함께 확인한다.

에이전트에 제공하는 것은 서버의 읽기 capability이지 서비스 계정 private key가 아니다. 읽기 전용 Google scope, host의 호출 method 제한, 도구 allowlist를 함께 적용한다. 통합용 service account나 secret의 기존 운영 권한은 모델에게 전달하지 않는다.

JVM 응답은 승인 상태·정산 판정의 근거, 시트는 원문·표시값 확인의 근거다. 서로 다르면 각각의 조회 시각·revision과 차이를 설명하며 자동으로 덮어쓰거나 어느 한쪽을 최신이라고 추정하지 않는다. canonical cashflow 조회는 기존 고정 좌표 계약을 유지하고 양식 불일치는 거부한다.

### 13.3 구현 및 검증 상태

현재는 읽기 범위 승인과 코드 경로 조사를 완료했다. **Google 파일 ACL 부여, OAuth 변경, 연결 시트 실제 내용 조회, 새 sheet capability의 운영 배포는 아직 수행하지 않았다.** 구현 시 접근 가능한 연결과 403/404·미연결·삭제·탭 없음·부분 범위·양식 불일치를 구분하고, 변경 요청이 전송되지 않았음을 네트워크 로그/테스트로 확인한다.

### 13.4 Hermes 조사 원칙

v0.3에서 소스 확보와 정적 검토를 완료했다. 사용자가 지정한 `NousResearch/hermes-agent`의 `v2026.9.11`(제품 버전 `0.21.2`), commit `939e45c91d751fadd94dcd1b873ac3cb44846213`을 고정했다. [별도 검토 보고서](2026-09-14-hermes-readonly-assessment.md)에 코드 근거와 재현 경로를 기록했다. 기본 Slack toolset에는 쓰기·실행 도구가 포함되므로 그대로 운영 연결하지 않는다. 당시 설치·실행·실제 모델 호출은 하지 않았으며, 후속 실행 결과는 §14와 구분한다.

초기 조사에서는 별도 워커가 공식 저장소와 버전 명칭을 확인하고 고정 commit의 소스를 격리된 임시 디렉터리에 다운로드했다. clone은 설치·실행·클라우드 배포가 아니다. 당시 조사 범위에서는 설치 스크립트, dependency lifecycle, gateway, background job, 자동 업데이트를 실행하지 않았다.

비교 대상은 모델 provider 연결, 도구 실행 경계, Slack multi-turn, 영속 실행, 권한 우회 경로다. “읽기만 하라”는 프롬프트는 읽기 전용 보안 경계로 인정하지 않는다. 필요하다면 기존 MYSCube read gateway만 접근 가능한 별도 runtime과 좁은 자격 증명을 쓰며 terminal·파일 쓰기·일반 브라우저·임의 HTTP·확장 설치·미승인 MCP를 제거한다. host 정책을 우회할 수 있는 경로가 남으면 운영 연결하지 않는다.

### 14.4 개선의 해석과 남은 한계

18:43 제보에서는 시각 질문에 주·월 상태와 기한 보고서가 출력됐다. 이번 답변은 필요한 두 시각을 실제 근거로 답하고 불필요한 월·주차 설명과 단계 한도 경고를 내보내지 않았다. 이는 필드 투영과 모델 최종 문장 사용이 중요한 병목이었다는 가설에 부합한다. 그러나 질문 문구, 코드, 실행환경이 함께 바뀌었고 동일 snapshot의 대조 실험도 없으므로 개선을 Hermes, 특정 프롬프트, 모델 성능 중 하나의 인과 효과로 단정할 수 없다.

사용자의 긍정 평가는 표현·유용성에 대한 관찰로 기록한다. 이 발언은 이 대화에서 제공됐으며 Slack 피드백 저장이나 학습 반영까지 확인한 것은 아니다. 검토된 후보 궤적 쌍이 없고 trace의 기존 피드백 정책도 count=0, weight=0이므로 **PLC-DPO 또는 weight tuning으로 개선됐다는 증거는 없다.**

잔여 검증 항목:

- 실제 worker trace가 `hermes-readonly-v1`인 Slack 요청을 별도로 확인해야 한다.
- CIC 그룹화, 조직장별 목록, 모호한 요청, 다중 턴 정정, 실패·권한·부분 결과는 이 한 건으로 통과 처리하지 않는다.
- 답변에는 `**강조**` 문법이 남아 있다. Slack native mrkdwn 렌더링 품질과 emoji 사용성을 모두 해결했다고 주장하지 않는다.
- 도구 호출은 읽기 두 건이지만 queue·대화·감사는 저장된다. 이 trace만으로 모든 업무 DB에 쓰기가 전혀 없었음을 증명한 것으로 표시하지 않는다.
- 연결 시트 셀·수식 조회와 정산 의무/체크아웃 제외 정책의 agent 연결은 여전히 미완료다.

### 14.5 Hermes 클라우드 실호출과 Slack 증거의 분리

별도 비공개 Cloud Run 서비스 `myscube-hermes-readonly-00001-w7j`에서 Hermes 0.21.2와 실제 `gemini-3.6-flash`의 왕복은 확인했다. capability 목록 질문에 `agent_capabilities` 한 번을 요청하고 한국어 답변을 생성했으며 input=3,344, output=46, thinking=665, partial=false였다. 이 시험의 도구 결과는 호스트의 읽기 기능 목록으로, 실제 사업 DB 조회 시험은 아니다.

배포 [run 34834567824](https://github.com/merryAI-dev/MYSCube/actions/runs/34834567824)은 서비스 생성 후 익명 접근 검증에서 실패했다. `/healthz`는 인증 유무와 관계없이 Google 앞단의 404였고 실제 `/run`은 익명 403, 인증된 WebSocket은 모델 왕복에 성공했다. 검증 경로를 실제 `/run`으로 바꾸는 수정은 [PR #786](https://github.com/merryAI-dev/MYSCube/pull/786)에 기록했다. 이미지 빌드·실호출·배포 workflow 성공·Slack worker 경로는 서로 다른 검증 단계다.

새 런타임은 기본 실행 도구 대신 호스트의 읽기 allowlist만 호출한다. 별도 Gemini API 실호출 성공을 위 Slack 사례와 합쳐 **“Hermes → 업무 DB → Slack E2E 성공”으로 보고하지 않는다.** 이 구분 자체를 향후 평가의 실행 provenance 필수 항목으로 추가한다.

### 14.6 후속 A/B 적용 프로토콜 (실측 전)

사용자 승인에 따라 동일 `gemini-3.6-flash`를 사용하는 두 실행 경로를 비교한다. 기본 A는 기존 실행기이고, 질문에 `[Hermes]`를 표시하면 B로 보낸다. 같은 스레드의 후속 질문은 가장 최근 명시 태그를 이어받으며 `[Baseline]`으로 A로 돌아간다. 태그는 모델 입력에서 제거하고 호스트 감사 기록과 답변 하단에 실제 선택 경로를 남긴다. B 연결이 없거나 실패하면 A로 몰래 대체하지 않는다. 같은 데이터 읽기 도구·권한·별도 답변 검토를 사용한다.

수동 선택형 파일럿으로, 무작위 배정된 통계적 A/B 실험은 아니다. 두 경로의 반복 상한 등 기존 설정은 동일하지 않으므로 우선 전체 실행기 구성 비교로 해석한다. 동일 질문을 별도 새 스레드로 보내 실제 trace의 경로·조회 결과·사용량·지연·공개 답변을 대조한다. 실제 운영 DB는 시간에 따라 달라질 수 있으므로 근거가 달라지면 모델 차이로 평가하지 않는다. 사용자의 모든 요청을 자동으로 두 번 실행하지 않아 중복 공지와 유료 호출을 피한다. 이 절은 구현 프로토콜이며 A/B 운영 성공 수치는 아직 없다.

Slack 표현 변경은 두 경로 공통 발송 함수에서 일반 Markdown 제목 기호·구분선을 제거하고 강조·목록을 Slack 문법으로 정규화한다. 코드 구간·음수·숫자·멘션 차단을 보존하며 피드백 메시지 갱신에도 같은 함수를 적용한다. 문체는 모델이 생성하고 문법 호환성만 호스트가 처리한다.
