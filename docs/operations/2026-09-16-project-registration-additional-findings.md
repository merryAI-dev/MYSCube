## 확인한 문제

### P1 — 계약 날짜 편집 중 연도별 입력 소실

- `ProjectEditorWizard.tsx:1225`는 날짜 입력마다 전체 draft를 정규화한다. `project-editor.ts:343`은 날짜가 비었거나 범위가 역전되면 연도별 재무를 빈 배열로 만든다.
- 2025년 계약금액100/2026년200, 각 연도별 선금·입금월을 입력한 상태에서 종료일을 비웠다가 원래 날짜로 복구했다.
- 함수 재현 결과: 기존 두 행이 사라지고 2025년300/2026년0으로 재생성됐다. 선금과 입금월은 두 연도 모두 초기화됐다. 총액만 남아 연도별 배분 소실을 놓치기 쉽다.
- 실제 브라우저에서도 300/0 재분배와 선금·입금월 초기화가 자동저장 PATCH payload에 포함됨을 확인했다. 격리 mock 저장 결과이며 운영에서 이미 소실됐다는 증거는 아니다.
- 조치 방향: 날짜 입력 중 임시 상태와 연도별 입력을 분리해 보존하고, 범위 변경 확정 시 제외할 연도 데이터를 명시적으로 처리한다. 단순히 초기화 후 자동저장을 막는 것만으로는 부족하다.

### P1 — 해석하지 못한 금액을 정상적인 0으로 저장

- `project-contract-amount.ts:48`은 쉼표 제거 후 `Number()` 변환에 실패하면 0을 반환한다. 연도별 입력은 매 입력 이벤트마다 파싱하고 숫자로 다시 표시한다(`ProjectEditorWizard.tsx:2370`).
- 실제 등록·수정 위저드에서 일반 숫자 연속 입력, 쉼표 붙여넣기, 임시저장 payload는 정상 확인했다.
- 전각 `１２３４５`, 단위가 붙은 `12,345원`은 안내 없이 즉시 0으로 바뀌고 자동저장 PATCH payload도 0이었다. 합성 composition 이벤트도 전각 입력에서 같은 결과다.
- 사용자 제보의 실제 입력 환경이 확인되지 않았으므로 이것이 해당 스크린샷 사례의 확정 원인이라고 단정하지 않는다. 실제 OS IME는 아직 검증하지 않았다.
- 조치 방향: 입력 문자열과 저장 숫자를 분리한다. 허용할 전각 숫자는 명시적으로 정규화하고, 잘못된 형식은 기존 값을 보존하며 오류를 안내한다. 파싱 실패를 0으로 취급하지 않는다.

### P2 — 미래 시작·종료 미정 프로젝트의 재무 입력 차단

- `project-editor.ts:624`와 위저드의 연도별 검증은 종료 미정일 때 올해를 마지막 연도로 사용한다.
- 2026년 현재 시작일2027-01-01, 종료 기간 없음이면 시작연도>종료연도로 판단해 재무 행이 사라진다. 최종 제출에서도 전체 연도별 재무 확인 오류가 남는다.
- 실제 브라우저에서 2027년 금액 입력칸이 없고 자동저장 PATCH에도 `financialYears=[]`가 포함됨을 확인했다.
- BFF는 같은 조건에 `Math.max(startYear, currentYear)`를 사용한다(`server/bff/routes/projects.mjs:1351`). 화면·서버의 기간 해석이 다르다.
- 조치 방향: 미래 시작을 허용하는 서버 정책과 화면의 입력 행 생성·검증을 같은 함수/계약으로 맞춘다.

## 별도 확인 후보

- `buildProjectEditorReviewChanges`는 연도별 예정월만 바꾸면 변경사항을 빈 배열로 반환한다(직접 함수 재현). 다만 현재 포털의 BFF 변경 비교는 `financialYears`를 포함한다. 이 결과를 운영 검토함의 누락으로 확대해 주장하지 않는다. 해당 클라이언트 helper의 실제 사용 경로를 정리할 대상이다.
- 관리자 저장은 프로젝트 저장 후 담당자 배정 변경을 별도 호출한다. 후속 배정 호출 실패 시 전체 저장 실패로 안내될 수 있는 부분 성공 경로가 있다. 실제 실패 주입은 아직 하지 않았으므로 확정 버그 수에는 포함하지 않는다.

## 구현 및 배포 전 영향 검토 (2026-09-17)

- 금액 원문은 편집기 상태와 기존 로컬 checkpoint의 선택 필드로 보관한다. 유효한 정수만 draft에 반영한다. 전각·쉼표·원 단위를 정규화하며 잘못된 문자열은 0으로 저장하지 않는다. 오류가 있으면 자동/수동/최종 저장을 막고 단계 이동·명시복원 후에도 원문을 유지한다.
- 날짜 공란·역전·기간 축소 시 기존 재무행을 보존한다. 기간 밖 행은 화면에 표시하고, 사용자가 확인한 경우에만 제외하며 총계를 재계산한다. 기간 확대 시 기존 합계를 새 연도에 중복 배정하지 않는다.
- 단년도→다년도 변경 시 기존 입금 계획을 원래 연도에만 반영한다. 다년도→단년도 정리 확인 후에는 남은 연도의 입금 계획을 단년도 필드에 반영한다.
- 종료 미정의 마지막 연도 계산을 화면·BFF가 공유한다. BFF의 기존 미래 시작 정책 자체는 변경하지 않는다.
- 첨부 응답 때문에 같은 편집 세션의 잘못된 금액 원문이 초기화되지 않도록 보호한다. 저장 성공 표시도 금액 형식 오류가 남아 있으면 표시하지 않는다.
- 사용자 요청에 따라 업로드 timeout·AbortSignal·강제취소 변경은 모두 제외했다. 기존 업로드/취소 흐름과 포털10MB·관리자1GB 제한을 유지하고 첨부 영역에 파일당 제한만 표시했다.

영향 범위는 등록·수정·관리자가 공유하는 금액/날짜 편집 UI와 draft 정규화, BFF의 동일한 종료연도 계산이다. 업로드 클라이언트, 리스/fence, outbox, JVM, 캐시플로 좌표, Firestore Rules/indexes/스키마 변경은 없다. 운영 초안 마이그레이션·삭제는 수행하지 않았다.

최종 단위 4,151개 통과, BFF Firestore emulator 264개 및 Storage 규칙3개 통과, production build 통과, 타입 신규 오류 없음(기존 baseline187개). 기존 대용량 업로드의 네트워크 대기 동작은 이번 수정으로 해결했다고 주장하지 않는다.
