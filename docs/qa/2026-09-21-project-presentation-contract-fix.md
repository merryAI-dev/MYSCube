# 프로젝트 공통 표시·정산 의미 계약 수정: 독립 QA

## 목적과 범위

배포805 감사에서 확인한 세 문제를 프로젝트별 예외가 아닌 공통 규칙으로 해결한다: 구형 원장 초기 조회의 연도별 누락 안내, 구형 완료 프로젝트의 체크아웃 본문, 정산 유형과 기준이 모순될 때 BFF가 공급대가를NONE으로 바꾸는 의미 변환.

운영 데이터 쓰기·자동 보정·주정산/월결산/JVM 변경은 금지한다. 이번 문서는 구현 전 통과 기준이며 완료 판정이 아니다. 지정 QA skill 경로가 없는 것은 이전에 확인했고 독립 stage gate로 진행한다.

## Intent/data-path gate

1. 금액 안내: canonical 원장/제출 snapshot/개인 초안 → 공통 재무 해석 → Wizard 조회/편집/승인표. v1/v2 여부 때문에 안내를 빠뜨리지 않는다. 미기록을0으로 확정하거나 연도 row를 영속 저장하기 위한 자동 보정을 하지 않는다.
2. 체크아웃: 같은 snapshot의 상태 → 공통 노출 정책 → Portal 본문과 승인 본문. 상단 진입 버튼과 본문 노출을 별개로 확인한다. 과거 상태가 잘못됐더라도 날짜만으로 임의정정하지 않는다.
3. 정산 의미: 원문 payload + 현재 원장 → 공통 검증/투영 → GET readiness와 승인POST. 의미가 다른 기준으로 조용히 변환하면 실패다. 모순을 거절한다면 사람에게 문제항목·현재값·확인담당자·정상 재제출 경로를 구체적으로 알려야 한다.

## 공통 구현 통과 기준

- ID/이름/특정 프로젝트를 하드코딩하지 않는다. v1/v2와 표시위치에서 같은 조건을 사용한다.
- 구형 원본, 미제출 초안, 제출본의 소유 경계를 유지한다. 관리자 문서는 제출본을 확인하며 최신 개인 초안으로 바꾸지 않는다.
- 표시용 파생값으로 저장 필드·금액·상태·정산 기준·승인 상태를 변경하지 않는다.
- 기존 임시저장·복원·최종 제출의오류 보존 정책과 관리자 사업비 방식 숨김을 유지한다.

### 연도별 누락 안내

- 805의 활성26개/전체34개 원장 초기 조회를 동일snapshot으로 재생하면 필요한 연도·금액 항목 안내가 나타난다.
- 누락연도는 실제 계약기간 공통규칙으로 판정하고 종료미정/미기록일 때 임의 연도를 만들어 확정하지 않는다.
- 신형 초안 및 승인표에도 같은 snapshot은 같은 누락항목을 표시한다. 합계수익률 계산 조건은 유지된다.
- 새 helper/공통영역으로 이동한 뒤 같은 안내가 화면에 중복 출력되지 않는다. 빈 row에서도 렌더 오류가 없다.

### 체크아웃 본문

- 기존 S_GH 사례뿐 아니라 같은상태의 v1/v2/미기록 모든형식에서 본문 노출이 일치한다.
- 완료와 완료(잔금대기)의 허용정책은 기존 공통정책을 따른다. 계약전/진행중에는 체크아웃 본문을 보이지 않는다.
- 조회 전용 화면에 체크박스·업로드가 보이더라도 쓰기를 할 수 없어야 한다. 수정 화면에서는 기존초안 저장과 연동하며 다른체크아웃값을 초기화하지 않는다.
- 첨부가 없거나 구형기록이없을 때 미기록/미첨부를 구별한다. 완료로보이는원장상태를 임의로수정하지 않는다.

### BFF 의미 보존과 상세 안내

- 유효한 공급대가가 변환 후NONE이 되지 않는다. 공급가액의명시된동의어 정규화는동작한다.
- 모순된 제출은공통검증으로차단하거나원문을보존하는명확한정책을사용한다. 미리선택한답을추정해채우지않는다.
- GET readiness와승인POST는같은모순규칙을사용한다. 버전충돌이먼저발생하는사례와버전정합후의모순사례를분리해검증한다.
- 거절 시현재원장·제출요청·초안·첨부쓰기0. 기승인/철회요청조회는자동재제출/자동정정하지않는다.
- 안내는잘못된값이무엇인지,등록자가어디서어떤항목을확인해야하는지,조직장은새제출본을검토해야한다는점을명시한다. 내부code만보이면불합격이다.

## 증거 기준

독립QA는 새수정소스+805의고정운영읽기snapshot 재현으로 전후를대조한다. 최소공통매트릭스는실제컴포넌트로확인하고, 805재무196뷰·동일제출395뷰 중변경영역의전수회귀를사용한다. 전체PNG저장과모든항목육안확인을동일시하지않는다. BFF는실제함수/transaction adapter 또는서비스테스트로의미·원본보존을검증한다. 운영승인POST는실행하지않는다. 테스트통과만으로운영데이터정정완료나배포완료를주장하지않는다.

## 추가 승인 범위: 이전 제출 양식 조회

구형 제출자료의 관리자 조회를 유지하고 승인목록에 양식 배지를 표시한다. 제출버전1/2/미기록/알수없는버전과 요청없음을 구별한다. 양식 판정과 표시 원문은 해당 `record.request`의 제출 payload에서 가져오며, 개인초안이나 현재원장으로 미기록을 메우지 않는다. 원문펼침에서0·false·빈문자열·미기록의차이를 유지한다. 관리자 사업비입력방식 숨김은 원문에도 적용한다. 원문은 안전하게 텍스트렌더링하고 클릭/펼침이 쓰기를 유발하지 않는다. 요청없는원장에 구형제출본이 있는 것처럼 배지를 붙이지 않는다. unknown버전을현재양식으로오인하지않는다.

## 구현 후 독립 결과: 최초 UI 두 문제

## 후속 범위: 제안서 파일 한 슬롯 확장 (구현 전 기준)

- 실제input의accept와클라이언트/BFF허용규칙을대조한다. 확장자대소문자,빈MIME의File,표준MIME,확장자와명시MIME모순,미허용확장자를확인한다.
- 허용파일은초안첨부metadata·Storage형식으로보존되어재열기와history복원에사용가능해야한다. 최종제출/승인문서조회는동일name/path/type를사용한다. 미리보기를지원하지않는형식은열기/내려받기안내를제공하고PDF라고허위표시하지않는다.
