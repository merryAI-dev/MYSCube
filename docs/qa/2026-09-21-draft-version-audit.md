# 임시저장 버전 관리 독립 QA

2026-09-21. 필수값 개선 중 사용자가 추가로 제기한 “최신 저장이 반드시 올바른 것은 아니며 이전 버전을 확인할 수 없다”는 문제를 조사했다. 운영 데이터 수정, 승인 실행, 주정산·월결산 변경은 하지 않았다.

## 수정 전 조사 결과

조사 시점의 `draftRevision`은 **동시 저장 충돌을 막는 번호**다. 사용자가 과거 임시저장 내용을 비교하고 선택해 복원하는 버전 이력 기능은 아니다. 임시저장 보존·충돌 방지가 있다는 사실만으로 버전 관리까지 구현됐다고 안내하면 안 된다.

- 등록·수정 모두 저장할 때 같은 초안 문서의 `payload`를 교체하고 `draftRevision`을 증가시킨다.
- 저장 시각과 감사 이벤트는 남지만, 감사 이벤트에 과거 필드 전체와 첨부 목록이 보존되는 것은 아니다.
- 등록·수정 화면은 응답의 버전을 내부 ref에 보관한다. 사용자에게 버전 번호, 작성자, 기준 승인본, 버전별 변경 내용을 함께 보여주는 기능이 없다.
- 로컬 복원 안내는 한 개 로컬 초안의 시각과 “버리기/임시저장 불러오기”만 제공한다. 서버 저장본과 필드별 비교가 없고, 로컬 저장 자체도 같은 키를 덮어쓴다.
- 기존 rebase 기능은 **기준 승인본·내 초안·현재 승인본**의 3자 비교다. 과거 임시저장 A와 B를 선택하는 기능이 아니다. 충돌은 사용자가 선택하므로 단순히 최신 승인본을 강제하지는 않는다.

## 실제 실행 증거

현재 소스와 SHA-1이 일치하는 `server/bff/routes/project-info-drafts.mjs` 실제 서비스를 fixture 트랜잭션 DB로 실행했다. 코드 정적 판단에만 의존하지 않았다.

1. 초안 열기: revision 0.
2. 이름 `correct earlier`, 메모 `A` 저장: revision 1.
3. 이름 `later wrong`, 메모 `B` 저장: revision 2.
4. 재조회: revision 2와 B만 반환.
5. privateEditDrafts의 해당 문서는 1개. 서비스 메서드에 history/listVersions/restore가 없음.
6. 감사 이벤트는 revision 0/1/2를 기록하지만 A의 필드 내용은 없음.

실행: `/tmp/myscube-sprint-validation/server/bff/routes/draft-history-audit.test.mjs`, `vitest -t 'QA current draft revision'` **1 PASS**. 원본 결과: `/tmp/myscube-draft-history-audit.json`. 실제 서비스와 fixture DB 검증이며, 운영 DB의 백업 보존 여부나 사용자별 과거 복구 가능성을 입증하는 시험은 아니다.

멱등성 응답 캐시에 과거 저장 응답이 일시적으로 남을 수 있으나, TTL이 있는 재시도 캐시이며 이력 조회 API가 아니다. 이를 안정적인 복구 원장으로 취급하면 안 된다.

## 실제 저장 경로와 API

| 대상 | 저장·읽기 | 사용자 가능한 것 | 부족한 것 |
|---|---|---|---|
| 등록 초안 | `projectRequestDrafts/{draftId}`; GET/PATCH `/api/v1/project-registration-drafts/:draftId` | 여러 별도 초안의 이름과 저장 시각을 보고 이어쓰기 | 하나의 초안 내 과거 revision 내용 목록·비교·복원 |
| 등록 초안 목록 | GET `/api/v1/project-registration-drafts` | ACTIVE 초안 최대 100개, 시각 내림차순 | revision을 목록에서 반환하지 않음. 여러 초안과 버전 이력은 다름 |
| 수정 초안 | `privateEditDrafts/{project+actor 기반 id}`; GET/PATCH `/api/v1/project-info-drafts/:projectId` | 본인 현재 초안 재열기, 버전 충돌 차단 | 이전 revision 원문 조회·복원 |
| 수정 기준 정렬 | POST `.../:projectId/rebase` | 기준 승인본과 초안을 비교, 겹치는 수정 직접 선택 | 임시저장 자체의 과거 버전 복원 |
| 로컬 초안 | localStorage `mysc:project-editor-autosave:{key}` | 미반영 로컬 초안 1개 복원 또는 삭제 | 여러 과거 버전, 서버본과 비교, 출처·서버 revision 식별 |
| 관리자 승인 | review-document의 요청 스냅샷·reviewToken | 본인이 읽은 제출본과 다른 버전 승인 차단 | 실무자 비공개 임시저장 이력은 아님. 공개해서도 안 됨 |

## 첨부파일과 복원의 특별 위험

초안 파일 교체·제거는 이전 **초안 소유 파일** 정리를 실행하거나 cleanup outbox를 만든다. 기존 제출본에서 상속한 파일은 보호하는 경로와 테스트가 있지만, 모든 과거 초안 파일이 보존되는 구조는 아니다. 따라서 JSON 이력만 저장하고 파일을 그대로 삭제하면 “복원 성공”이라고 표시해도 첨부 원본은 사라질 수 있다.

로컬 초안 복원도 portal 등록·수정에서는 첨부 필드를 현재 서버 초안의 첨부로 교체한다. 이는 유효하지 않은 파일 참조 복원을 막지만, 과거 로컬 값 전체가 그대로 돌아오는 동작이 아니다. 복원 전에 이 차이를 알려야 한다.

## 근본 수정안과 단계별 통과 기준

1. **출처 표시:** 현재 작성 화면에 초안 revision, 저장 시각, 서버/기기 내 보관 구분, 기준 승인 버전, 마지막 제출 버전 표시. 최신은 “가장 최근 저장”으로만 표현하고 권장 정답처럼 선택하지 않는다.
2. **불변 이력:** 성공한 초안 저장과 동일 트랜잭션에서 원문 payload·첨부 참조·기준 버전·스키마 버전·작성자·저장 시각을 append-only revision 문서로 보존. 신규 저장뿐 아니라 첨부 추가/제거·rebase·회수도 일관된 이력 단위로 정의한다. 저장 실패와 재시도는 이력 중복을 만들지 않아야 한다.
3. **명시 비교와 복원:** 사용자에게 A/B의 필드·금액·첨부 차이를 먼저 보여주고 선택받는다. 복원은 기존 revision을 덮어쓰지 않고 과거 내용에서 **새 revision을 만드는 작업**이어야 한다. 복원 직전에 현재 revision·편집 임대·권한을 다시 확인한다. 자동 제출·자동 승인은 하지 않는다.
4. **첨부 보존:** 이력에서 참조하는 파일은 정리 대상에서 제외하거나 불변 버전 파일로 보관한다. 이미 없어진 옛 파일은 복구 가능하다고 표시하지 않고 정확히 재첨부 필요를 안내한다. 기존 저장소 전체에 무조건 보존 정책을 바꾸기 전 저장 비용·보관 범위 결정이 필요하다.
5. **검증:** A 정상→B 잘못 입력→A/B 비교→A 선택→C 생성→새로고침 C 확인, C 이후 동시 D 저장 시 복원 충돌 차단, 명시 0/false/없음 유지, 파일 교체·제거 후 과거 버전 파일 조회, 다른 사용자 비공개 차단, 신규 필수 정책에 미달하는 과거 내용도 임시 복원은 허용하고 최종 제출만 상세 차단.

기존에 남기지 않은 과거 revision을 새 코드로 소급 복원할 수는 없다. 보존 시작 시점을 표시하고, 기존 승인 스냅샷·본인 로컬 초안 등 실제 남아 있는 출처만 복구 후보로 안내해야 한다.

## 이번 작업 트리의 개선 (미배포)

등록·수정 초안에 실제 저장 이력을 별도 문서로 보관하고 본인만 조회하는 GET API를 추가했다. 임시저장, 첨부 변경, 제출·회수·기준 정렬의 버전 변경을 같은 트랜잭션에서 기록한다. 새로운 작성 회차에는 고유 이력 식별자를 부여해 같은 시각의 제출→재작성에서도 버전이 충돌하지 않는다. 기존 데이터는 일괄 수정하지 않으며 기존 초안은 첫 변경 직전 내용부터 보관한다.

Tailwind 기반 패널은 화면에 불러온 초안, 마지막 저장 확인본, 기준 프로젝트와 제출 문서를 구분한다. 본인이 선택한 과거 저장본과 마지막 서버 저장본의 차이를 보여주며 공란·미기록·0·false를 구분한다. 저장 성공 응답은 작성 중인 입력값을 재설정하지 않는다. 조회 실패 시 기존 비교 결과와 입력을 유지한다.

현재 작성 회차의 최근 20개 이력 조회·비교 범위다. 과거 파일은 목록만 비교하며 다운로드·자동 복원은 제공하지 않는다. 이전에 저장하지 않았던 내용을 소급 복구했다고 주장하지 않는다. 운영 인증을 포함한 실사용 전체 E2E는 아직 수행하지 않았다. 독립 QA의 실제 컴포넌트 브라우저 검증과 Firestore 에뮬레이터 검증은 별도 구현 QA 문서를 참조한다.
