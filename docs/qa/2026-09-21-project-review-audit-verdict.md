- request가 있는 승인 문서의 업무 내용을 해당 최종 제출본에서 읽으며 현재 원장·이후 임시저장과 섞지 않음.
- 최종 결과보고서 매핑 및 제안서 PDF/종료 증빙 표시 누락을 연결함. 과거 유실 데이터 자동 복구는 하지 않음.
- 파일과 Drive 링크 동시 제출 시 둘 다 표시함. 최신 운영 제출본에 동시 존재 사례가 없어 격리 fixture 근거임.
- JLIN의 실무자 연도별 선금 70%와 패치 승인 요약 70%를 실제 같은 제출본으로 확인. 현 운영 승인 요약의 14%와 차이 확인.

## 브라우저 확인 방법과 한계

운영 승인 화면 71개 문서의 실제 열람에 더해, 11:39:58~11:40:01 KST 운영 저장값을 독립 Chromium에서 실제 입력/승인 컴포넌트로 재현했다. 79개(현재 71·휴지통 8) 프로젝트에서 입력 4단계와 승인 문서 총 395개 전체 화면을 캡처하고 루트 및 독립 QA 3인이 분담하여 모두 직접 열어 대조했다. 원래 모달 viewport 79개도 별도로 남겼다. 요청 없는 5개는 원장 기반 화면 재현이며 실제 승인 요청이 있다는 뜻이 아니다. 같은 프로젝트·제출 버전을 기준으로 비교했고 운영 수정 페이지의 초안/lease 생성은 피했다.

실제 첨부 바이트·PDF 본문, 사용자별 다운로드 권한, 외부 시트 재동기화, 두 실제 사용자 세션의 저장/승인 클릭까지 검증한 것은 아니다. 외부 연결이 차단된 재현 화면의 미리보기 실패를 운영 파일 소실로 세지 않았다. 초기 명부 조회가 없는 재현의 빈 역할 선택창은 저장값 소실이 아니었다. 이후 실제 읽은 명부를 로컬 API 응답으로 공급하여 79개 인력 화면을 재캡처했다. 로컬 fixture GET 158회, 오류·쓰기 시도 0이며 저장 인력 156개 모두 명부 매칭 및 라벨 표시를 확인했다. 실제 사용자 인증/명부 API 권한 검증은 아니다. 승인 문서는 전체 촬영에 한해 바깥 스크롤 높이만 확장했다.

로컬 비공개 캡처 인덱스: `/tmp/myscube-review-audit-20260921/browser-visual/index.html`. 원문 스냅샷·첨부 경로·화면은 저장소에 커밋하지 않았다.

## 후속 구현 구조 제안 — 아직 구현하지 않음

최종 제출 시점의 버전 있는 제출본을 승인 문서의 단일 원본으로 사용한다. 임시저장은 별도 편집 상태로 유지하고, 제출본과 현재 원장의 차이는 명시적인 비교 보기로만 제공한다. BFF의 필드별 수동 화이트리스트 중복을 줄이기 위해 제출 스키마·업무 라벨·표시 범위의 공통 계약을 두고, 누락과 명시 삭제(null/false/빈 문자열)를 구분한다. 승인 시 변경할 필드만 버전 검증 후 원장에 반영한다.

이 계약은 단순 공통 타입 선언으로 완료되지 않는다. UI 입력→초안 저장/재열기→최종 제출→BFF 저장→승인 조회→승인 반영의 실제 왕복에서 필드 존재·값·삭제 의도·권한을 검증해야 한다. 과거 제출본에 없는 값은 현재 원장으로 조용히 채우지 않고 확인 불가로 표시한다. 운영 데이터 보정이나 상태 일괄 변경은 이번 감사에 포함하지 않았다.

## 재연결 이후 새 증거

CUA native pipe는 복구되지 않았지만, 사용자의 계속 조사 요청에 따라 독립 테스트 브라우저로 전환해 캡처를 완료했다. 11:32 재조회에서 변경된 요청/초안 한 쌍을 분리 기록했고, 실제 브라우저용 11:40 재조회 때 초안이 다시 열려 원문 보유 89개/metadata-only 144개였다. 원본 10:14 분석과 서로 다른 시점이므로 한 스냅샷인 것처럼 섞지 않는다.

독립 DOM 대조에서 표시된 총액 356/356, 연도별 계약·수익·실비·지원금 320/320, 입력 연도 VAT·수익·실비·지원금 320/320가 저장값과 일치했다. 첨부 파일명 172개, 제안 링크 24개, 발표 링크 22개 표시를 확인했다. 이는 표시된 필드의 값 대조이지 미표시 필드까지 통과했다는 뜻이 아니다. 승인 문서에서 폴더 링크 31개와 연도 VAT 80개 행이 빠지는 문제는 남았다.

추가 육안 발견:

- 일부 단년도 입력 검토의 연도별 문장은 선금/중도금/잔금 0으로 표시하지만 같은 화면 하단과 승인 문서는 실제 금액을 표시한다. 입력 검토 자체도 공통 계산 모델로 정렬해야 한다.
- 긴 폴더/참여시트 URL이 옆 카드 내용을 침범한다. 값은 존재해도 검토자가 읽을 수 없는 표시 결함이다.
- 구형 승인 완료 문서에 결재자 미지정·검토대기 도장이 함께 보이고, 철회 요청도 검토대기로 표현되는 사례가 있다. 요청 상태와 이력 미기록을 구분해야 한다.
- 구형 미등록 금액이 입력의 0 placeholder, 검토의 '-', 승인 0으로 다르게 나타난다. 0과 미기록을 공통으로 구별해야 한다.

이번 조사에서 운영 쓰기·승인·반려·임시저장 변경·배포는 수행하지 않았다. 전수 조사 범위를 넓혔지만, **PR #801의 전체 해결 판정은 FAIL**이다. 확인된 누락·삭제 의도·승인 버전 문제를 수정한 뒤 실제 왕복 검증이 필요하다.
