# 임시저장 복원·연도별 금액 안내: 독립 QA 기준

이 문서는 신규 구현의 통과 기준이며 구현 완료나 운영 배포 결과가 아니다. 기존 관리자 사업비 입력 방식 숨김 패치는 유지한다. 운영 데이터 쓰기, 주정산·월결산·JVM 변경은 범위 밖이다.

## 실제 데이터 경로

복원은 버전 목록/비교 UI → 현재 작성값 보호 저장 → 저장 ACK의 revision·작성 회차 → BFF restore 요청 → 소유자·편집 lease·CAS·history 회차·첨부 접근 검증 → 현재 draft 및 append-only history의 원자적 새 revision → 성공 ACK 후 편집기 교체 → 재열기 경로다. canonical 프로젝트와 조직장에게 이미 제출된 요청은 최종 제출/승인 전까지 바뀌지 않는다.

금액 안내는 저장된 각 연도 금액과 입력 여부 → 공통 표시 정책 → 실무자 Wizard 및 관리자 승인표다. 안내를 보여주기 위해 입력 여부나 실제 금액을 수정하지 않는다.

## 구현 전 판단

표시만 바꾸어 과거 내용이 복원된 것처럼 보이거나 클라이언트에서 선택한 임의 payload를 서버 검증 없이 덮어쓰면 불합격이다. 서버가 보관한 정확한 작성 회차·revision을 읽어 **새 revision**으로 만드는 구조여야 한다. 현재 작성 내용을 자동 보호 저장한다는 사실을 불러오기 버튼 근처에 설명하고, 별도 최종 제출/승인이라는 점도 표시한다.

## 단계별 통과 기준

### 1. 보호 저장과 복원

- 목록에서 버전 선택만으로 현재 입력이 바뀌지 않는다. 명시적 불러오기만 복원을 시작한다.
- 현재 미저장 내용이 있다면 보호 저장 성공을 먼저 확인한다. 실패하면 restore를 호출하지 않고 작성 내용 및 현재 비교를 유지한다.
- 보호 저장 ACK 이후 정확한 새 revision으로 CAS 복원한다. 보호 저장과 복원 사이에 다른 탭이 변경하면409로 중단한다.
- 복원 성공 ACK 이전에 현재 입력을 과거 내용으로 덮어쓰지 않는다. 네트워크 실패·권한/lease 실패·첨부 확인 실패·회차 변경 시 현재 내용이 유지된다. 보호 저장이 이미 성공했다면 그 저장본도 남아야 한다.
- 복원은 현재 revision을 증가시킨다. 기존 history 문서 내용·번호·actor/time을 덮어쓰지 않는다. 과거 버전의 payload와 파일 목록을 새 history로 보존한다.
- 복원 뒤 일반 임시저장 및 재열기가 가능하다. 원장과 제출 요청, 승인 상태는 그대로다.
- 복원 요청 재시도/중복 클릭은 새 버전을 중복 생성하거나 서로 다른 내용을 확정하지 않는다. 진행 중 버튼 및 배경 autosave와의 직렬화가 필요하다.
- 취소/컴포넌트 전환/다른 프로젝트 이동 뒤 늦은 ACK가 새 화면을 덮어쓰지 않는다.

### 2. 서버 소유권·출처·첨부

- tenant·소유자·프로젝트·작성 회차·source revision·current revision·lease fence 모두 서버가 확인한다.
- 다른 작성 회차나 다른 사용자의 source를 경로 조작으로 복원할 수 없다. 이미 제출/폐기된 초안은 정책에 맞게 거절하고 자동 재활성화하지 않는다.
- 새 history의 저장자와 시각은 인증 actor 및 서버 시각으로 기록한다. payload의 actor/time 위조값을 사용하지 않는다. 구형 history에서 기록되지 않은 작성자는 현재 사용자로 소급 추정하지 않는다.
- attachmentRefs와 payload에 포함된 각 문서 참조 모두 실존·허용 소유권/프로젝트 범위를 확인한다. 복원 실패 때문에 현재 파일을 삭제하지 않는다. 현재 접근 불가한 과거 파일을 성공으로 가장하지 않는다.
- 첨부 접근 여부는 검증 시점 기준이며 저장 이후 외부 삭제까지 영구 보장한다고 안내하지 않는다.

### 3. 목록·페이지·구형 초안

- 최근20개 외에 다음 페이지를 읽을 수 있다면 중복/누락 없는 cursor와 현재 generation 범위가 필요하다. 새 저장 중 페이지 조회의 경계도 테스트한다.
- history 없는 현재 초안 fallback은 과거 버전 보존 증거와 구별한다. 이력 보관 시작점 이전 데이터는 복원 가능하다고 표시하지 않는다.
- 0과null, false와미기록, 빈문자열과미기록, 명시적해당없음을 비교·복원·재열기에서 구별한다. 초기화 기본값이 과거 미기록을 새 확정값으로 바꾸지 않는다.

### 4. 연도별 안내·합계 수익률

- 누락된 구체 연도·항목 이름을 안내한다. 입력 기록 없는0은 미확인, 명시적으로 입력한0은 유효값으로 처리한다. false 플래그가 있는 양수를 자동 확정하지 않는다.
- 합계 수익률은 모든 연도의 계약금액과 수익이 확인된 경우에만 계산한다. 분모 합계0은0%로 추정하지 않는다. 다른 구성항목만 누락이면 그 항목 안내와 수익률 계산 조건을 구별한다.
- 단일/다년, 연도 순서 변경, legacy 양수·0·미기록, 부분 입력, 삭제 후 재입력, 기존 합계 불일치를 모두 확인한다.
- Wizard와 관리자표는 동일한 금액/입력기록에 동일한 계산 결과를 표시한다. 표시 계산이 저장금액·inputFlags·입금 계획을 변경하지 않는다.

## 검증 증거와 경계

독립 확인은 실제 컴포넌트 브라우저, BFF 서비스 테스트/직접 함수 실행, 원본/변경후 저장 객체 비교를 사용한다. synthetic callback 브라우저와 실제 BFF 테스트를 구별하고 운영 저장을 했다고 표현하지 않는다. 보호 저장 실패·복원 실패·CAS 경합·다른 회차·첨부 실종 실패는 정상 성공 경로와 별도 테스트해야 한다. 통과하지 않은 단계는 미검증/실패로 남긴다.

## 구현 후 독립 검증 결과

### 연도별 금액 안내: 지정 경로 PASS

실제 Wizard와 승인문서에 같은 합성2개연도 자료를 주고 실행했다. 2027년 미확인0 다섯 항목이 연도·필드명까지 같은 안내로 나타났고, 총수익률은 양쪽 모두 계산 불가였다. 같은2027년0을 명시적으로 입력 확인한 경우 안내가 사라지고 총수익률40.00%가 표시되었다. 표시 전후 원본 payload 동일, JS pageerror0. 두 미입력 화면 PNG를 직접 육안 확인했다. 증거 `/tmp/myscube-annual-guidance-qa/result.json` 및 PNG. 합성 상위금액과 연도합계의 불일치도 fixture에 남아 있으며 자동으로 보정하지 않았다.

### 복원 UI 보호 순서: 지정 경로 PASS

실제 `ProjectEditorWizard.withPreservedDraft`와 `ProjectDraftVersionPanel`을 로컬 API callback에 연결했다. 운영쓰기/실제Portal API end-to-end 증거는 아니다.

- 정상: 미저장값 보호save 시작→ACK revision1→restore(expected1)→과거 내용으로 재열기. 선택만으로 입력은 변하지 않았다. 복원 payload의0과false를 확인했다.
- 보호save 실패: restore 호출0회, 현재 작성값 유지.
- restore 실패: 보호save ACK 후 오류 표시, 현재 작성값 유지. 실패화면 PNG 직접 육안 확인.
- 현재fallback과 동일 내용: 강제 보호save가 실제 호출되어 ACK revision1 후 restore(expected1)가 실행됨.
- 이미 진행 중인 자동저장 경합: 먼저 자동저장 ACK1→복원 직전 새 작성값 보호save ACK2→restore(expected2). 이후1.8초를 기다려도 오래된 autosave가 복원 내용을 덮어쓰지 않았고 추가 save 호출도 없었다.

증거 `/tmp/myscube-restore-ui-qa/result.json`, `queue-result.json`, 네 PNG. 저장자/시각이 버전 선택 목록에 나타남도 확인했다. mock 서버 callback의 메타데이터는 화면 검증용이며 인증 주체 검증은 BFF 테스트 범위다.

### BFF 첨부 경계 검토와 회귀

처음 구현은 history의 attachmentRefs와 payload 문서가 같은kind/path일 때 payload의 metadata 검사를 생략했다. 이때 둘의size/contentType 등이 달라도 검사를 통과할 수 있어 보완 요청했다. 구현 담당자가 둘을 별도로 검사하도록 수정하고 불일치 거절 테스트를 추가했다. 소유 범위는 현재 초안 prefix, 동일 프로젝트 canonical prefix, 기존canonical과 정확히 일치하는legacy참조로 제한한다. 구형 첨부가 현재 허용 범위와 일치하지 않으면 실패시키는 것은 이번 안전 정책이다.

독립 격리 소스에서 draft history helper 및 두 BFF route 테스트146개 통과. 서비스 fake DB와 Storage 테스트는 운영 파일 복원 실행 증거와 구별한다. 임시 검증 미러에 policies 디렉터리를 빠뜨린 첫 실행은 import 단계 실패였고 복사 후 재실행 통과했다.

잔여 경계: 실제 인증된 운영Portal→BFF 복원은 쓰기금지에 따라 미실행. 늦은ACK 다른프로젝트 전환은 코드검토 대상이며 이 독립 브라우저에서 직접 재현하지 않았다. pagination·Storage 실제성 검사와 idempotent/CAS 세부 조건은 담당자의 서비스 테스트 결과와 함께 최종 판단한다. 이 문서는 운영 데이터 전체 복원 가능이나 배포 완료를 의미하지 않는다.
