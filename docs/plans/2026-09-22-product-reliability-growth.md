# MYSCube 제품 품질·업무 전환 측정 설계

## 목적과 완료 기준

구성원이 업무 실패의 이유와 다음 행동을 이해하고, 운영자가 개선 우선순위와 실제 개선 효과를 판단하는 내부 도구를 만든다. 최초 범위는 프로젝트 임시저장·최종 제출·조직장 승인이다. 이후 다른 업무에도 같은 측정 계약을 적용한다.

운영자가 다음 질문에 답할 수 있어야 한다.

- 어떤 업무에서 몇 번 실패했고 몇 명·몇 개 사업이 영향을 받았는가?
- 원인이 확인됐는가, 누가 무엇을 해야 하는가?
- 수정 배포 후 동일 문제가 다시 발생했는가?
- 이용량 변화를 고려해도 실패율이 줄고 완료율이 높아졌는가?

## 현재 확인한 기반과 한계

코드 확인과 2026-09-22의 운영 읽기 전용 조사를 구분한다. Firestore 오류 저장소는 전체 페이지를 확인했으나 환경 분리·중복 제거·성공 분모 검증은 아직 완료하지 않았다. 감소율은 단정하지 않는다.

- `src/app/platform/observability.ts`: Sentry 연동, 전역 오류 포착, 내부 BFF 오류 전송. Sentry에는 환경·릴리스 설정이 있으나 내부 오류 payload에 독립된 필수 환경·릴리스 필드는 없다. 네트워크 실패를 무시하며 응답 성공 여부도 확인하지 않아 수집 유실을 별도로 측정해야 한다.
- `server/bff/app.mjs`: client_error_events 저장, requestId·사용자·화면·fingerprint 기록, BFF 요청별 HTTP 상태·처리 시간·errorCode 로깅.
- 오류 Slack 전송과 worker 존재. 즉시 전송 실패는 failed로 저장하지만 worker는 pending만 읽으므로 자동 재시도 경로를 검증해야 한다.
- `scripts/setup_monitoring_alerts.sh`: Cloud Run 기준 5xx·지연·버전 충돌 경보 설정. 현재 Vercel BFF와 JVM 각각 실제 수집 대상에 포함되는지 확인 필요.
- API 요청 수는 재시도·자동저장·여러 호출을 포함하므로 사용자 업무 시도 수와 같지 않다. 프론트에서 차단된 제출도 API 로그만으로는 알 수 없다.

## 한 사건, 역할에 맞는 두 화면

구성원 화면은 업무 화면 가까이에 원인, 영향, 다음 행동, 문의번호와 처리 상태를 표시한다. 예: “입력 내용은 저장됐지만 승인 요청은 완료되지 않았습니다. 담당자가 확인 중입니다.”라는 문구는 저장 성공 근거가 있을 때만 사용한다. 저장 확인이 없으면 “저장 여부를 확인하지 못했습니다”로 안내한다. 원인 미확정은 조사 중으로 명시한다.

운영 화면은 같은 사건 ID로 발생 추이, 영향 사용자/사업 수, 원인 근거, 담당자, 배포 버전, 재발 여부를 보여준다. 구성원에게는 본인 업무와 권한 내 사업 정보만 노출한다. 스택·인증정보·전체 요청 본문은 공지에 노출하지 않는다. 사람별 오류 순위는 만들지 않는다.

사건 상태: 조사 중 → 원인 확인 → 수정 중 → 배포 후 관찰 → 해결. 관찰 중 재발하면 재발로 표시한다. 예외 로그가 없다는 이유만으로 해결 처리하지 않고, 해당 업무 시도와 성공이 관측되는지 함께 확인한다.

## 공통 이벤트 계약

- 식별: eventId, operationId(한 업무 시도), requestId(한 API 요청), incidentId(묶인 사건), schemaVersion.
- 범위: tenantId, 권한 범위 내 projectId, 가명 사용자 키, 역할, 업무 종류, 화면, 클라이언트/서버 릴리스, 환경.
- 상태: started, succeeded, validation_blocked, system_failed, cancelled, unknown. 네트워크 단절로 저장 결과가 불명확하면 unknown이며 실패로 임의 확정하지 않는다.
- 진단: 안정적인 errorCode, 단계, 원인 분류, 발생·수신 시각, 처리 시간, 재시도 연결 ID.
- 실험: experimentId, variant, assignmentVersion, 노출 시각. 실제 변경 화면에 노출된 경우만 실험 분모에 포함한다.

오류 분류는 시스템 장애, 데이터/버전 불일치, 입력 확인 필요, 권한/인증, 외부 연동, 취소·정상 충돌로 나눈다. 원인 확정 여부는 별도 필드다. 필드가 없는데 필수라고 차단되는 문제는 시스템 문제로 재분류할 수 있어야 한다.

서버 저장 성공은 서버가 확정한다. 클릭이나 HTTP 202만으로 저장 완료를 세지 않는다. 브라우저와 BFF가 같은 실패를 기록해도 operationId로 한 번만 집계하며 API 자체 실패 지표는 별도 유지한다. 동일 eventId 재전송도 중복 집계하지 않는다.

## 지표 정의

| 지표 | 기준 |
| --- | --- |
| 업무 시스템 실패율 | 고유 system_failed 업무 시도 / 같은 범위의 고유 시작 시도. 처리 중·unknown 건수와 확정 비율도 함께 표시 |
| API 실패율 | 대상 API 5xx 응답 / 대상 API 요청. 업무 실패율과 별도 표시 |
| 입력 차단율 | validation_blocked 고유 시도 / 최종 제출 시도. 시스템 실패율과 함께 봐야 우회·은폐를 방지할 수 있음 |
| 제출 완료율 | 기간 내 제출 대상의 고유 제출 성공 수 / 같은 시작 코호트의 대상 수. 추적 기간 명시 |
| 저장 안전성 | 저장 성공 이후 동일 버전을 다시 읽어 확인하지 못한 건수·버전 충돌·복원 실패 |
| 업무 소요 시간 | 시작부터 성공까지 p50/p95. 승인 대기 시간과 실제 입력 시간 분리 |
| 재발률 | 해결/관찰 사건 중 동일 원인으로 재발한 사건 비율 |
| 수집 품질 | 수집 성공률, 최종 수집 시각, 중복률, 결과 미확정 비율. 수집 중단은 오류 0으로 표시하지 않음 |

수동 임시저장과 자동저장은 별도 집계한다. 동일 시도의 내부 재시도와 사용자의 새로운 시도도 분리한다. 날짜는 KST, 구간은 시작 포함/끝 제외로 통일한다. 지표 정의 변경은 버전으로 남기고 이전 결과를 조용히 덮어쓰지 않는다.

## 배포 효과와 A/B 테스트

배포 전후 비교는 동일 업무·역할·프로젝트 유형·측정 버전을 사용하고 이용량, 표본 수, 관측 기간을 함께 표시한다. 단순 전후 비교에는 인과 효과가 아니라 관측 변화라고 표시한다. 성공 분모가 없던 과거 로그는 오류 건수까지만 복원하고 실패율을 만들어내지 않는다.

포트폴리오 예시(가상): 실패율 4% → 1%는 3%p 감소이며 상대 감소율은 75%다. 기간·분모·대상·배포 버전·신뢰구간·제외 기준을 함께 보존해야 재현 가능한 성과가 된다. 대외 공개는 집계·익명화된 결과를 별도로 검토한다.

A/B는 입력 안내 문구·입력 순서 같은 저위험 UX부터 시작한다. 저장 보존·결재 권한·필수 검증 완화는 실험 대상에 넣지 않는다. 사용자 단위 실험은 고정 배정하며, 협업으로 서로 영향을 주는 흐름은 프로젝트/조직 단위 배정을 검토한다. 배정 단위와 분석 단위를 일치시킨다.

실험 시작 전에 가설, 주 지표 하나, 최소 효과 크기, 필요한 표본, 관측 기간, 제외 조건, 중단 조건을 등록한다. 오류율·초안 유실·승인 불일치·문의 증가를 안전 지표로 둔다. 표본 비율 불일치와 중복 노출을 점검한다. 내부 도구의 작은 표본으로 유의미한 결론이 나지 않으면 근거 부족으로 보고하며 전후 비교를 A/B 성과로 부르지 않는다.

## 구현 순서와 검증 관문

1. 운영 로그 읽기 전용 조사: 기간 제한 없이 실제 남아 있는 가장 오래된 자료부터 전체 페이지를 확인한다. 소스별 보관 범위, 서비스/환경, 수집 빈 구간, 중복, 원인 상위 항목을 확인한다. 수집 범위를 명시한 기준 보고서가 산출물이다. 최근 7/28일은 화면 필터이며 조사 범위의 상한이 아니다.
2. 세 가지 핵심 업무의 공통 계측: 시작·결과·배포 버전 연결. 성공/실패/재시도/오프라인/401/409/중복전송에서 저장 결과와 이벤트를 대조한다. 계측 장애가 사용자 저장을 막지 않게 한다.
3. 읽기 중심 운영 화면과 구성원 안내: 동일 사건의 역할별 표현, 원인 미확정 표시, 집계 정의 공개, 마지막 수집 시각. API 실패·수집 단절 시 빈 차트를 0건으로 오인하지 않게 한다.
4. 배포 전후 보고서: 표본과 분모가 충분히 모인 뒤 주간 추이·재발을 평가한다. 운영 기록과 화면 집계를 독립 QA가 대조한다.
5. 실험 등록·노출·결과: 충분한 표본이 예상되는 UX 실험부터 적용한다.

원본 이벤트 → 중복 제거·분류 → 시간 단위 집계 → 권한별 BFF 조회 구조를 사용한다. 화면 열 때 전체 원본 로그를 읽지 않는다. 성공 계측에 필요한 추가 저장 비용과 보존 기간은 운영량 조사 후 산정한다. 새로운 외부 수집 서비스나 개인정보 노출 확대는 별도 승인 범위로 검토한다. 주정산·월결산 처리 로직은 이 설계의 변경 대상이 아니다.

| [Grafana](https://github.com/grafana/grafana) | 76,846 | 시계열·경보 운영 화면 | 운영자용 도구 후보. 구성원 안내 화면은 MYSCube 내에서 제공 |
| [GrowthBook](https://github.com/growthbook/growthbook) | 8,416 | 고정 배정·실험·warehouse 기반 지표 | A/B 엔진 우선 검토 후보. 분석 데이터가 준비된 후 연동 |
| [PostHog](https://github.com/PostHog/posthog) | 39,894 | 제품 분석·퍼널·실험 통합 | 대안 후보. 기존 오류 도구와 중복 수집/비용을 비교 |

라이선스 검토: Collector는 API 기준 Apache-2.0, Grafana는 AGPL-3.0. Sentry·PostHog·GrowthBook은 GitHub API가 NOASSERTION을 반환하므로 일괄 MIT라고 쓰지 않는다. GrowthBook README는 주 코드 MIT와 별도 Enterprise 디렉터리를 구분한다. 채택 시 사용할 버전·디렉터리·SDK·호스팅 조건을 실제 LICENSE와 대조한다.

빅테크·표준 자료의 적용 근거:

- [Google SRE: Monitoring](https://sre.google/workbook/monitoring/) 및 [Alerting on SLOs](https://sre.google/workbook/alerting-on-slos/): 사용자 관점 성공 비율과 오류 예산에 기반한 경보. MYSCube처럼 낮은 트래픽에서는 단일 실패의 큰 백분율을 해석할 때 실제 표본과 영향도를 함께 표시한다.
- [Microsoft Research: Diagnosing Sample Ratio Mismatch](https://www.microsoft.com/en-us/research/articles/diagnosing-sample-ratio-mismatch-in-a-b-testing/): A/B 효과 해석 전 배정 비율·누락 사용자 검증. 표본이 적거나 수집이 깨졌으면 승자를 선언하지 않는다.
- [Microsoft Research: Post-Experiment Stage](https://www.microsoft.com/en-us/research/articles/patterns-of-trustworthy-experimentation-post-experiment-stage): 실험 결과 해석에서 계측 품질과 노출 조건 검증을 포함한다.
- [OpenTelemetry Signals](https://opentelemetry.io/docs/concepts/signals/): 로그·메트릭·트레이스 역할을 분리하고 같은 요청을 연결한다.
- 토스 자료는 앞 절의 API 오류 안내, 사용자 여정 QA, 버전 정합성 자동 검증에 적용한다.

권장 구성은 기존 Firestore/BFF 로그와 Sentry 연동 상태부터 확인해 공통 이벤트를 정비하고, 집계 저장소와 MYSCube 구성원/운영 화면을 연결하는 것이다. 실험 엔진은 GrowthBook을 우선 비교한다. 다섯 제품을 동시에 설치하지 않는다. 대규모 Kafka·별도 OLAP 운영은 현재 확인된 규모만으로 정당화하지 않는다.

첫 개발 산출물은 (1) 소스별 최대 보관 범위 및 수집 상태 표, (2) 원시/중복 제거/운영 환경별 오류 추이, (3) 원인 조사 상태와 담당자·구성원 안내를 연결하는 사건 목록, (4) 성공 분모 수집 계약이다. 이 네 가지가 검증된 뒤 배포 효과와 A/B 결과를 성과 보고서로 제공한다.
