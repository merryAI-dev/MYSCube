## 채점 규칙

- 총 8개 영역, 32개 항목이다. 각 항목은 배점 전부 또는 0점이다. 구현·검증 일부만 있거나 확인하지 못했으면 0점이다.
- 완료 후 배점을 낮추거나 실패 항목을 삭제하지 않는다. 요구 범위가 실제로 바뀌면 사용자에게 이유를 설명하고 새 평가표 버전과 이전 점수를 함께 보존한다.

- 자원·대상·권한 미확정은 구현 결함과 구분하되 점수를 주지 않는다. 점수를 올리려고 승인받지 않은 대상에 연결하지 않는다.
- 이번 범위에 신규 임의 SaaS, 조직 전체 협업 기능, 정산 파이프라인 재작성은 포함하지 않는다. 패키지는 승인된 고정 집합이어도 된다.

## 증거 범위와 다음 순서

S22 실제 호스트 검증은 독립 QA가 관측한 `/tmp/myscube-actual-host-renderer-qa.json`과 IAP 읽기 결과를 사용했다. 이 로컬 경로는 영구 공개 증거가 아니며 비밀값을 포함한 호스트 설정을 공개 저장소에 복사하지 않는다. 후속 점수 변경에는 비식별 보고서 또는 CI/배포 기록을 연결한다. 현재 `toi-completion-status.md`의 과거 운영 미설치 문구를 최신 실증의 반증으로 사용하지 않는다. 문서 갱신 자체에는 점수를 주지 않는다.

첫 구현은 A1/A2/A3/B4/C1/E2를 위한 **기존 제작 경로의 canonical 다중 파일 workspace 전환**이다. 편집 UI만 병렬 추가하면 점수는 오르지 않는다. 실제 저장·Git·remote 실행·대화가 같은 계약을 사용하고 기존 저장본을 보호해야 한다. 구조 개선 후 D3/C4/E1의 실제 업무 대화 품질, E4/G3의 사용성과 지연, D4/H2/H4의 운영 연결을 순서대로 검증한다. 해당 순서는 항목 통과를 예약하지 않는다.

매 증분은 독립 QA가 변경 항목, 새로운 관측, 기존 항목 회귀 여부와 점수를 기록한다. 실제 모델·운영 사용자 경로를 fixture로 대체하거나 미승인 연결을 완료로 간주하지 않는다.
