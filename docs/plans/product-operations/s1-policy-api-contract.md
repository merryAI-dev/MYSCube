# S1 — TOI 원칙을 적용한 정책·API 계약
## 목표·진입 조건
S0에서 임시저장·제출·승인의 실제 호출 경로를 확인한다. 화면 종류와 관계없이 같은 정책·오류 의미를 사용한다.

## 작업
1. 현재 BFF 라우트와 스키마에서 업무 API 등록 목록을 만든다. operationKey, method, route, 입력/응답 스키마, 스키마 버전, 권한, 부작용, 멱등성·동시수정 규칙을 정의한다.
2. 오류 계약에 안정적 code, 사용자 안내, 확인할 필드, 재시도 가능 여부, requestId, 원인 확정 상태를 정의한다. 내부 stack과 구성원 안내는 분리한다.
3. 한 업무 시도 operationId와 여러 네트워크 요청 requestId의 연결을 정의한다. 재전송·새 시도 기준을 확정한다.
4. 프론트 releaseSha·BFF releaseSha·JVM revision과 양식 schemaVersion·업무 draftVersion을 서로 다른 필드로 관리한다.
5. 기존 BFF→JVM의 정책 소유 관계를 문서화한다. 중복 검증 규칙을 새 화면에 복제하지 않는다.

## 실제 경로·산출물
ProjectEditorWizard/portal-store → API client → BFF projects 및 draft 라우트 → 저장 응답.
관측 계약, API 등록 명세, 사용자 오류 문구 표, 호환성 테스트를 산출한다. TOI의 프록시 개념은 기존 BFF에 적용하며 새 범용 프록시를 추가하지 않는다.

## QA·완료 조건
동일 요청이 실무자/관리자에서 같은 code·필드 의미를 갖는다. 401/403/409, 필수 누락, 저장 실패, 결과 미확정, 옛 양식 요청을 검증한다. 브라우저를 우회한 요청에도 서버 권한·정책이 적용된다. 인증정보·개인정보가 일반 안내에 노출되지 않는다.
기존 소비자가 변경 응답을 읽을 수 있고, 원인 미확정과 확정을 구분하며, 임시저장이 최종 제출 검증에 잘못 막히지 않으면 통과한다.

## 중단·복구
기존 API 의미 변경이 필요하면 호환 버전을 먼저 추가한다. 운영 자료를 자동 변환해 오류를 숨기지 않는다. 새 계약의 비활성화가 기존 저장 경로를 끊지 않아야 한다.
