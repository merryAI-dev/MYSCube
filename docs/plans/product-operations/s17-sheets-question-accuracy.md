# S17 — Sheets 질의와 업무 질문의 정확도

2026-09-23. **설계·논문 검토 및 오프라인 입금 사본→지표 조회 구현 완료. 실제 Sheets API 수집·실제 모델 평가는 미완료.** [구현·검증 결과](s17-sheets-implementation.md)를 함께 읽는다. S16의 업무 정의 → 검증된 계획 → 사본 계산 구조를 확장한다. 운영 데이터·권한·주정산/월결산 파이프라인은 변경하지 않았다. Jev·벡터 DB는 도입하지 않는다.

## 목표 제품 동작

“이번 주 입금액 총액이 얼마야?”를 지원하도록 설계한다. 확인 가능한 자료를 계산해 답한다. 질문마다 별도 endpoint를 만들지 않는다. Sheets 수집 adapter와 재사용 가능한 입금 정의를 추가하면 기간·사업·조직·실적/예정·비교·그룹을 조합한다. 정의되지 않은 조합은 지원한다고 가정하지 않는다.

1. 권한 내 catalog와 대화에서 이미 확정된 기준을 먼저 찾는다.
2. 금액에 영향을 주는 기준이 불명확하면 구체적으로 한 가지씩 확인한다.
3. 확인된 기준으로 서버가 조회 계획을 검증하고 사본에서 계산한다.
4. 금액과 함께 기간, 집계 기준, 확인한 사업 범위, 누락, 자료 확인 시각을 표시한다.
5. “그중 CIC4만”, “지난주와 비교해줘”, “이걸 표로 보여줘”는 확정된 의미를 이어 사용한다. 비교 가능한 사본·관계가 없으면 필요한 자료를 안내한다.

예시 대화이며 실제 데이터 조회 결과가 아니다.

> 사용자: 이번 주 입금액 총액이 얼마야?
>
> 도우미: 실제 들어온 금액과 앞으로 들어올 예정 금액 중 어느 쪽을 볼까요?
>
> 사용자: 실제 입금. 고객에게 받은 돈만, 부가세 포함해서.
>
> 도우미: 기간은 사업비 시트의 이번 정산주로 볼까요, 월요일부터 일요일까지로 볼까요?
>
> 사용자: 정산주로.
>
> 도우미: [서버 계산 금액] · 고객 입금, 부가세 포함 · [정산주 시작일~종료일] · [확인 사업 수/대상 사업 수] · [자료 확인 시각]
>
> 사용자: 그중 CIC4만 보여줘.
>
> 도우미: 같은 기간과 입금 기준으로 CIC4를 조회한다. 조직 관계가 검증된 경우에만 실행한다.

확정된 회사 표준 지표가 있으면 매번 위 질문을 반복하지 않고 적용 기준을 표시한다. 다만 이번 검토가 회사 입금 정책을 새로 확정한 것은 아니다. 사용자별 대화 선택을 전사 기본값으로 승격하지 않는다. 사용자가 명시적으로 기준을 바꾸면 이전 기준을 대체한다. 권한은 매번 다시 검사한다.

## 코드에서 확인한 중요한 차이

| 구분 | 현재 근거 | 조회 설계에 미치는 영향 |
| --- | --- | --- |
| 입금 | `policies/cashflow-policy.json`의 IN 7개 라인: 내부 선입금 3종, 매출, 매출부가세, 팀지원금, 이자 | 전체 IN 합계를 외부 고객 수금이라고 부르지 않는다. 고객 수금·전체 통장 유입·외부 순유입은 별도 정의다. |
| 실적/예정 | `cashflow-coordinates.mjs`의 Actual 38:44행/합계45행, Projection 15:21행/합계22행 | 두 모드를 혼합하지 않는다. 원천행과 합계행을 중복 합산하지 않는다. |
| 이번 주 | `cashflow-week-core.mjs`: 월별 5개 정산 슬롯, 달력 6주차는 5주차에 포함 | 정산주와 월~일 달력주는 다를 수 있다. 날짜별 자료 없이 주차 금액을 일수 비율로 나누지 않는다. |
| 값의 상태 | `cashflow-sheet-snapshot.mjs`: EMPTY/ZERO/VALUE/INVALID/ERROR, Actual '-'는 ZERO, Projection '-'는 EMPTY | 빈칸을 0으로 만들지 않는다. 오류·누락을 숨긴 전사 총액을 내지 않는다. |
| Sheets client | `google-sheets.mjs`: FORMATTED_VALUE 읽기, 공용 쓰기 scope 및 Firebase 자격증명 fallback | 이 모듈을 그대로 import했다고 읽기 전용 격리가 확보되는 것이 아니다. 별도 인증/자원 경계 검토가 필요하다. |
| 현재 분석 라우터 | `semantic-catalog.mjs`, `semantic-query.mjs`, `conversation-agent.mjs` | 주정산 상태와 오프라인 입금 사본 정의가 연결되어 있다. 실제 Sheets API에 연결된 것으로 설명하면 안 된다. |

고정 좌표 계약은 그대로 사용한다. A1:BT60, 주별 E:BL 60칸, 프로젝트당 단일 weeklyYear, 연간 C:D/BM:BR, 행 인덱스 LINE_ROWS가 기준이다. `weekOrdinal === -1`은 읽지 않는다. 다른 양식은 `CashflowTemplateMismatchError`로 거부한다. 명칭 추론이나 옛 자료 fallback으로 적응하지 않는다.

특히 현재 정책의 `VAT_REFUND` 분류는 `SALES_VAT_IN`으로 연결된다. 따라서 행 이름만 보고 `SALES_IN + SALES_VAT_IN`을 정확한 “고객에게 받은 돈”으로 확정할 수 없다. 실제 해당 시트에 환급이 포함됐다는 증거는 아니지만, 구분 가능성을 먼저 검증해야 한다는 근거다. 집계 블록만으로 상대방/거래 성격을 구분할 수 없으면 “시트의 매출·매출부가세 입금 합계”로 정확히 설명하고, 고객 수금만 필요하면 검증된 거래별 자료가 추가로 필요하다. 질문을 명확히 했다고 자료의 해상도가 높아지는 것은 아니다.

## Sheets 연결 구조

`허용된 원본 목록 → 독립 읽기 전용 수집 → 좌표/셀 상태 검증 → 버전 고정 사본 → 업무 정의와 계획 검증 → 서버 계산 → evidence → 답변/HTML`

- 사용자가 질문할 때마다 운영 sync나 JVM을 호출하지 않는다. 검증된 기존 사본이 충분하면 그것을 사용하고, 부족하면 독립 collector를 둔다. 수집 실패 시 운영 BFF 조회로 우회하지 않는다.
- 새 collector는 허용된 spreadsheet/sheet 목록과 읽기 전용 권한만 사용한다. AI가 spreadsheet ID, OAuth scope, 원본 URL을 임의 선택하지 않는다. 계정·프로젝트·quota 공유 여부를 확인한 후 활성화한다.
- [Sheets values.batchGet](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets.values/batchGet)은 한 spreadsheet의 여러 범위를 묶는다. 여러 spreadsheet 전체에 대한 원자적 스냅샷은 아니다. 병렬 수집에도 한도를 둔다.
- 표시 문자열은 승인된 parser로 해석하고 원문과 상태를 보존한다. [spreadsheets.get](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets/get)의 ranges/field mask로 필요한 오류·셀 메타데이터를 조회하는 방식을 검토한다. 렌더 옵션이나 수식 원문을 바꿔 기존 의미를 재해석하지 않는다. Sheets가 계산한 고정 블록을 읽으며 SUMIFS 원천 로직을 복제하지 않는다.
- 사본에는 source ID, 고정 셀 좌표, mode, weeklyYear, yearMonth/weekNo, currency, cell state, 원문, 값, 수집시각, revision/hash를 보존한다. 결과에는 정의 ID/version/hash, 계획, 대상/성공/실패 사업 수, 사본 시각 범위를 연결한다.
- 정수 원 단위 계산은 정확 연산을 사용한다. JS Number로 합계 정확성을 가정하지 않고, 실행기/직렬화 경계에서 큰 정수와 음수 정정값을 검증한다. 혼합 통화는 환산 정책 없이 합산하지 않는다.
- 전사 총액의 분모는 원래 대상 목록이다. 성공한 시트만으로 분모를 줄이지 않는다. 원본 중복 연결은 중복 집계하지 않되 여러 사업이 한 시트를 공유하는 경우 처리 정책을 확인한다.
- 일부 시트를 읽지 못하면 “확인된 N개 사업 부분합”으로 구분한다. 빈 결과, 미연결, 실제 0원은 서로 다른 결과다. 수집시각이 다른 시트의 합계를 같은 순간의 잔액이라고 표현하지 않는다.
- 기존 HTML evidence binding을 재사용한다. 모델이 숫자를 재작성하지 않고 서버 계산 결과를 연결한다. 답변·표·저장 후 재열기에서 동일한 정의와 사본 버전을 확인한다.

## 논문 검토와 적용 판단

Autoregressive는 앞서 생성한 토큰을 조건으로 다음 토큰을 만드는 방식이다. 그 자체가 질문 이해나 계산 정확성을 보장하는 기법은 아니다. 이번에는 그 위에 붙는 제약·분해·실행 피드백·명확화 방식을 검토했다. 아래는 원문 방법/한계에 근거한 MYSCube 적용 판단이며 논문의 성능 수치를 우리 제품 성능으로 전용하지 않는다.

| 연구 | 확인한 방법과 한계 | MYSCube 적용 결정 |
| --- | --- | --- |
| [PICARD, EMNLP 2021](https://aclanthology.org/2021.emnlp-main.779/) · [논문 PDF](https://aclanthology.org/2021.emnlp-main.779.pdf) | 생성 중 token 후보를 incremental parsing으로 검사한다. 문법·스키마 제약은 업무 의미의 정답 보장이 아니다. | 현재 `html-completion.mjs`의 hosted function-calling API에는 token/logit 제어 경로가 없어 직접 구현했다고 할 수 없다. **typed plan + 허용 정의 + 서버 compiler** 원칙을 유지한다. 모델 교체/자체 decoding 도입은 범위 밖이다. |
| [DIN-SQL, 2023](https://arxiv.org/html/2304.11015) §4 | schema linking, 난도 분류/분해, 생성, 보정으로 나눈다. | 지표·기간·대상·조건·자료 단위를 구분하는 해석 계약을 채택한다. 매 질문에 여러 모델 호출을 의무화하지 않고 단순 요청은 한 계획으로 처리한다. |
| [Execution-Guided Decoding, 2018](https://arxiv.org/html/1807.03100) | 부분 실행의 오류로 후보를 제거한다. 실험 방식에는 empty result 제거도 포함된다. | 실행 검증 피드백을 참고하되 **0건을 오답으로 제거하는 규칙은 채택하지 않는다.** 금지된 범위/권한은 재시도로 우회하지 않는다. 유효 SQL이 의도까지 맞는 것은 아니다. |
| [AmbiQT, EMNLP 2023](https://aclanthology.org/2023.emnlp-main.436/) | 한 질문의 복수 의미를 다룬다. 토큰 후보가 다양하다고 의미가 다양해지는 것은 아니다. | 실적/예정, 고객 수금/통장 유입, 정산주/달력주처럼 결과를 바꾸는 해석을 드러내고 확인한다. 가장 높은 점수의 해석을 조용히 채택하지 않는다. |
| [Self-Consistency, ICLR 2023](https://arxiv.org/html/2203.11171) | 여러 추론 경로를 샘플링하고 최종 답을 집계한다. | 어려운 사례의 **오프라인 비교 실험 후보**로 제한한다. 다수결이 같은 잘못된 정의에 동의할 수 있고 비용·지연이 늘어난다. 운영 기본값으로 다중 호출하지 않는다. |
| [Large Language Models Cannot Self-Correct Reasoning Yet](https://arxiv.org/html/2310.01798) | 연구가 평가한 모델/과제에서 외부 피드백 없는 자체 수정이 악화되는 경우를 확인했다. 모든 최신 모델에 대한 불가능 정리는 아니다. | “다시 생각해” 루프를 신뢰하지 않는다. 서버 검증의 구체적 실패만 보정 근거로 사용한다. 모델 confidence는 데이터 근거가 아니다. |
| [BIRD-INTERACT](https://arxiv.org/html/2510.05318) | 질의 명확화와 환경 탐색을 포함한 상호작용 평가. 정답 SQL 조각으로 확인 답변을 고정하고 필요성/충분성을 검토한다. | 사용자 답변 후 정확한 계획에 도달하는지 평가한다. DB 구조 문제를 사용자에게 묻지 않고 자료/정의에서 먼저 확인한다. 논문의 쓰기 작업은 도입하지 않는다. |

기존 S15/S16의 LangGraph·Dify/Graphon·WrenAI·MetricFlow 고정 SHA 소스 검토와 함께 적용한다. 이번 검토를 이 논문들의 전체 저장소 실행/재현 또는 실제 모델 실험으로 표현하지 않는다.

## 서버가 결정할 것과 사용자에게 물을 것

| 상황 | 처리 |
| --- | --- |
| 업무 의미가 두 가지이고 대화/승인 정의로 결정할 수 없음 | 비개발자용 선택 질문. 예: “고객에게 받은 금액만 볼까요, 내부 선입금을 포함한 통장 유입 전체를 볼까요?” |
| 이미 확정된 기준으로 “그중”, “지난주도” | 기준을 이어 사용하되 실제 기간과 변경 조건을 표시 |
| 스키마 이름·고정 좌표·등록 지표의 연결 문제 | catalog/계약에서 해결. 사용자가 SQL이나 필드명을 설명하게 하지 않음 |
| 정의 없는 계산/관계 | 계산 불가 이유와 현재 가능한 범위 안내. 근거 없는 식을 모델이 만들지 않음 |
| 계획 형식 오류 | 검증 코드/실패 필드만 근거로 제한된 보정 검토. 권한·대상·기간 확대 금지 |
| 403/429/timeout, 사본 누락·오래됨 | 자료 오류로 표시. 의도 질문이나 모델 재추론으로 해결한 척하지 않음 |

최초 단계에서는 기존 strict plan 검증과 clarification을 재사용한다. 자동 계획 보정은 아직 구현하지 않았다. 도입 시 한 번의 보정만 허용하는 후보안을 기존 전체 시간/호출 예산 안에서 평가하고, 회복률과 새 오류 발생률이 개선될 때만 켠다.

## 구현 단계와 통과 조건

1. **의미/자료 경로:** 입금 지표의 포함 라인·세금·내부거래·주차·통화·대상 범위를 운영 담당자와 확인한다. source/snapshot/plan/evidence 계약을 고정한다. 현재는 소스 검토와 [독립 QA gate](s17-sheets-query-qa-gates.md) 작성까지 완료했다.
2. **오프라인 구현:** 기존 좌표/상태 parser를 사용하는 독립 adapter, 입금 항목 정의, coverage 검사, typed plan/서버 집계/evidence 연결을 구현했다. 실제 parser·DuckDB·Firestore emulator·브라우저 검증 결과는 [구현 기록](s17-sheets-implementation.md)을 따른다. 회사의 고객 수금 정책 확정 또는 운영 데이터 검증을 뜻하지 않는다.
3. **읽기 전용 연결:** 승인된 접근/비용/수집 한도 안에서 지정 시트만 수집한다. 원본 셀과 사본·API·HTML을 대조한다. 사업별 실패, 403/429, 자격증명 회수, 운영 서비스 부하 분리를 확인한다. 아직 미실행이다.
4. **실제 모델 평가:** 아래 평가를 모델 버전·프롬프트 버전·정의 버전·사본 버전을 고정해 실행한다. fixture planner 통과를 질문 이해 정확도라고 발표하지 않는다.
5. **운영 게이트:** 지연/호출 비용·격리·사용자 흐름·저장 후 재조회까지 통과한 뒤 별도 활성화한다. 정산 pipeline을 바꾸지 않고도 동작해야 한다.

## 정확도 평가 계획

동일한 고정 자료로 A=현재 라우터, B=해석 분해+명확화+검증 피드백, C=B+어려운 사례의 제한된 복수 후보를 비교한다. C는 비용이 승인된 평가에서만 실행한다. 학습/예시용 질문과 홀드아웃 질문을 분리하고, 모델에게 정답을 만들게 하지 않는다. 정답 계획·필요한 확인 답변·금액은 독립 검토한다.

| 사례 묶음 | 기대 동작 |
| --- | --- |
| 실제 입금 vs 예정 입금 | mode가 맞고 모호할 때만 확인 |
| 고객 수금 vs 내부 선입금 포함 | 검토된 라인 집합 적용, 세금 포함 여부 보존 |
| 이번 주·지난주·월/연도 경계·6주 달 | 서버 시간대와 자료가 지원하는 기간 단위 적용 |
| “그중 CIC4”, “아니 부가세 빼고” | 기존 기준 보존 + 명시적 수정, 조직 관계 없으면 안내 |
| 0원·'-'·EMPTY·수식 오류·음수 | 상태/부호 보존, 미확인을 0으로 처리하지 않음 |
| 일부 사업 수집 실패·복수통화·중복 원본 | 완전 총액 단정 금지, 분모와 누락 표시 |
| 우연히 숫자가 같은 잘못된 계획 | 기간·정의·대상이 틀리면 실패 |
| 빈 결과·금액 없는 정상 업무 | 재시도로 양수 결과를 만들어내지 않음 |
| 권한 회수·원본 셀의 지시문·이전 대화의 미허용 자료 | 조회/HTML 노출 차단, 자료를 시스템 지시로 취급하지 않음 |

측정값은 의미별 정확도(mode/기간/지표/모집단), 완전한 질문 처리 성공률, 필요한 질문 누락률, 불필요한 질문률, 다중 대화 성공률, 수치·근거 일치율, 누락 감지율, 무허용 실행/쓰기 횟수, end-to-end p50/p95, 호출 수/비용이다. 테스트셋 크기와 분모를 함께 공개하고 고정 회귀셋의 critical 오류 0건을 필수 게이트로 둔다. 소규모 표본의 100%를 운영 보장으로 표현하지 않는다. 개선율은 실제 실험 전에는 제시하지 않는다.

설계 문서 작성 단계에서는 브라우저 QA를 요구하지 않았다. 이어진 오프라인 기능 구현에서는 브라우저 저장·복원까지 검증했다. 운영 연결 단계의 실제 Sheets 원본 대조와 모델 평가 게이트는 아직 남아 있다.
