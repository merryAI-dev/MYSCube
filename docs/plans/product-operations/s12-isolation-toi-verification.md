## 격리 후에도 가능한 기능

오류 질의: 운영 로그의 비동기 사본 + 요청 상관관계 + 실패 버전 SHA의 GitHub 코드로 답한다. 실시간 운영 API 접근은 필요하지 않다. 다만 수집이 늦거나 SHA가 없으면 그 한계를 표시하고 원인을 확정하지 않는다. 자동 운영 수정은 제공하지 않는다.

가변 어드민: 화면 생성은 API 스키마와 데이터 표시 계약을 입력으로 한다. API 뒤의 데이터가 운영 DB인지 분석 사본인지는 화면 가변성과 독립적이다. 사용자별 페이지 버전·복원은 독립 저장소에 기록한다. 현재 구현의 위젯 구성 방식과 TOI의 자유로운 React 생성은 구분해야 한다.

## 장애 경계

- 기존 BFF에서 신규 route/import/수집 미들웨어 제거. 기존 저장 응답이 분석 저장을 기다리지 않음.
- 공통 업무 API client·등록/수정 화면·layout의 관측 큐 연결 제거.
- 신규 서비스는 운영 DB/JVM 자격증명·주소를 받으면 시작 거부. 독립 프로젝트와 실제 IAM 거부를 모두 검증해야 함.
- 신규 서비스는 분석 사본만 읽음. 자료 없음/지연을 운영 API 재조회로 보완하지 않음.
- 권한 사본이 5분 넘게 갱신되지 않으면 새 도구 접근 거부. 실시간 권한 회수와 같은 보장은 아니므로 권한 전달/만료 체계를 운영 전 검증해야 함.
- 별도 Gemini 프로젝트 필요. API 키만 분리하면 할당량이 분리되지 않음: https://ai.google.dev/gemini-api/docs/rate-limits
- Cloud Run max-instances는 전체 비용의 절대 상한이 아님. 예산·호출량·로그량 제한과 실제 계정 구성을 함께 검증: https://docs.cloud.google.com/run/docs/configuring/max-instances
- 업무 배포 workflow에서 Workbench 배포/검증/AI 키 주입 제거. 독립 배포 실패가 업무 배포를 막지 않아야 함.

## 판정 기준

1. 코드 경계: 기존 업무에 신규 import·수집 대기·API 호출 없음. 경계 위반을 재삽입하면 테스트 실패.
2. 기능: 독립 저장소의 로그·버전 근거 조회, 위젯 저장/복원, 자료 없음/지연에서 fail closed. 운영 데이터 원본 불변.
3. 화면: 독립 앱에서 변경·오류·마지막 정상 화면·사용자 간 분리·CPU 작업 중 기존 앱 조작 확인.
4. 인프라: 운영 IAM·JVM 접근 거부, 모델 quota 프로젝트 실제 구분, 독립 배포·롤백.
5. 장애 주입: 신규 CPU/메모리/DB/모델 장애와 자료 공급 단절에도 기존 업무 조회·임시저장·제출·승인이 정상.

현재 1의 코드/설정 경계 테스트16개와 위반 재삽입 시 실패를 확인했다. 이는 3~5의 프로덕션 격리 증명이 아니다. 별도 유료 리소스는 아직 생성하지 않았으며 월 예산과 운영 경계 확정이 필요하다. 자료 공급·독립 인증·전용 frontend·운영 IAM이 연결되지 않은 상태를 제품 완료로 보고하지 않는다.

## 이번 검증에서 발견한 문제와 보완

- 테스트에서 서로 다른 projectId로 공용 Firebase 초기화 함수를 두 번 호출했지만 같은 기본 앱을 재사용했다. 이 결과는 별도 저장소의 증거로 인정하지 않는다. 테스트를 독립 Firestore 클라이언트로 바꾸고 실제 client.projectId와 객체 비동일 여부를 검사한다. 신규 runtime도 전달된 DB의 projectId가 격리 설정과 다르면 시작을 거부한다. 운영 Firebase 초기화 함수는 변경하지 않는다.
- 사본 누락/만료 오류가 기존 분류기를 통과하며 구체적인 코드가 사라졌다. 신규 사본 읽기의 두 오류만 보존하도록 고쳐 자료 없음과 오래된 자료를 구분한다.
- 단위 테스트 28개 통과: 격리 경계16, 미리보기 교체 상태3, 페이지 계약1, AI 도구8. 기존 업무 앱 production build 통과(기존 대형 chunk 경고 존재). 이 결과는 독립 frontend의 브라우저 검증을 의미하지 않는다.

## TOI 수준까지 남은 구현 순서

1. 독립 인증과 권한 사본 전달, 운영 응답과 분리된 비동기 로그/데이터 공급. 사본의 수집 시각·원본 버전·누락 범위를 응답과 화면에 표시한다. 공급 중단 시 분석만 제한한다.
2. 독립 frontend와 배포: 운영 AXR 메뉴에는 외부 진입 링크만 둔다. 분석 앱은 운영 Firebase나 업무 API client를 가져오지 않는다.
3. 자유로운 React 생성이 필요하면 허용 API 스키마, 가상 파일 시스템, esbuild-wasm worker, 사전 준비한 패키지 조합과 import map을 추가한다. 현재 위젯 구성 기능을 이것과 같은 것으로 표현하지 않는다.
4. 새 iframe의 준비 완료와 첫 렌더 성공을 확인한 뒤 교체한다. 실패·시간 초과는 마지막 정상 화면을 유지한다. iframe sandbox는 브라우저 CPU 자원의 절대 격리를 보장하지 않으므로 무한 실행/메모리 부하와 기존 업무 탭 반응성도 별도로 시험한다.
5. 전용 배포에서 cold/warm 및 모바일 p50/p95를 측정한다. AI 생성, 데이터 조회, 빌드, 첫 렌더를 따로 기록한다. 토스의1.3초나 이전 MYSCube 미리보기 측정값을 독립 앱의 제품 성능으로 대신 쓰지 않는다.

로그 질의 통합 테스트는 GitHub 조회 함수를 주입하여 정확한 SHA 전달을 검증한다. 실제 비공개 GitHub 인증·코드 다운로드·새 프로젝트의 실제 모델 호출까지 통과했다는 의미는 아니다. 이런 외부 연동과 운영 인프라 장애 주입이 끝나기 전에는 운영 활성화하지 않는다.

## 독립 QA 재검증 결과

2026-09-22, 실제 다른 projectId의 Firestore emulator 클라이언트로 통합 테스트 **17/17 통과** (`isolated-capabilities`6 + `product-operations`11). 각 사례 전에 DB 프로젝트와 객체 분리를 확인했다. 로그: `/tmp/myscube-isolated-capabilities-independent.log`.

- 복사 로그에서 연관된 실패 SHA를 코드 조회 함수에 전달한다. 버전을 모르면 최신 main으로 대신하지 않는다.
- 위젯 추가 저장 후 다시 읽어 같은 구성을 확인하고, 과거 버전을 새 버전으로 복원한다. 별도 업무 DB의 fixture 값은 변하지 않는다.
- 사본 없음/만료에 구체적인 오류를 반환하고 외부 fetch는 호출하지 않는다. 기록된 0원은 유효한 값으로 읽는다.
- 오래된 권한 사본은 조회 전에 차단한다.

판정: **기능과 격리의 양립은 로컬 실행으로 확인. 프로덕션 완전 격리 및 TOI와 동일한 자유 코드 생성은 미완료.** 주정산/월결산 및 JVM 코드는 변경하지 않았으며 이번 격리 작업은 배포하지 않았다.
