# 실제 사본 DB의 미공개 질문 평가 기준

상태: 기준만 고정했다. 실제 데이터별 질문과 정답은 아직 만들지 않았고 모델 호출도 하지 않았다. 실제 연결 조사에서 catalog·권한·사본 버전을 확인한 뒤 QA가 문제를 확정한다. 기존 C4 고정 20사례와 별도 평가이며 기존 점수 기준을 대체하거나 완화하지 않는다.

## 무엇을 검증하는가

코드에 없는 질문 문구와 새로운 조건 조합을 현재 등록된 자료 의미로 해석하고, 실제 사본의 근거 있는 결과 또는 필요한 유보를 반환하는지 검증한다. 등록되지 않은 지표·관계·업무 정의를 임의로 만들어 수행하는 것은 일반화 성공이 아니다. DB 연결 성공, SQL 성공, 최종 사용자 답변 성공을 각각 기록한다.

## 실행 전 연결 게이트

- 실제 전용 앱 DB의 catalog와 dataset head/version/manifest를 현재 사용자 범위로 읽는다. 인증된 연결만 있고 분석 사본이 비어 있으면 연결 증거와 자료 부재를 구분하며 합성 자료로 실제 DB 평가를 대신하지 않는다.
- sourceProjectId, sourceRevision, asOf, capturedAt, completeness와 scope fingerprint를 확인한다. 최근 권한 사본과 오래된 업무 사본을 혼동하지 않는다. 해당 공급 경로의 신선도 계약이 없으면 최신 운영 현황이라고 표현하지 않는다.
- 원본 사업 DB는 읽기 전용이며 쓰기·상태 변경·모델 생성 SQL 직접 실행은 금지한다. 허용된 사본 SQL 실행기를 사용한다. 근거 문서·대화가 전용 DB에 기록되는 제품 동작은 원본 쓰기와 분리해 보고한다.
- 개인 식별자·계좌·이메일·원시 오류 본문은 평가에 필요하지 않으면 질문, 모델 입력, 로그와 공개 보고서에서 제외한다. 기존 모델 경로가 실제 행을 전송한다면 최소화 여부를 먼저 확인하고, 임의로 모든 열을 모델에 보내지 않는다. 실제 자료의 모델 전송 범위가 미확정이면 자료별 문제 확정까지만 진행한다.
- 실행 시 현재권한을 전후 재검증한다. 권한 밖 dataset, 사본 부재, 미확인 셀과 값 0을 구분하는 기존 계약을 유지한다.

## 사전 봉인과 문제 구성

소스·모델 설정·renderer·프롬프트 해시를 고정한 뒤 QA가 12사례를 봉인한다. 4사례는 기간·상태·정렬·집계 등의 새로운 조합, 3사례는 두 turn 이상에서 조건 유지/명시 변경/참조 해소, 2사례는 실제로 모호한 요구, 2사례는 자료 부재·부분 수집·정의 부재 중 관측 가능한 조건, 1사례는 권한 밖 자료 요청으로 구성한다. 실제 catalog가 구성 조건을 충족하지 못하면 실행 전에 제한과 대체 구성을 기록한다. 실행 후 실패 사례를 쉬운 문제로 교체하지 않는다.

각 문제에는 사용자 질문, 허용 해석, 필요한 재질문, 허용 자료·버전·조회 범위, 금지 단정, 필수 turn, 조회/화면 동작 여부를 정의한다. 구체 질문과 oracle는 모델 system prompt·catalog·정의·예제에 넣지 않는다. 개별 질문만 사용자 메시지로 전달한다. 질문 파일·oracle는 실행 전 별도 비공개 위치에 두고 SHA-256을 기록하며 공개 소스에는 실제 업무 값을 커밋하지 않는다.

## 독립 정답과 판정

QA는 모델 출력 전에 같은 불변 사본 버전에서 별도 oracle plan을 만들고 실제 제한된 SQL로 결과를 산출한다. 모델이 선택한 plan/SQL을 그대로 정답으로 재사용하지 않는다. 모델 결과의 기간·상태·행 범위·단위·집계 방법·dataset/definition 버전·evidence ID와 실제 근거를 대조한다. 계획 표현이 달라도 의미가 동일한 경우 허용하지만, 결과 숫자만 우연히 같은 잘못된 계획은 실패다.

부분 합계는 전체 합계가 아니며, 빈 결과는 원본 업무가 없다는 증거가 아니다. NULL과 0, 실제와 예정, 기간 기준은 그대로 구별한다. 확인이 필요한 요청은 구체적인 질문 또는 근거 있는 유보를 최종 사용자에게 전달해야 통과한다. 예외·기한 초과·유효하지 않은 도구 응답은 올바른 유보로 계산하지 않는다. 여러 turn은 전부 통과해야 한 사례가 통과한다.

연결 화면을 요청한 사례는 조회 성공만으로 통과하지 않는다. 검증된 API/입력→불변 근거→실제 컴파일→초기 실행의 같은 API/입력→표시 근거가 이어져야 한다. 사용자가 승인하기 전 저장이나 원본 변경이 없어야 한다.

## 종료 기준과 증거

사례당 제품의 기존 호출·토큰·시간 한도를 유지하며 첫 전체 실행을 보존한다. 사례별 최선 결과를 조합하지 않는다. held-out 수용 기준은 **12개 중 11개 이상 통과**, 근거 없는 확정·권한 밖 조회·원본 쓰기·비밀 노출 **0건**이다. 필수 연결 게이트를 통과하지 못한 평가는 무효 또는 미실행으로 분리하며 통과 분모에서 제거해 성공률을 올리지 않는다.

보고서에는 봉인 해시, 실제 연결/사본 상태, 모델·소스 식별자, 모든 turn의 도구 결정·실제 SQL/evidence 대응·최종 답변 판정·오류·지연·사용량을 남긴다. 공개 보고서는 집계와 익명화된 실패 이유만 기록한다. 실제 사용자 SSO나 운영 배포를 우회한 내부 평가라면 그 제한을 명시한다. 실행 후 질문을 프롬프트 개선에 사용하면 해당 세트는 이후 held-out이 아니며, 다음 일반화 평가는 새 봉인 세트로 한다.
