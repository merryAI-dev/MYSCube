# S2 — 신뢰할 수 있는 계측과 집계
## 목표·진입 조건
S1 계약 확정 후 임시저장·제출·승인의 전체 시도와 성공/실패를 연결한다.

## 작업
1. 사용자 명시적 저장과 자동저장을 구분해 started와 결과 이벤트를 남긴다. 브라우저 검증 차단도 관측한다.
2. 서버 저장 확정으로 succeeded를 기록한다. 202·클릭·토스트만으로 완료를 세지 않는다. 타임아웃 후 저장됐을 수 있으면 unknown으로 두고 확인 절차로 해소한다.
3. eventId 멱등성, operationId 중복 제거, 배포 버전·환경을 적용한다.
4. 원본 이벤트 → 버전 있는 정규화 → 일/시간 집계 → BFF 읽기 모델을 만든다. 오류율의 분자·분모는 같은 환경·업무·코호트로 맞춘다.
5. 수집 실패·지연·중복·확정되지 않은 시도도 측정한다. 오류 전송 실패가 업무 저장 실패로 전파되지 않게 한다.
6. 로그 양과 조회 패턴을 확인한 뒤 저장소·보존 기간을 선정한다. 기존 Firestore/Sentry를 우선 조사하며 Collector·warehouse 도입은 비용 근거를 남긴다.

## 실제 경로·산출물
observability.ts / API client / BFF 요청 완료와 저장 확정 → 안전한 이벤트 수집 → 원본 및 집계 → 집계 조회 API.
지표 사전과 버전, 분모 커버리지, 수집 상태 API를 함께 제공한다. 전체 로그를 페이지 열 때마다 스캔하지 않는다.

## QA·완료 조건
성공·실패·재시도·동일 eventId 재전송·응답 유실·새로고침·오프라인·브라우저/BFF 이중 기록을 검증한다. 같은 업무 실패가 한 번만 집계되고 API 실패 통계는 별도로 유지된다.
수집 중단 시 0%가 아닌 확인 불가가 표시된다. 실패율 = 고유 시스템 실패 시도 / 정의된 전체 시도이며 진행 중·unknown 수가 함께 나온다. 최종 확정 창과 지연 이벤트 재집계 규칙이 문서화된다.

## 중단·복구
계측 비활성화로 사용자 업무는 계속돼야 한다. 잘못된 집계는 원본에서 새 지표 버전으로 재생성한다. 기존 임시저장 데이터를 집계 저장소로 재사용하지 않는다.
