## 확인된 원인과 아직 확인하지 못한 원인

1. 생성 실패 두 건은 기존 구성원별 분당 12회 제한에 걸렸다. 하니스가 연속 요청 속도를 조절하지 않은 문제다. 재측정에서는 제한 안에서 요청 간격을 두고, 제품 제한은 그대로 유지한다.
2. 화면 교체 실패 한 건은 이전 미리보기 확인 단계의 HTTP 409였다. 기존 화면의 폴링과 새 후보 생성이 겹치는 코드 경로가 확인됐으나, 원래 측정에는 단계별 추적 정보가 없어 이 한 건의 원인을 단정하지 않는다. 해당 UI 경계는 별도 수정·회귀 대상이다.
3. 두 세션의 동시 조회는 실제 저장된 API 호출 기록으로 원인을 확인했다. 초기 조회 2건은 성공했고, 이후 20건은 10건 성공·10건 `analytics_query_busy`였다. 각 라운드에서 단일 분석 작업 실행 중 들어온 다른 요청을 즉시 거부했다. CPU 부족이나 OOM으로 추정한 결론이 아니다.
4. 하니스가 매 라운드의 시작 상태 대신 누적 고정 카운터를 기다려, 이전 실패의 영향도 시간 초과로 보이게 했다. 다음 하니스는 라운드별 시작값·실제 성공·오류를 따로 기록해야 한다. 다만 저장 기록에서도 매 라운드 실제 거부가 확인되어 기존 G4 실패 판정은 유지한다.

## 분석 요청 대기 변경

수정 커밋: `44e7b35c` (`fix(workbench): queue bounded analytics requests across actors`).

실제 분석 작업은 계속 한 번에 하나만 실행한다. 서로 다른 구성원이 요청한 경우 한 건만 순서대로 기다릴 수 있다. 한 구성원은 실행·대기를 합쳐 한 건만 점유할 수 있고, 추가 요청은 기존 429로 제한한다. 신뢰된 구성원 식별값이 없는 내부 직접 호출은 기존 즉시 거부 동작을 유지한다.

대기와 실행은 요청 접수 시점부터 기존 최대 3초 예산을 공유한다. 대기 중 취소·기한 초과는 즉시 대기 자리를 반환한다. 실행 중 취소·기한 초과는 작업 종료를 요청하되, 실제 자식 프로세스의 종료가 확인되기 전에는 다음 작업을 시작하지 않는다. 결과 파싱 전후에도 단조 시계로 기한을 확인하므로 타이머 콜백이 늦게 실행된 경우에도 기한을 넘긴 성공을 허용하지 않는다.

구성원 구분값은 서버의 검증된 tenant·actor로 생성한다. HTTP 입력에서 받지 않는다. 기존 SQL 정책, worker 메모리 제한, 데이터·결과 크기 제한, 권한 재확인과 데이터 버전 검증은 유지한다. 원본 DB 쓰기나 권한·서비스 설정 변경은 없다.
