# S9 실제 로그와 GitHub 기반 QA 질의

2026-09-22. 기존 S7/S8 통과와 별도 범위. 운영 데이터 쓰기·배포 없음.

## 사용자 흐름
관리자 → `로그·GitHub QA` → 질문·업무 종류 → 실제 보관 오류 조회 → 오류 기록 선택 → 관측 사실 / 코드상 후보 / 미확인 / 다음 확인.

키 없이 쓰는 기능은 구조화된 근거 조회다. 질문을 이해하는 범용 AI라고 표시하지 않는다. 선택된 오류를 외부 모델이 해설하는 API도 구현했으나 기존 AI 활성 플래그가 꺼져 있으면 실행되지 않는다. API 키·활성화·실제 모델 품질 검증은 별도다.

## 데이터 경로
- `client_error_events`: 수신 시각+문서 ID 복합 커서, 최초 조회 시각 cutoff, 페이지 100건. 같은 시각의 105건 탐색 회귀 테스트.
- `reliability_operations`: 실패 요청 번호로 서버 관측 후보 조회. 로그 계정, 업무 종류, 서버 관측 여부, 수신 시각 주변 120초를 추가 대조한다.
- 요청 번호는 호출자가 지정할 수 있어 인과관계 증명이 아니다. 여러 후보·한도 도달 시 SHA를 선택하지 않는다.
- 화면 SHA는 `release`, 실제 서버 처리 후보 SHA는 `releaseSha`. `ingestRelease`는 오류를 수집한 서버 버전으로, 실패한 요청 버전으로 대체하지 않는다.
- GitHub는 고정 공개 저장소 `merryAI-dev/MYSCube`의 등록된 코드 경로만 40자리 SHA로 읽는다. main 대체, 임의 URL, shell 실행, credentials 전달 없음.
- API 응답 크기, 파일 크기, 8초 네트워크 한도, blob SHA 검증, 제한된 메모리 캐시. 403/429/404/오류를 자료 없음과 구분한다.
- 화면에는 로그 원문·스택·이메일을 반환하지 않는다. 소스 인접 문맥은 토큰·이메일을 제거한다. 읽기 전후 현재 관리자 구성원 상태 확인.

## 실제 운영 읽기 검증
`verify_workbench_live_read.mjs`는 기존 gcloud 로그인으로 읽기만 수행한다. 로그에는 개인 식별자·원문을 기록하지 않는다. 결과 파일 `evidence/workbench-live-read.json`.

2026-09-22 09:21 UTC에 실제 최신 오류 100건을 읽었다. 화면 버전이 있는 기록은 0건이었다. 선택한 오류는 버전 부족으로 코드 연결을 거부했다. 별도로 GitHub의 `a61b75f13abc131c890f7d6952baf8cab20f1bc4` 두 파일을 읽고 blob을 검증했다. **이 SHA가 해당 운영 오류의 버전이라는 뜻은 아니다.**

기존 전체 보관 조사 9,141건과 이번 최근 100건 검증은 서로 다른 시점·범위다. 최신 조사로 과거 전수 조사를 대체하지 않는다. Vercel/Cloud Run 전체 로그는 현재 화면에 연결되지 않았고 이를 명시한다. 과거에 저장하지 않은 SHA를 만들어 복구하지 않는다.

## 검증 기준
권한 변경, 타 계정 요청 번호, 중복 후보, 누락 SHA, 동일 시각 페이지 경계, 부분 GitHub 실패, 소스 무결성, 모델 근거 없는 답변 거부. 실제 GitHub 성공 증거와 에뮬레이터 fixture 성공을 분리한다.
