# S6 — TOI형 화면 제작 파일럿
## 목표·진입 조건
S1 API 계약과 S2~S4 관측·운영 체계를 갖춘 뒤, 반복적인 운영 화면 제작 수요가 있을 때 선택적으로 추진한다. 첫 파일럿은 비식별 오류 집계의 읽기 전용 화면이다.

## 작업
1. 등록된 API 스키마와 허용 UI 컴포넌트만 AI에 제공한다. 인증·권한·정책은 서버가 보장하고 생성 코드가 변경할 수 없다.
2. 코드 초안을 사용자/프로젝트별 버전으로 관리한다. 업무 데이터 초안과 저장소·버전·복원 기능을 분리한다.
3. 처음에는 기존 Vite 기반 격리 프리뷰로 수요를 검증한다. 실시간 코드 편집 요구가 확인되면 esbuild-wasm/가상 파일 시스템/import map을 검토한다.
4. 패키지는 허용된 조합과 lockfile로 고정한다. TOI의 packageSetHash에 대응하는 산출물 ID에는 public entry·lockfile뿐 아니라 빌드 도구/설정 버전도 반영한다.
5. 빌드·정책 검사·실행 준비 확인이 끝난 후보만 미리보기에 표시한다. 실패하면 마지막 정상 화면에 이전 버전임을 표시하고 조작을 차단해 최신 데이터로 오해하지 않게 한다.
6. 검증된 코드 버전만 정상 PR/CI 배포 경로로 승격한다. 생성 직후 운영 반영하지 않는다.

## 보안·실행 경계
별도 origin의 sandbox iframe과 CSP, origin/메시지 스키마 검증을 사용한다. 브라우저 분리만으로 서버 권한이 확보되는 것은 아니다. 프리뷰에는 운영 인증정보·private registry 토큰을 전달하지 않는다. 허용된 API 호출만 제한된 broker를 거치며 임의 네트워크 주소와 쓰기 API는 거부한다.
등록 API URL 변경은 서버 측 검토 대상이며 내부망 임의 호출/SSRF가 가능한 프록시로 확장하지 않는다. 토큰 전달이 꼭 필요하면 단기·제한 범위 프리뷰 자격 증명을 별도 설계한다.

## 실제 경로·산출물
등록 API 계약 + 요청 → AI 코드 초안 → 정적 검증/빌드 → 격리 미리보기 → 승인된 버전 → PR/CI → 운영 화면.
읽기 전용 파일럿, API 계약 레지스트리, 패키지 조합 manifest, 코드 버전 이력, 미리보기 실패 안내가 산출물이다.

## QA·완료 조건
A 사용자의 컴파일/런타임 오류가 B에게 번지지 않는다. 무한 루프·잘못된 import·패키지 중복·외부 통신·권한 없는 API·위조 postMessage를 검사한다. iframe만으로 모든 자원 고갈을 방어한다고 주장하지 않는다.
마지막 정상 버전 표시, 콜드/웜 시작 시간 p50/p95, 빌드 실패율을 측정한다. TOI의 1.3초를 자체 성능 증거로 사용하지 않는다.
운영 데이터 쓰기 불가와 실제 권한 우회 차단을 독립 QA가 검증해야 다음 단계로 간다.

## 중단·복구
프리뷰를 폐기해도 코드 초안은 남는다. 업무 작성 화면에 iframe 전체 교체 방식을 이식하지 않는다. 운영 승격 실패 시 이전 정상 릴리스를 유지하며 작성 중인 업무 데이터를 덮어쓰지 않는다.
