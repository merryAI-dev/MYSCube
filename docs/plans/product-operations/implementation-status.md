## 구현한 것

- 읽기 전용 조사기를 저장소에 추가했다. 날짜 하한 없이 보관된 컬렉션을 조회하고 같은 `readTime`의 COUNT와 대조한다. 조회 중단 시 체크포인트부터 같은 시점으로 재개하며 만료된 스냅샷을 새 시각으로 몰래 바꾸지 않는다.
- 기존 BFF 요청 로그에 등록 초안·수정 초안·제출·조직장 결재의 허용된 경로만 분류한다. 식별자 없는 `operationKey`, 서버 환경·배포 SHA, HTTP 결과를 추가한다. 권한 정책이나 저장 트랜잭션은 변경하지 않는다.
- 호출자가 요청 번호를 보내지 않았을 때 응답·저장 기록과 요청 로그가 서로 다른 번호를 쓰던 경로를 수정했다. 응답에 사용한 요청 컨텍스트의 번호를 로그에서도 우선 사용한다. 통합 테스트에서 실제 응답·Firestore 레코드·요청 로그를 대조했다.
- HTTP 202는 처리 중, 2xx는 HTTP 응답 확인으로 표기한다. 업무 완료율의 분모/성공으로 사용하지 않는다. 연결이 끝까지 완료되지 않은 요청은 현재 finish 로그에 포함되지 않는다.
- 기존 오류 수집에 선택적 클라이언트 환경·배포 정보와 별도 서버 수집 환경·배포 정보를 저장한다. 옛 클라이언트도 계속 받는다. Vite 빌드가 명시된 Sentry 설정 또는 CI/Vercel 배포 정보를 주입하며, 출처가 없으면 빈 버전/미확인 환경을 유지한다.
- 오류 전송의 HTTP 거절·네트워크 실패를 탭 메모리에 기록하고 전송만 5초로 제한한다. 오류 전송 실패를 같은 수집기로 재전송하지 않는다. 이 값은 전사 수집 상태나 영구 이력이 아니다.

새 외부 서비스, 저장 컬렉션, 수집 빈도, 보관 기간을 추가하지 않았다. 기존 이벤트와 요청 로그에 메타데이터를 추가하는 변경이다. JVM 및 주정산·월결산 처리 코드는 변경하지 않았다.

## 실행·검증

```bash
python3 -m unittest discover -s scripts -p test_reliability_audit.py -v
python3 scripts/reliability_audit.py \
  --project inner-platform-live-20260316 --tenant mysc \
  --production-host myscube.myscguard.app \
  --production-host inner-platform.vercel.app \
  --checkpoint /tmp/myscube-reliability-checkpoint.json \
  --output /tmp/myscube-reliability-coverage.json
```

재개할 때 동일 인자에 `--resume`을 추가한다. 체크포인트는 로컬 0600 권한으로 저장하며 Git에 넣지 않는다. 스냅샷 만료 시 새 파일과 새 실행으로 처음부터 다시 조사한다. 실패·총계 불일치 시 exit 2이며 완료를 선언하지 않는다. 인증 정보는 gcloud에서 가져오되 출력하지 않는다.

고정 시점 조회·재개 가능 기간의 근거: [Firestore runQuery 공식 명세](https://docs.cloud.google.com/firestore/docs/reference/rest/v1/projects.databases.documents/runQuery). `readTime` 조회는 일반적으로 최근 한 시간 범위이며 PITR 설정에 따라 더 오래된 시점 지원 여부가 달라진다.

독립 QA에서 Python 8개와 대상 Vitest 10개가 통과했다. 브라우저 UI 변경은 없어 이번 범위는 전송 동작 테스트와 API/저장 통합 테스트로 검증한다. S3에 진입할 때는 별도 사용자 흐름·모바일 브라우저 검증이 필수다.

최종 검증 결과:

- 전체 단위 테스트 재실행: 4,505 통과, 285 건너뜀. 최초 실행은 기존 worker endpoint 테스트 1건에서 예상 503 대신 404로 실패했다. 해당 파일 단독 17개와 전체 재실행이 통과했으며, 일시적 실패의 근본 원인은 아직 확정하지 않았다.
- 최종 Firestore 통합 테스트: 270 통과. 별도 Auth/Firestore/Storage 규칙 테스트: 3 통과. 새 요청 번호 대조와 구형 오류 전송 형식의 실제 저장까지 확인했다.
- 초기 통합 실행은 로컬 Java 경로 부재로 시작하지 못했다. 기존 `/tmp/myscube-followup-java/`의 JDK 21을 사용해 실행했다. 새 구형 클라이언트 테스트에서 필수 idempotency 헤더가 빠진 fixture도 수정 후 재검증했다.
- Vite 제품 빌드 성공. 기존 500 kB 초과 청크 경고는 남아 있다. 타입 검사에서 새 오류 없음(기존 기준선 187개).
- 지정된 QA/Understand 스킬 파일과 지식 그래프는 현재 경로에 없어 적용했다고 주장하지 않는다. AGENTS에 명시된 단계 기준으로 독립 QA가 코드·테스트·조사 결과를 검토했다.

저장소의 `node_modules`가 다른 사용자 경로를 가리켜, 기존 의존성이 있는 `/tmp/myscube-response-hotfix-validation`에 소스를 동기화해 Node 검증을 수행했다. 추적된 링크는 수정하지 않았다. 운영 데이터 쓰기·배포는 수행하지 않았다.

## 이전 기반 작업 시점의 다음 게이트

S1의 사용자 오류 계약과 UI 의도별 operationId는 후속 구현이 필요하다. S2에 앞서 Vercel 실제 요청 로그 접근과 성공 분모 수집 경로를 확정한다. 현재 자료에서 오류율을 복원하거나 단순 HTTP 건수를 업무 성공률로 바꾸지 않는다. S2에서는 저장/자동저장·검증 차단·중복 재시도·서버 저장 확정·응답 유실을 실제 경로에서 분리해야 한다. S3는 그 검증이 끝난 후 역할별 조회와 안내를 연결한다.

### 검증 증거

- 전체 단위 테스트:4,521 통과. 신규 모델 경계/계측 전달 테스트 포함. 일부 통합 테스트는 일반 단위 실행에서는 건너뛰고 별도 에뮬레이터에서 실행한다.
- 전체 Firestore 통합 재실행:294 통과, 별도 Auth/Firestore/Storage3 통과. 이후 추가한 실행 중 권한 변경·이전 응답 재전송 차단 포함 제품 통합9개도 통과.
- 동시 계측 전달에서 Firestore `INVALID_ARGUMENT: Transaction is invalid or closed`가 간헐 발생했다. 수집 성공으로 간주하지 않는다. 테스트는 해당 오류/ABORTED에만 클라이언트 보존 큐의 재전송을 재현하고 최종 업무/집계가1건인지 검사한다. 모든 동시 쓰기의 첫 시도 성공을 증명한 것이 아니다.
- 실제 BFF + Firestore 에뮬레이터 + 브라우저: 개인 설정 저장/재조회/복원 및 관리자→별도 PM 공개 안내2개 통과. 모바일390px 검사와 스크린샷 육안 대조.
- 타입 검사: 새 오류 없음(기존187개 기준선). 제품 빌드 통과, 기존 대형 청크 경고 유지.
- 실제 운영 자료를 수정하는 테스트와 외부 모델 실호출은 하지 않았다. JVM 성공 금액 경로는 기존 port를 주입한 fixture 검증이며, 운영 JVM 전체 사업을 새 화면에서 대조했다는 의미가 아니다.

### 배포 운영 순서

1. `firebase/firestore.rules`의 `reliability_*`, `personal_work_pages`와 하위 이력 접근 차단을 **새 BFF보다 먼저** 반영하고 규칙을 확인한다. 현재 CI의 앱 배포가 Firestore 규칙 배포까지 수행한다고 가정하지 않는다. 이를 생략하면 기존 일반 컬렉션 읽기 규칙이 새 비공개 자료를 노출할 수 있다.
2. PR/CI 통과 후 main 자동 배포로 앱+BFF를 배포한다. 로컬 프로덕션 배포·추측에 따른 workflow dispatch는 사용하지 않는다. JVM 소스 변경이 없으므로 JVM 재배포 대상이 아니다.
3. 운영 계정으로 읽기 전용 화면/버전/권한을 확인하고 이후 발생한 실제 업무 계측을 관측한다. 테스트 목적으로 결재·임시저장을 변경하지 않는다.
4. 자연어 기능은 기본 비활성으로 유지한다. 외부 전송 범위·비용을 별도로 확인하고 설정한 후에만 실제 모델 품질 게이트를 진행한다. 상세는 [S8](s8-cashflow-evidence-assistant.md).

남은 장기 단계는 S4의 실제 배포 전후 성과 분석과 S5의 실험 표본·노출 계측/판정이다. 구현했다는 이유만으로 오류율 감소나 A/B 효과를 주장하지 않는다.

## 활성화 배포 게이트 — 2026-09-22

관리자 AXR 메뉴에서 운영 현황·로그/GitHub QA·개인 페이지·현금흐름 조회를 제공합니다. 초기 AI 활성화는 관리자만 허용합니다. 기존 정산 에이전트와 활성화 플래그를 분리하고 기존 Secret을 재사용했습니다. 새로운 키 또는 JVM 변경은 없습니다.

- 실제 Gemini 합성 smoke: 페이지 schemaVersion1·2026-09 기간 보존·자동 저장 없음 확인(입력768/출력81tokens). QA는 합성 근거 도구1회 호출 후 원인 미확인을 유지하는 partial 결과. 실제 사업 자료는 이 smoke에 전달하지 않았습니다.
- Firestore 운영 규칙의 기존 Git 원문 일치 확인 후 새 private collection 차단만 선반영. 활성 ruleset 내용 일치 확인; 사업 레코드 쓰기0. 증거: `evidence/activation-firestore-rules.json`.
- 새 조회/AI HTTP에만 조직동시2, 사용자60초 고정구간12회. AI는 별도로 조직동시1·사용자하루5회·조직하루20회. 초과는 신규 기능만429, 기존 업무 경로는 admission 저장소도 접근하지 않습니다.
