## 1. 문제와 근거

79개 프로젝트, 125개 요청, 233개 초안의 저장 경로를 조사했다. 실제 저장본을 이용한 읽기 전용 브라우저에서 입력 4단계와 승인 문서 395개 화면을 육안 대조했다. 운영 승인 문서 71개 열람과 로컬 재현은 별개 증거다. 운영 사용자별 저장·승인·다운로드 권한 전체를 검증했다는 의미는 아니다.

현재 입력 폼, 초안 변환, BFF 제출/승인 변환, 승인 문서가 각각 필드를 선별하고 기본값을 적용한다. 그 결과 필드 누락, 공란과 0의 혼동, 금액 요약 차이, 명시적 삭제 미반영이 발생한다. 승인 API에는 조직장이 실제 읽은 요청 버전을 전달하는 보호도 부족하다. PR #801은 일부 제출본 표시·첨부 매핑·JLIN 비율을 개선하지만 전체 해결 기준은 충족하지 못한다.

## 2. 범위와 이번에 하지 않는 일

이번 스프린트에는 신규 등록 초안, 기존 프로젝트 수정 초안, 최종 제출, 조직장 검토·승인, 승인 완료 문서, 공통 금액·첨부·인력 표시 및 구체적인 오류 안내를 포함한다. 개인 초안과 최종 제출본이 다를 수 있다는 정상적인 차이도 화면에서 설명한다.

다음은 별도 작업이다: KDB 등 기존 상태의 일괄 수정, 농산업 등의 금액 자동 보정, 종료사업 체크아웃과 주정산·월결산의 새 업무 흐름, 50MB·다중 확장자 업로드 확대, 인증 토큰/15분 세션 개편, 신규 DB·백엔드 프레임워크 이관, 모든 과거 제출 버전의 영구 보존. 현재 첨부의 참조·표시·권한 구분은 이번 범위다. 기존 요청을 삭제하거나 전체 WIP stash를 복원해 다른 작업을 섞지 않는다.

## 3. SSoT와 데이터 소유 원칙

| 구간 | 기준 데이터 | 반드시 보장할 것 |
|---|---|---|
| 작성·재열기 | 해당 사용자의 활성 초안 + draftRevision | 다른 사람의 초안 비노출, 저장 중 입력 및 첨부 보존 |
| 최종 제출 확인 | 서버가 저장하고 반환한 요청 버전의 제출본 | 이후 초안·최신 원장으로 조용히 교체하지 않음 |
| 조직장 검토 | 동일 요청 버전의 제출본 | 실무자 제출 확인과 업무값·계산·검증 결과 일치 |
| 승인 | 검토한 버전 + 현재 원장 버전 조건을 충족한 transaction | 해당 제출본의 허용 필드만 반영, 운영 전용 값 보존 |
| 승인 완료 문서 | 해당 결정의 approvedSnapshot 또는 연결된 제출본 | 현재 프로젝트를 과거 승인 내용처럼 표시하지 않음 |
| 현재 사업 운영 | 승인된 원장과 별도 운영 상태 | 주정산·월결산 잠금·실입금·예산을 일반 수정 승인으로 초기화하지 않음 |

기존 Express BFF·Firestore·React를 유지한다. 프로젝트 제출 전용 공통 필드 계약에 저장 키, 소유 범위, 삭제 의미, 첨부 종류, 표시 라벨 및 파생 계산을 연결한다. 권한·DB 접근·transaction은 BFF에 둔다. 공통 타입만 만들고 실제 저장 경로를 그대로 두는 작업은 완료로 인정하지 않는다.

신규 제출에만 서버가 `snapshotSchemaVersion`을 부여한다. 이번 버전 1은 제출 필드 소유 계약의 표식이며 모든 필드가 채워졌다는 보증이 아니다. 필수값 검증은 기존 업무 정책을 따른다. 필수입력 정책 버전과 구분한다. 과거 요청의 키 누락은 현재 값으로 보충하거나 명시적 삭제로 해석하지 않는다. 신규 요청도 기존 requestId/requestVersion 방식에 맞춰 처리하며, 현재 구조가 모든 과거 본문을 영구 보존한다고 가정하지 않는다.

## 4. 임시저장 보존 계약

| 상황 | 기대 동작 | 검증 증거 |
|---|---|---|
| 불완전한 입력·필수 첨부 없음 | 임시저장은 허용하고 최종 제출 검증과 분리 | 신규/수정 초안 저장 후 재열기 값 대조 |
| 저장 요청이 진행되는 동안 사용자가 계속 입력 | 늦게 도착한 응답이 최신 로컬 입력을 덮지 않음. 저장 성공 표시는 서버 확인된 revision 기준 | 응답 순서를 바꾼 브라우저 테스트 |
| 새로고침·재로그인·네트워크 실패 | 서버에 저장된 revision 복구, 미확인 저장을 성공으로 표시하지 않음 | 실패 응답·재열기·권한 만료 사례 |
| 여러 탭·다른 사용자 편집·lease 만료 | 기존 lease/fence/revision 충돌 보호 유지. 충돌 시 입력 유지와 재확인 안내 | 충돌 응답과 양쪽 초안/원장 대조 |
| 종료 기간 없음 해제·폴더 링크 비움·선택 첨부 제거 | false/빈 문자열/null/빈 배열의 의미를 끝까지 보존 | 초안→제출→승인→원장 재조회 |
| 최종 제출 검증/transaction 실패 | 초안 payload·첨부 참조 유지, 성공 화면으로 이동하지 않음 | 실패 전후 저장 레코드 동일성 |
| 최종 제출 성공·응답 유실·재시도 | 기존 idempotency와 transaction 의미 유지, 요청 중복 생성 없음. 정리는 commit 성공에만 연결 | 같은 키 반복 요청 결과 및 초안 상태 |
| 회수·반려·재제출 | 기존 허용 상태 전이 유지. 수정본은 새 요청 버전, 이전 결재창 승인 거부 | 전체 lifecycle 테스트 |
| 첨부 교체/참조 제거 | 초안의 참조 변경과 파일 물리 삭제 분리. 제출본이 참조하는 파일 보존 | 초안·요청 attachmentRefs 및 객체 참조 검사 |

임시저장 성공은 서버 확인이 있는 경우에만 표시한다. 브라우저 강제 종료 직전의 미저장 입력까지 복원한다고 약속하지 않는다. 별도 로컬 영구 저장 도입은 개인정보·만료 정책 검토 없이 추가하지 않는다. 불필요한 취소·중단 처리 계층도 늘리지 않는다.

| S6 / 프론트 | 금액·비율·통화·미등록 표시 및 오류 안내 통일 | 단년도 연도 요약 0 오표시 해소. 구형 전체 입금계획 보존 표시. 긴 URL 겹침 없음. 상태와 이력 미기록 구별 | S5 |
| S7 / 독립 QA | 전체 왕복·회귀·79개 자료 재대조 | 7절 gate 통과와 증거 첨부. 수정 전/후 차이를 의도된 변화와 회귀로 분류 | S2~S6 |

S3은 신규 등록과 수정의 차이를 보존한다. 신규 등록은 기존 정책에 따라 PENDING 프로젝트 생성이 동반되며, CHANGE 최종 제출은 승인 전 원장 업무값을 바꾸지 않는다. 승인 projection은 기존 지정 결재자·권한·base/target 버전 검증을 대체하지 않는다.

주요 작업 위치: `src/app/platform/` 공통 계약·editor·request·review 모델, `src/app/components/projects/` 입력/검토/승인 화면, `src/app/lib/platform-bff-client.ts`, `src/app/data/types.ts`, `server/bff/schemas.mjs`, `server/bff/routes/project-info-drafts.mjs`, `project-registration-drafts.mjs`, `projects.mjs`. 실제 호출 관계 확인 후 파일 범위를 확정한다. JVM은 실제 호출/변환 경로에 변경 필요성이 확인된 경우만 포함한다.

실패 gate는 일정 때문에 건너뛰지 않는다. 독립 작업은 병행하되 프론트와 서버의 연결 검증 전 개별 완료를 전체 완료로 취급하지 않는다. 각 변경은 공통 계약으로 수렴하는 리뷰 단위이며, 필드마다 임시 fallback을 추가하는 식으로 마무리하지 않는다.

## 7. QA 단계와 수용 기준

| Gate | 통과 기준 | 증거 |
|---|---|---|
| G1 의도·실제 경로 | UI state→API→초안/요청/원장→outbox/sync→다른 화면의 경로와 필드 소유 정의 완료 | 호출 경로·매트릭스·정책 결정. 표면 라벨만 수정하는 계획은 반려 |
| G2 구현 | 실제 저장/승인 경로가 공통 계약 사용, 초안과 운영 필드 보존 | 기존 실제 handler+Firestore emulator 통합 테스트, 저장 전후 비교 |
| G3 사용자 흐름 | 실무자와 관리자 세션에서 동일 요청 버전의 값·첨부·검증 안내 일치 | 격리 환경의 브라우저 화면, API 요청/응답, 승인 후 persisted read |
| G4 회귀·배포 | loading/empty/error/권한 거절/중복 저장/구클라이언트/회수·재제출/legacy 통과 | 자동 검사·독립 육안·배포 결과. 운영에서 승인/저장 버튼을 눌러 시험하지 않음 |

필수 시나리오:

1. 신규 등록과 기존 수정 각각 임시저장→재열기→제출 확인→조직장 검토→승인→원장 조회.
2. 제출 뒤 작성한 다른 초안은 승인 문서에 섞이지 않으며 다른 사용자에게 노출되지 않음.
3. v1 문서를 연 뒤 v2 재제출: 오래된 승인 거절, 사용자의 결재 의견 보존. 버전 가드를 제거하면 테스트 실패.
4. 기간 없음 true→false, 폴더 문자열→빈값, 선택 첨부→null, 숫자→0을 왕복 보존. 기존 잘못된 생략 로직으로 되돌리면 테스트 실패.
5. 과거 sparse 요청의 키 없음이 기존 원장 첨부·예산·운영 값을 지우지 않음.
6. 단년도, 다년도, 연도별 배분 없는 전체 계획, 부분 연도, 분모 0, 미입력/명시 0, USD 모두 양쪽 동일 의미.
7. 저장 당시 월별 참여율과 현재 외부 시트가 달라도 검토 문서의 제출값 불변. null과 0% 구별.
8. 첨부 파일만/링크만/둘 다/명시 없음/기록 없음/접근 불가를 구별. 표시 실패가 미제출로 둔갑하지 않음.
9. 승인 완료·철회·대기·반려와 결재 이력 미기록을 구분. 오래된 승인 메모로 새 요청을 완료 처리하지 않음.
10. 기존 79개 fixture 전수 재검사 및 영향 화면 육안 대조. 사라진 과거 payload·다운로드 권한·파일 본문 미검증은 별도 명시.

관련 unit/route 테스트, `npm test`, `npm run bff:test:integration`, `npm run build`를 실행한다. 계약 파괴 시 테스트가 실패하는 사보타주 검증을 포함한다. 실행 환경 차이·기존 실패는 기준 커밋과 비교하여 보고하고 통과로 숨기지 않는다. 테스트 건수만으로 사용자 흐름 통과를 대체하지 않는다.

최종 오류 UI는 ‘무엇이 문제인지 / 어떤 제출 내용인지 / 누가 어디서 어떻게 수정하는지’를 업무 용어로 보여준다. 예: ‘검토 중 제출 내용이 변경되었습니다. 작성자가 다시 제출한 내용을 확인한 뒤 승인해 주세요.’ 내부 토큰·민감 응답·스택은 노출하지 않고 문의용 추적 번호만 제공한다. 필드 오류는 상세 목록과 해당 항목 이동, 시스템 오류는 입력 보존·재시도 가능 여부를 구분한다.

## 8. 호환 배포와 롤백

1. PR #801 변경을 포함한 대상 기준 SHA와 미배포 상태를 확인한다. 감사 문서의 과거 상태를 현재 배포 상태로 가정하지 않는다.
2. 서버에 추가 필드 읽기 호환과 version/token 응답을 먼저 준비하고 새 프론트가 이를 전송하도록 연결한다. marker 없는 기존 초안/요청을 계속 읽을 수 있어야 한다.
3. 버전 없는 승인 요청을 거부하는 전환 시점을 명시한다. 새 프론트 반영 후 강제 검증을 활성화하고 구클라이언트는 새로고침을 안내한다. 전환 중 무보호 구간을 허용할 수 없다면 승인 작업에 한정한 짧은 중단·안내를 배포 계획에 명시한다. 무기한 permissive 경로는 남기지 않는다.
4. 제출/승인 쓰기 계약 변경 전에 구버전 서버가 새 snapshot을 읽고 처리할 수 있는지 확인한다. 안전한 롤백 대상이 아니면 전체 이전 버전 복귀 대신 호환 수정 또는 영향 쓰기 경로의 명시적 중단을 선택한다. 서버 저장 데이터는 되돌리거나 초안 삭제로 복구하지 않는다.
5. main CI 성공에 따른 `Production Deploy` 자동 실행·완료 SHA를 확인한다. 로컬 production 배포 및 일반 수동 dispatch는 사용하지 않는다. JVM은 실제 소스 변경이 있을 때만 기존 자동 배포 정책을 따른다.
6. 배포 직후/다음 영업일에 저장 실패, 제출 실패, 정상적인 409와 비정상 증가, 승인 실패, outbox/sync 실패를 기존 로그와 비교한다. 배포 전 기준 빈도와 담당자를 S8 시작 전에 기록한다. 급증·원장 변경 이상 발견 시 확대를 중단한다.

로그에는 requestId·version·draftRevision·오류 코드 등 추적 가능한 최소 식별정보를 사용하며 토큰·첨부 접근 URL·폼 전체·개인정보를 새로 수집하지 않는다. 별도 관측 서비스 도입 없이 기존 로그·audit·outbox를 활용한다.

## 9. 착수 시 결정할 정책과 완료 정의

| 결정 | 권장 기본값 / 미결정 시 처리 |
|---|---|
| 계약총액과 구성합 불일치의 제출/승인 차단 여부 | 임시저장 허용. 양쪽 동일 경고 먼저 제공. 신규 차단은 업무 정책 확인 후 적용, 과거값 자동 보정 금지 |
| 별도 당해연도 예산의 소유권 | 일반 수정 승인에서 보존 권장. 업무 정책 확인 전 자동 재계산 확대 금지 |
| 구형 버전 없는 결재 보호 | 서버 revision token 비교 권장, 가짜 requestVersion 생성·데이터 backfill 금지 |
| 종료 상태와 체크아웃 | 이번에는 출처·상태 표시 정렬과 원장 보존. 전환 정책/주정산·월결산 연결은 별도 스프린트 |
| 승인 버전 보호 전환 시간 | 새 UI 배포 확인 후 강제 검증. 구클라이언트 처리와 필요 중단 범위 확정 |

완료는 다음을 모두 만족할 때다: 공통 필드 계약으로 실제 저장/조회/승인 경로 연결, 초안 보존, 검토 버전 승인 보장, 양쪽 화면 공통 표시/검증, 운영 필드 보존, 독립 QA 통과, CI·배포 SHA·운영 읽기 확인, 알려진 미검증 범위와 기존 데이터 확인 목록 공개. 정책이 미결정인 항목은 완료로 표시하지 않는다.

이번 문서는 계획 산출물이므로 문서 QA는 조사 근거·내부 링크·의존 순서·안전 조건·수용 기준을 검토한다. 제품 변경이 없어 문서 작성 자체에 브라우저 재시험은 필요하지 않으며, 구현 단계의 브라우저 QA는 위 gate에서 필수다.

### G1 보완 — 숫자 원문과 명시 삭제

유효하지 않은 숫자 편집 원문은 기존 로컬 보존/원격 저장 차단을 유지한다. 0·NaN으로 바꾸거나 기존 numeric payload에 문자열을 저장하지 않는다. 서버 초안은 현재 UI가 보유한 유효 draft 값을 보존하며 최종 제출 정규화와 분리한다. 새 raw 원격 저장 형식 도입은 이번 범위가 아니다. 필드별 소유권·삭제 의미는 공통 계약 파일과 테스트로 고정하고 필수값 null은 기존 제출 검증으로 거부한다.
